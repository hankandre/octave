# Security boundary

This is Octave's security design for the TV app: where the token is held, how requests leave the device, and how server addresses are trusted. Every claim names the test that proves it today, or the task that will add the test. **Tested** means a test on `main` proves it; **Planned (T…)** means the rule is binding but its test does not exist yet, and the named task adds it. Nothing below is stated as tested that is not.

The desktop app proved the same rules for libmpv with its own native tests. They live in the tag `desktop-tauri-final`; what each proved, and what a future libmpv engine must pass, is in [`docs/mpv-options-checklist.md`](mpv-options-checklist.md).

## 1. The token boundary

The access token is the one secret Octave holds. Jellyscale requires it on every media request, so it travels on every request, always in the `Authorization: MediaBrowser … Token="…"` header and never anywhere else. [Decision 0005](decisions/0005-token-boundary.md) (accepted 2026-11-20) sets where it lives on Android: **native memory only. The token never enters JavaScript.**

### Where the token is, and who does HTTP

- **On Android the token is held only by the native session module's session registry and its encrypted store.** It never enters JavaScript. The core holds an opaque session id: 128 random bits made by Kotlin at sign-in or restore, not derived from the token, meaningless to the server. The id may appear in props; it is kept out of logs by habit.
- **Kotlin sends every request.** The core decides catalog requests (path, query, body) and parses their responses; Kotlin adds the header and sends them through the one client (§2). Kotlin alone sends and parses the two sign-in calls (`POST /Users/AuthenticateByName`, `POST /Users/AuthenticateWithQuickConnect`); their responses never reach JavaScript. Before sign-in, `GET /System/Info/Public`, `GET /QuickConnect/Enabled` and the Quick Connect initiate and poll calls go through the same transport with the tokenless header, to a fixed list of paths.
- **What crosses at sign-in:** the password or the Quick Connect secret, once, from JavaScript to Kotlin, as an argument of `signIn`; Kotlin does not keep it after the call returns. The DeviceId is derived in the core and passed in; it is not a secret.
- **Token echoes are removed.** Jellyfin echoes the token in some response bodies (an external subtitle `DeliveryUrl` with `ApiKey=…`, a `TranscodingUrl` with `ApiKey=`). Before any body crosses to JavaScript, Kotlin replaces every occurrence of the session's token value, as written and percent-encoded, with a fixed marker. The filter is by value, so it does not depend on which routes echo it.
- **In Node** (tests and the tripwire) the core's `JellyfinGateway` holds only the opaque session id. The reference transport (`packages/core/src/adapters/fetch-transport.ts`) holds the token in an ECMAScript `#private` field, so a walk of the gateway cannot reach it. That path never runs on the TV.

### The native session surface

Four methods and one event, in a session module of their own that shares the registry with the player module. Adding a method or an event is an architecture change that needs a decision record. Three of the five members exist (T3-05): `signIn`, `request` and `endSession`, with the shapes in decision 0005's T3-05 amendment (each takes one map and resolves one map; every outcome is a value with one of the core's seven error codes; none rejects on purpose). `restoreSessions` and `sessionEnded` are T4-05's. `ModuleSurfaceTest` holds the module's JavaScript surface at exactly the three.

| Method | Takes | Returns |
|---|---|---|
| `signIn` | origin, DeviceId, and a password credential or a Quick Connect secret | `{ session, userId, userName?, serverId? }` or an error code |
| `request` | a session id (or, for the fixed pre-sign-in paths, the server's base URL and a DeviceId), a method (`GET`, `POST`, `DELETE`), a server path, query pairs, a JSON body, a timeout | `{ status, body }` or an error code |
| `restoreSessions` | nothing | a list of `{ session, origin, userId, userName, serverId }` |
| `endSession` | a session id | nothing; always succeeds locally |

Event: `sessionEnded { session, reason }`, where `reason` is a fixed code (`revoked`, `store-unreadable`).

`request` is not a general HTTP bridge: it accepts no header and no absolute URL (the path must start with `/` and resolves against the session's server URL, base path included); it sends through the one client; a 3xx or a status of 0 is an error, never followed; any URL with a credential parameter or the token value is refused; errors are codes, and no error, result or event carries a header, a URL or a play-session id. Since T3-16 a path with a `.` or `..` segment (as written or percent-encoded, up to four rounds), a backslash, a control character, or an escape that is malformed or not UTF-8 is refused before anything is built; the URL sent is the session's base path plus the path exactly as written, and the one client refuses a session call outside the base path, or one whose encoded path still holds a dot segment (up to four rounds of decoding) or an escape that is not UTF-8. An answer over its class's cap (1 MiB before sign-in, 4 MiB for a session's `POST` or `DELETE`, 8 MiB for a session's `GET`) is `unexpected-response`, decided before it is parsed.

### The session registry and authority

The registry maps a session id to its origin, header and token, and nothing outside the module's HTTP package can read an entry. It holds more than one session. The player's launch request carries a session id and token-free URLs (T2-05, T8-01); the image view takes an item id, image type, tag, size and session id (T3-11). Both ask the registry for the client and never see the header. A recreated activity or a restarted JavaScript runtime calls `restoreSessions` and gets the same ids back while the process lives.

### The stored credential

A token is persisted only as one encrypted record per session, written and read only by Kotlin: AES-256-GCM under a key generated in the Android Keystore (the key never enters the app process), stored under `getNoBackupFilesDir()`, which Auto Backup always excludes. Backup is also off app-wide (§6). The key needs no user authentication (a TV has no screen lock to rely on). Users stay signed in by default. A record is removed in three ways:

- **Sign-out.** `endSession` removes the registry entry and deletes the record first, then sends `POST /Sessions/Logout` with the token held in a local variable. A failed or refused logout is reported as a code and changes nothing locally.
- **A confirmed 401.** When an authenticated request gets 401, Kotlin sends `GET /Users/Me`; if that is also 401 it ends the session as sign-out does, without the logout call, stops any player using it, and emits `sessionEnded` with `revoked`. One 401 alone does not sign the viewer out.
- **An unreadable record** (the key is gone, the ciphertext fails its tag) is deleted and reported as `store-unreadable`.

### Development builds

In a debug variant the debugger and the dev-launcher network inspector can read the header. Rule (owner, 2026-11-20): **a development build signs in only to a development server**, never to a server holding a real library. A release build contains no inspector wiring.

### Residual risk

Code running inside the app process, or root, can read the token: same-process Kotlin memory is not a boundary against it. Decision 0005 protects against accidents, JavaScript state, logs, and third-party JavaScript. A crash reporter, over-the-air JavaScript updates, or any third-party runtime code would reopen the decision.

## 3. Server addresses (decision 0001 on Android)

[Decision 0001](decisions/0001-private-lan-http.md) holds unchanged: HTTPS is accepted for every host; plain HTTP depends on the literal host, never a DNS answer. The address must also be written in plain ASCII (`classifyServerAddress` in `packages/core/src/domain/host-class.ts`): `http` or `https`, then a host of ASCII letters, digits, `.`, `_` and `-` or a bracketed IPv6 literal, with no `%`, user info, backslash or tab, and the parsed host must be plain ASCII with no `xn--` label (any case). An address that fails either test is public, so plain HTTP to it is refused. These rules need no URL parser to agree, so the Kotlin classifier mirrors them from the same vectors.

- Loopback (`localhost`, `127.0.0.0/8`, `::1`) needs no confirmation. Private LAN (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `fc00::/7`, `fe80::/10`, `*.local`, `*.home.arpa`) needs a one-time confirmation per server `Id` and origin. Every other host, including CGNAT `100.64/10`, is public and refused for plain HTTP before any request. IPv4-mapped IPv6 takes the class of the embedded IPv4 address. A name with an internationalized (`xn--`) label is public for plain HTTP. URLs containing user information are refused. Tested: `packages/core/src/domain/host-class.test.ts` against `packages/core/tests/fixtures/host-classes.json`.
- The gateway refuses a public `http://` URL before an HTTP client exists. For a private-LAN `http://` server it sends only the unauthenticated `GET /System/Info/Public` probe, then refuses password and Quick Connect sign-in until the viewer has confirmed the warning for that server `Id` at that exact origin. Tested: `packages/core/src/jellyfin/gateway.test.ts`.
- The confirmation record holds only the server `Id` and origin, never a token. The `Id` is public, so the confirmation is not proof of identity (decision 0001, accepted residual risk). The port is `packages/core/src/lan-http-confirmations.ts`; the TV store is Planned (T4-02).
- **Cleartext on Android.** Android's network security configuration cannot express CIDR ranges or `*.local` for IP literals, so the app allows cleartext app-wide and the host classifier is the enforcement point: the core refuses a public `http://` address before the transport is called (tested above), and the native client refuses it again before any request, with a Kotlin classifier that passes `packages/core/tests/fixtures/host-classes.json`. The native refusal is tested: `modules/session/android/src/test/java/dev/octave/session/http/HostClassTest.kt` (T3-03).
  - Where it lives (T3-15): `modules/session` declares it, beside the one client and the classifier, in its `AndroidManifest.xml` (`android:networkSecurityConfig`) and `res/xml/octave_network_security_config.xml`, which holds one `base-config` with `cleartextTrafficPermitted="true"` and nothing else. The manifest merger carries it into the app. Every other value keeps the platform default, so HTTPS trust is the system store, unchanged.
  - What it removes: Android no longer blocks plain HTTP from any code in the app's process. Octave's own code can send only through the one client, which the classifier guards; the HTTP clients React Native and Expo link are fenced by `pnpm lint:network` and ESLint (T3-04) and, on the release APK, by the dex check in `pnpm tv:apk:check` (T3-19), not by Android.
  - Tested: `scripts/tv-cleartext.test.ts` (the judges and the two source files); `pnpm tv:apk:check` reads the configuration from the release APK through its manifest and resource table, and `pnpm tv:e2e` does the same for the e2e APK; `CleartextProbe` (the module's `src/androidTest`) under `pnpm tv:e2e` sends plain HTTP through the one client to a private-LAN address (`10.0.2.2`) and to loopback on the emulator, in the module's test APK under the same declaration, and every public vector of `host-classes.json` is refused before a request exists.
  - Tested (T3-05): a plain-HTTP request from the release-type app's own process to a private-LAN address. Wire test `transport-private-lan-and-proxy` sends `GET /System/Info/Public` through the one client to `http://10.0.2.2:<port>` on the emulator, and the mock's private-LAN origin counts the requests whose `Host` is exactly that address, which no request through `adb reverse` carries. Its judge fails the pair without one (`judgeWire`, `scripts/tv-wire-private-lan.test.ts`, item 9; negative control: a device file that probed the reversed loopback port instead failed with `privateLan=0`). The address comes from the mock's answer, and only `privateLanProbeTarget`'s exact `http://10.0.2.2:<port>` is followed; this is harness code under `src/e2e/`, never app behaviour.
  - Planned, with no owning task: HTTPS with a real certificate on the device. `tasks/backlog.jsonl` asks the Product Owner to place it.
- After the viewer confirms, the password, access token, and media cross the LAN unencrypted. The warning says so.
- A host classifier that sees a non-ASCII host fails closed, because Expo's URL implementation, `whatwg-url-minimum`, has only "Small IDNA/TR46 support" (its README; the rules do not depend on it). Tested by `packages/core/src/domain/host-class-non-ascii.test.ts`, `packages/core/src/jellyfin/gateway-non-ascii-host.test.ts` and the conformance suite (`packages/core/src/conformance/url-conformance.ts`) against both shared URL files, which `pnpm tv:e2e` also runs on the Android TV emulator under Hermes with Expo's URL (T3-02). An HLS master URL or server URL whose host is not written in plain ASCII is refused with detail `host`.

### LAN discovery

Discovery (T4-01) sends one fixed datagram, `who is JellyfinServer?`, with no token, device id, or user data, to the IPv4 broadcast address on UDP 7359, and reads for a fixed time. Every reply is untrusted: oversized or malformed replies are dropped, names are stripped of control and bidirectional characters and capped, and a reply is listed only when its `Address` passes the host-class rule. Choosing one runs the normal probe, which must report the discovered `Id`, and then the confirmation. The `Id` is public, so a spoofed reply can copy it; the sign-in screens show the exact origin for every sign-in, typed or discovered. Planned (T4-01).

## 5. What is not protected

- Anyone on a confirmed private LAN can read plain-HTTP traffic, token included (decision 0001).
- A device that holds a confirmed LAN address and port on another network and presents a copied server `Id` inherits the confirmation (decision 0001, decision 7).
- A spoofed discovery reply can relay Quick Connect; the visible origin is the only cue.
- Code inside the app process, or root, can read the token (§1).

Persisted state is limited to the encrypted credential records (§1, T4-05), the preferences record, and the LAN confirmations. None of it is backed up or carried to another device (§6). Playback positions, track choices, and play-session ids are not persisted. Authentication secrets must never be added to Query caches, analytics, crash payloads, or diagnostic exports. Octave has no analytics and no third-party services.

## 6. The release manifest

The release APK is built to ask Android only for what Octave uses, and to declare backup and device-to-device transfer off (T3-22). The declarations are **Tested** below; that no Octave data leaves a device through either is **Planned (T4-05, T4-09)**. `apps/tv/plugins/with-trimmed-manifest.js` trims the manifest and writes the backup rules; `scripts/tv-apk-manifest.mjs` reads both out of the built APK with `aapt2 dump xmltree` and fails on anything else. `pnpm tv:apk:check` runs it after the badging check, and the `tv` job runs `pnpm tv:apk:check` on the release APK it builds.

### Permissions and queries

The release APK holds these permissions and declares no package-visibility query:

| Entry | Kind | Why |
|---|---|---|
| `android.permission.INTERNET` | uses-permission | Every server request |
| `dev.octave.tv.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | uses-permission and declared permission (`protectionLevel="signature"`) | `androidx.core` adds it so receivers registered at run time are not exported; it grants nothing outside the app |

Removed, because Octave does not use them:

- `android.permission.SYSTEM_ALERT_WINDOW` (Expo template): draws over other apps; only React Native's developer overlay reads it.
- `android.permission.VIBRATE` (Expo template): a TV has no vibrator and nothing calls React Native's `Vibration`.
- `android.permission.READ_EXTERNAL_STORAGE` and `android.permission.WRITE_EXTERNAL_STORAGE` (template and `expo-file-system`): Octave reads and writes no shared storage.
- The `VIEW` + `BROWSABLE` + `https` query (template): Octave opens no link in another app.
- The `OPEN_DOCUMENT_TREE` and the any-MIME `VIEW` queries (`expo-file-system`): Octave picks no folder and hands no file to another app; the second would also make most installed apps visible to Octave.

The rule: every `uses-permission` (any `uses-permission-sdk-*` too), every declared `permission`, `permission-group` and `permission-tree`, and every child of `<queries>` in the release APK must be on the named lists `ALLOWED_PERMISSIONS`, `ALLOWED_DECLARED_PERMISSIONS` and `ALLOWED_QUERIES` in `scripts/tv-apk-manifest.mjs`, or `pnpm tv:apk:check` fails naming the entry. A task that needs a new entry adds it with its reason to the list and to this section in its own PR. **Tested** for the check (`scripts/tv-apk-manifest.test.ts`, T3-22, including the recorded manifest of a build before this task, which fails with one line per removed entry) and for the release APK (`pnpm tv:apk:check` in the `tv` job). A debug build still declares `SYSTEM_ALERT_WINDOW` for the developer menu; the rule covers the release APK only.

### How the check reads attributes

The check reads each attribute as Android does, so no other attribute can stand in for the one Android uses (T3-23).

- From `AndroidManifest.xml` it takes an attribute only when `aapt2 dump xmltree` prints a framework resource id for it (`(0x01` and six hex digits), which is how Android finds an attribute. An attribute in another namespace, or in none, is not read, and it carries no id. Probed (`docs/specs/T3-23.md`, "Probe re-run"): the merger and aapt2 kept a `name` in another namespace and in none on a `uses-permission`, in the app's manifest and in a library's, and an `allowBackup` in another namespace and in none on the app's `<application>`. Unverified: a library `allowBackup`; the check treats it the same way regardless.
- From the data extraction rules file it takes an attribute only when it has no namespace, which is how Android reads `domain` and `path`.
- An element with two attributes of one local name, in any namespace and in either order, fails the check, naming the element and the attribute. No later attribute replaces an earlier one.
- An attribute line that could be read two ways fails the check as unreadable: a namespace holding `=`, a quote, `(` or whitespace; a quoted value holding a quote; a `(Raw: "…")` copy that differs from the value; any other text after the value. Tested by `scripts/tv-apk-manifest-namespace-extra.test.ts`. Not covered: a namespace holding a line break (plan 006, `tasks/backlog.jsonl`).
- Elements are read by their local name, as Android reads them.
- From the network security configuration file (`scripts/tv-apk-check.mjs`, T3-15) it takes every attribute by local name, in any namespace, as Android does, and the same duplicate rule fails a second `cleartextTrafficPermitted` or `usesCleartextTraffic`. **Tested**: `scripts/tv-cleartext-duplicate-extra.test.ts`.

**Tested** (`scripts/tv-apk-manifest-namespace.test.ts` and `scripts/tv-apk-manifest-namespace-extra.test.ts`, on recorded dumps with lines inserted; `pnpm tv:apk:check` on the APK the `tv` job builds). The check reads the APK our build made; a hand-forged binary manifest whose name strings disagree with its ids is outside what it guards.

### Backup

Backup is off. The application declares `android:allowBackup="false"`, which turns off backup on Android 11 and lower and cloud backup on Android 12 and higher, and `android:dataExtractionRules` naming a rules file whose `<cloud-backup>` and `<device-transfer>` sections each exclude every domain (`root`, `file`, `database`, `sharedpref`, `external` and the four `device_*` domains) and include nothing. Device-to-device transfer needs the second section: on Android 12 and higher some devices run it despite `allowBackup="false"`, and a missing section means the mode is fully on. The declarations are meant to keep every credential, LAN confirmation, preference and install id out of a backup or a transfer; that this holds on a device is **Planned (T4-05, T4-09)**. The check also refuses a `fullBackupContent` other than `false`, a `backupAgent` and a `fullBackupOnly`.

- The declarations (`allowBackup="false"`, the `dataExtractionRules` reference resolving to one rules file, both sections, every domain excluded, no include): **Tested** (`scripts/tv-apk-manifest.test.ts` and `scripts/tv-manifest-trim-extra.test.ts`, T3-22, on recorded dumps of a release APK; `pnpm tv:apk:check` on the APK the `tv` job builds).
- That nothing Octave stores leaves the device through a cloud backup or a device-to-device transfer: **Planned (T4-05, T4-09)**. The check reads the manifest and the rules file; it runs no backup or transfer on a device, and that `path="."` excludes a whole domain on a device is unverified.
- No `cross-platform-transfer` (iOS) section is declared; Octave has no iOS app to match.
