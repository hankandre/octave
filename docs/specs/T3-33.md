## Goal

`docs/security.md` says a development build signs in only to a development server, because in a debuggable build the debugger and the network inspector can read the `Authorization` header. Nothing enforces it. After this task the native session module enforces it: in a development build it sends nothing to a server whose host is not loopback, the emulator host `10.0.2.2`, or a host the developer listed at build time on their own machine. The refusal happens before any request, crosses to JavaScript as the existing `refused` code, and carries no address. A release build is unchanged and holds no list.

The second half of the finding, that a debug build's Metro and inspector path must not point at a LAN address, is recorded with what already covers it, and its one open part went back to the Product Owner because no test of it can exist inside the rules this task may change. The Product Owner closed it as recorded (option C), with backlog entry 295 asking a later pass to weigh a fence.

## Which builds are development builds

One input decides: the app's `ApplicationInfo.FLAG_DEBUGGABLE`, read at run time by `OctaveSessionModule`. The module's own build type is not used, because it is wrong for `debugOptimized` (Facts) and because the JVM tests and the device probes run in the module's debug variant.

| Build | How it is made | Debuggable | Development build | Allowlist it holds |
|---|---|---|---|---|
| `debug` | `./gradlew :app:assembleDebug`, by hand | yes | yes | `OCTAVE_DEV_SERVERS` of the build machine, or none |
| `debugOptimized` | `./gradlew :app:assembleDebugOptimized`, by hand | yes | yes | none: it links the module's release variant, so only loopback and `10.0.2.2` qualify |
| `release` | `pnpm tv:build` | no | no | none |
| e2e | `pnpm tv:e2e:build` (release build type) | no | no | none |
| The module's probe test APK | `octaveDeviceProbeApk` (module debug variant) | n/a | not judged: it never builds a `SessionTransport` | the debug `BuildConfig` field is present and holds what Gradle was handed (the canary when `scripts/tv-build.mjs` builds it), but nothing reads it; the APK judge is never given this APK |

When the module cannot read the flag (no React context), it counts the build as a development build for that one call. That fails closed. The transport built then is not kept: the module keeps a transport only once it was built from a context, so a first call without a context cannot make a release build refuse for the life of the process (spec check issue 5).

A build type added later is a development build exactly when it is debuggable; nothing needs to list it.

## Approach

### The rule

`DevelopmentServers` is an immutable value with one factory and one check:

```kotlin
internal class DevelopmentServers private constructor(private val development: Boolean, private val listed: List<ParsedHost>) {
    // Throws OctaveHttpException(HttpRefusal.DEVELOPMENT_BUILD) when this is a development build and the host does not qualify.
    fun check(address: ServerAddress)

    companion object {
        // allowlist: the text of BuildConfig.OCTAVE_DEV_SERVERS. Not read when debuggable is false.
        fun forBuild(debuggable: Boolean, allowlist: String): DevelopmentServers
    }
}
```

- `forBuild(false, anything)` holds no list and `check` returns for every address. This is the release rule, "signs in as before".
- `forBuild(true, text)` splits `text` on commas, trims each entry with `HostClassifier.jsTrim`, drops empty entries, and parses each entry as a host with the classifier's own parser (`HostClassifier.parseServerHost("http://" + entry + "/")`, kept only when the whole entry was read as the host). An entry that does not parse is dropped: it admits nothing.
- `check` reads the host from `address.host` with `HostClassifier.parseUrlHost`. This is the host OkHttp dials, which `ServerAddress.parse` step 4 has already tied to the host as written. An address whose host does not parse is refused.
- A host qualifies when one of these holds:
  1. `HostClassifier.classify(host) == HostClass.LOOPBACK` (`localhost`, `127.0.0.0/8`, `::1`, and their IPv4-mapped forms).
  2. It is the IPv4 address `10.0.2.2`, compared as four octets, or `::ffff:10.0.2.2` through `ParsedHost.Ipv6.mappedIpv4`.
  3. It equals a listed host: IPv4 by octets, IPv6 by its eight groups (an IPv4-mapped entry or host compares as its IPv4 address), a name by its lower-cased text exactly. No wildcard, no suffix match, no CIDR range, no port.
- The scheme and the port play no part: the item speaks of the host, and the rule holds for `http` and `https` alike.
- `toString()` is `"DevelopmentServers([redacted])"`. Nothing in the class logs, and the exception is the existing `OctaveHttpException`, whose message is the code and which has no cause.

### Where it is asked

`SessionTransport` becomes `SessionTransport(identity: ClientIdentity, servers: DevelopmentServers)`, with no default value, so a caller cannot forget the rule.

- `signIn`: `servers.check(address)` directly after `ServerAddress.parse(server)` and before `buildRequest` and `send`.
- `request`, tokenless branch: `servers.check(address)` directly after `ServerAddress.parse(...)`.
- `request` with a session, and `endSession`, are not checked: a session exists only because `signIn` passed the check in this process.

`ServerAddress.parse` stays first, so a public plain-HTTP address and a malformed one keep their own refusals. All of them cross as `refused`.

Decision, open to the Product Owner's veto: the tokenless calls are checked too, although the item and the owner's decision speak of signing in. Reasons: (a) the Quick Connect calls among them are steps of signing in, and the secret `POST /QuickConnect/Initiate` returns crosses to JavaScript, where the inspector of a debug build can read it and redeem it once the user approves the code; (b) "before any request" is then true of the whole sign-in flow; (c) the rule becomes one sentence, a development build sends nothing through the one client to a server that does not qualify, which also means a replaced bundle in a debug build cannot use the native client to reach a home-network address. Consequence for T4-02: in a development build the address probe of a server that does not qualify answers `refused`. The fixture servers are loopback and `10.0.2.2`, so the screens' development is unaffected (Product Owner log line 282). The narrower reading, sign-in only, is one line fewer in `request` and drops the tokenless cases from the tests.

`SessionRegistry.open` is left as it is: frozen tests and the device probes call it with public hosts, in the module's debug variant. Instead item 1's class holds a scan: in `src/main`, `SessionRegistry.open(` appears in `SessionTransport.kt` only. T4-05's restore will open sessions from stored records and must ask the rule; a backlog line says so.

### The module

`OctaveSessionModule` builds the rule beside the identity:

`transport()` returns the kept transport when there is one. Otherwise, with a React context, it reads `applicationInfo.flags` for `ApplicationInfo.FLAG_DEBUGGABLE` and the version name from that context, builds `SessionTransport(ClientIdentity.of(Build.MODEL, versionName), DevelopmentServers.forBuild(debuggable, BuildConfig.OCTAVE_DEV_SERVERS))` once under a lock, and keeps it. With no context it returns a transport built with `forBuild(true, …)` for that call only and keeps nothing. No method, argument, result field or event of the module changes, so decision 0005's surface is as it was.

### The allowlist

- **Mechanism: the environment variable `OCTAVE_DEV_SERVERS`**, set in the developer's own shell or in an ignored `mise.local.toml`, at the time the debug build is made. Its value is a comma-separated list of hosts: names or IP literals, an IPv6 literal in brackets, no scheme, no port, no path, no wildcard. Example value: `dev-jellyfin.invalid,media-test.invalid`.
- `modules/session/android/build.gradle`:
  - `android { buildFeatures { buildConfig true } }`.
  - `defaultConfig { buildConfigField "String", "OCTAVE_DEV_SERVERS", '""' }`, so the release variant's field is the constant empty string.
  - `buildTypes { debug { … } }` overrides the field with `providers.environmentVariable("OCTAVE_DEV_SERVERS").getOrElse("")`, written as a Java string literal. Gradle fails the build, naming the variable and never the value, when the value holds a character outside letters, digits and `. _ - : [ ] ,` and spaces, so a quote or a backslash can never reach the generated source.
- The variable is read nowhere else. The JVM tests never read `BuildConfig`; they hand `forBuild` a text.
- With the variable unset or empty the list is empty and only loopback and `10.0.2.2` qualify.
- **Never committed.** `findAllowlistAssignments(text)` in `scripts/dev-allowlist.mjs` finds every place a text gives the variable a value: the name, an optional closing quote, optional spaces, `=` or `:`, optional spaces, then the value, which is a quoted string up to its closing quote or else the run of characters up to the next space or line end. A place passes only when the value is empty or is a comma-separated list in which every entry is a name ending in `.invalid` (RFC 2606: it can never be a real server). Anything else fails, an identifier or an expression included. The test runs it over every file of `git ls-files -z` that is text. This spec, the documents and `scripts/tv-build.mjs` therefore write only `.invalid` values, and `tv-build.mjs` writes its canary as a literal on the assignment line. Because a quote, spaces and a colon after the name count as an assignment, every mention in prose, a comment or a backlog line is worded so the name is never directly followed by `=` or `:` (spec check issue 3); the rule is not narrowed for prose.
- **A release build holds none.** Three things, each tested:
  1. The field exists with a value only in the debug build type (above).
  2. `forBuild(false, text)` does not read `text`.
  3. `scripts/tv-build.mjs` sets `env.OCTAVE_DEV_SERVERS = "octave-allowlist-canary.invalid"` for every build it runs, replacing whatever the machine holds, the way it already controls `OCTAVE_E2E`. `scripts/tv-apk-allowlist.mjs` reads every entry of the APK with `scripts/tv-zip.mjs` and fails, naming the entry, when one holds the canary's bytes. It is a step of `pnpm tv:apk:check` for the release APK. `scripts/tv-e2e.mjs` runs the same judge on the e2e APK after `checkE2eApk` returns clean and before the first `adb` call, outside `E2E_APK_CHECKS`, so the frozen T3-31 tests that pin those three checks and their error lines are unchanged (spec check issue 1). The judge is only ever given the app APK, never the probe APK. A list that reached a release APK by any route would bring the canary with it.

All four tests and the planned check are about the release build or about which build gets installed. What they leave open is a debug or `debugOptimized` APK that a person installs on a TV by hand, in two parts:

1. **It could be signed in to the real server**, and then a debugger or a replaced bundle could read the header. Items 1 to 3 close this: such a build sends nothing through the one client to a host that is not loopback, `10.0.2.2` or listed. On a TV, loopback is the TV itself. `10.0.2.2` is the owner's rule and stays; on a real network it is an ordinary private address, so a home network numbered `10.0.2.0/24` with a server at that address would qualify (Risks).
2. **Its development-server host could be set to a LAN address**, by the developer menu's dialog, the preference `debug_http_host`, or the property `metro.host`. Whoever answers at that address then supplies the JavaScript. This is item 4, and it is not closed here.

The item asks for a test that a development-server host set to any other address is refused. There are two places such a refusal can stand, and neither yields a test this task may write.

1. **At the connection.** The complete fence is a check on every request React Native's own client makes. 2. **At the setting.** Octave could clean `debug_http_host` when the process starts and undo a bad write. That is not a refusal: the setter writes the preference first and fills the in-memory override afterwards (Facts), so a listener that undoes the write is itself overwritten, and the dialog reloads at once; `metro.host` cannot be changed by the app at all. And the code under test would be React Native's development support running in a debug app, which no JVM test reaches: the repository has no debug build in any command or CI job. A device test would need one, would be a CI change, and could show only the start-up half.

No build-time setting exists either (Facts). So the test the item describes cannot exist inside the rules this task may change. The options are in "Open questions".
