## Goal

From Home, one select on Resume runs a whole viewing through the core and leaves the server's play state right:

1. Home's play request becomes a viewing: one item read, Playback Negotiation through the core's `createPlaybackPlan`, a typed launch of the player module, and the player screen. No app code builds a media URL.
2. The coordinator reports the start after the first frame, progress every 10 s and on pause and seek, and the stop on Back, at the end and on an error (failed). A failed report is one plain notice and never stops playback. Back while loading sends nothing.
3. The progress positions are real: the engine reports its position every second, so a 10 s report never repeats the start position.
4. Back returns to Home, whose card shows the new position without a reload of the screen.
5. A wire test on the pinned Jellyscale shows the three reports with the header and the resume list at the reported position, and the app's type for the native module and the adapter's are one shape.

**The core**

- `PlaybackCoordinator` (`packages/core/src/player/coordinator.ts`) owns attempts, cancellation and teardown. It calls `reporter.start(...)` on the **`loaded`** event (`handleEvent`, `case "loaded"`, lines 378-379), not on `first-frame`; `case "first-frame"` only starts the play-method check for HLS. `stop()` cancels a pending attempt (negotiation or launch) and stops the engine; `finishSession` reports Stopped with `failed` true for `error`, `retry` and `renegotiate`.
- `PlaystateReporter` (`player/playstate-reporter.ts`): `start` reports once and runs `clock.every(10_000)` progress ticks that read the coordinator's **latest event snapshot** (`currentSnapshot()`); `progress` and `finish` send nothing before `start`; a failed progress or stopped report calls `onWarning("report-failed")`; the stopped report has its own 5 s deadline.

### D2. Ports and layers

### D3. `playbackGatewayOf`

`createPlaybackPlan(item, ticks, signal, selection)` calls `gateway.createPlaybackPlan(item, ticks, signal, selection?.mediaSourceId, selection === undefined ? {} : { audioStreamIndex, subtitleStreamIndex, keepDirectPlay })`, copying only the fields present; every other member forwards to the gateway, bound. `itemDetail` is forwarded too, so the result is a `ViewingSource`. ### D4. The engine reports its position every second

`EngineCore.tick()`: when a launch is current, `loaded` is true, and the launch has not ended or failed, emit `PlayerEvent.State(snapshot(current), "property")`; otherwise nothing. `Media3Engine` posts one `Runnable` on `main` after a launch that did not throw, every 1000 ms, and removes it in `release()` (so on stop, on destroy and before the next launch). The event kind and cause exist in the port and the seam (`PLAYER_EVENT_KINDS`, `"property"`), so the surface is unchanged and `ModuleSurfaceTest` and `scripts/tv-module-surfaces.test.ts` stay green; no log call is added. The snapshot carries no URL and no string from Media3. In JavaScript the coordinator already keeps the latest snapshot from any `state` event and reports nothing for `"property"`; the reducer stores it. One second is the finest the player screen's elapsed time (T8-04) needs, and makes a 10 s report at most 1 s stale.

No test reads `Media3Engine.kt` or `EngineCore.kt` as source (Product Owner ruling, 2026-11-25: the planned `scripts/tv-player-tick.test.ts` is dropped, since a test of source shape proves no behaviour). `EngineCoreTickTest` holds `tick()`'s behaviour. The `Media3Engine` half (the runnable posted every 1000 ms and removed in `release()`) has no host test; it is checked on the device run and by review: in the capture of `pnpm tv:wire --task T8-03`, the first viewing's first progress post is not paused and carries a position of 8 s or more, which a missing or dead runnable cannot give (the post would repeat the first frame's position). The reviewer reads that record in the pull request's capture, and reads `release()` for the removal.

Without this, items 2 and 4 hold only through the Stopped report: every progress report would repeat the position of the last event (Facts), and a lost Stopped report, or the app killed mid-film, would leave the server at the start position.

### D5. `Viewing`

```ts
export interface ViewingSource extends PlaybackGateway { itemDetail(id: string, signal?: AbortSignal): Promise<ItemDetail> }
export type ViewingState = {
  itemId?: string;
  phase: "idle" | "loading" | "playing" | "ended" | "failed";
  session: PlaybackSessionState;       // playbackSessionReducer's
};
export class Viewing {
  constructor(source: ViewingSource, engine: PlayerEngine, clock: Clock, log: FailureLog);
  play(request: PlayRequest): void;    // never throws; a failure is state
  stop(): Promise<void>;               // Back; resolves once the Stopped report settled or hit its deadline
  state(): ViewingState;
  subscribe(listener: () => void): () => void;            // for useSyncExternalStore
  afterViewing(listener: (itemId: string) => void): () => void;
}
```

- `play`: waits for any earlier viewing's `stop()` to settle; resets the state (`{ type: "reset" }`), sets `loading` and the item id; reads `itemDetail(itemId, signal)` with its own `AbortController`; `toLibraryItem(detail)` (`Episode` stays `Episode`; `Series`, `Season`, `BoxSet` and folders are refused as `request-failed`; any other type plays as `Movie`, as T5-03 D3 plays `Other`); then `coordinator.start(item, request.start)`. The start choice is the request's, not the detail's user data, so Resume starts where the card said. A `play` while a viewing is loading or playing is ignored.
- Callbacks: `onEvent` dispatches `{ type: "event" }` and moves `loading` to `playing` on `first-frame`; `onReportingError(message)` dispatches `reportingWarningAction(message, log)`; `onSessionEnded("eof")` sets `ended`; an `error` event or a rejected `start` (not `PlaybackCancelledError`) dispatches `failureAction(error, log)` and sets `failed`.
- After any ending (`stop()`, `eof`, `error`) and `coordinator.flush()`, every `afterViewing` listener gets the item id once. A viewing cancelled before its first frame also signals: Home's read is then a no-op patch.
- "Once" (item 5) is per viewing: the reducer keeps the first `report-failed`, and the screen shows it when it first appears.

- **Frozen judges reading event lists.** If a frozen T8-02 or T8-07 device judge counts `state` events exactly, `--task T8-02` or `--task T8-07` goes red; stop and return it to the Product Owner. (Read: `player-original-file.ts:23-66` and `player-samples.ts:45-48` match events by kind and cause, so they should not.)
- **A POST on a pooled connection the server closed** (backlog 188): a progress report after a long pause may fail once with `network` and show the notice. `tasks/product-owner-log.md:751` brings 188 back when this task's device run shows it; the wire run pauses 2 s only, so it will not.
- **Jellyscale's 30 s progress coalescing** means a lost Stopped report on Jellyscale can leave the resume point up to 40 s old, outside item 4's 10 s. Item 4 holds on Jellyscale through the Stopped report; the wire test proves that path.
- **Jellyscale ignores `Failed`** (D12; backlog 356).
- **A Series hero** is not patched after its episode plays (D8).
- **Stop failure on Back.** The screen is gone when `viewing.stop()` rejects with `PlayerStopError`; the owner's "Couldn't stop playback" state needs the screen to stay, which is T8-04's Back (item 5) with T8-17. Backlog line.
- **`RUN_MS`**: measured on the implementer's own emulator: the full wire run took about 56 s from launch to done, and `--task T8-03` alone about 29 s, both inside the existing 480,000 ms, so `RUN_MS` is unchanged.
- **A Retry before a renegotiated session's first frame** uses the old session's last played position (Product Owner log, "Not taken up"); callers pass the current position, so they agree. No line.
- Out of scope: D13; `App.tsx` and sign-in (D11); remote play (T12).
