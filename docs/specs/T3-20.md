## Goal

Decision 0001 admits plain HTTP by the literal host. A `.local` or `.home.arpa` name is admitted by its suffix, and `localhost` by its name. Nothing checks where such a name points when the client connects: `OctaveHttp` sets no `Dns`, and the origin pin compares host names (`RequestPolicy.kt`, check 4). So a router, an ISP that answers unknown names with its own server, or a spoofed DNS or mDNS reply can point a confirmed name at a public address, and the password (`AuthenticateByName`) and the `Authorization` header then leave the home network in plain HTTP (security review of 2026-11-21, backlog entry 170, medium).

After this task the one client, for a plain-HTTP call to a name, connects only to resolved addresses that the shared host-class rule calls loopback or private LAN, and refuses the call with a typed refusal when the answer holds none. The check runs on every new connection. It can only refuse: no host is ever accepted because of where it resolves, which is the alternative decision 0001 rejected. IP-literal hosts and HTTPS sessions behave as before.

No native method or event is added; the session surface stays `signIn`, `request`, `endSession` (`ModuleSurfaceTest`). No transport error code and no on-screen wording is added.

## Approach

### The rule

`ResolvedAddressRule` is an `internal object` that implements `okhttp3.Dns`, in its own file. `OctaveHttp` sets it with `.dns(ResolvedAddressRule)`; it is the client's only `Dns`. It does three things.

1. **Resolve.** `lookup(hostname)` asks its resolver, `Dns.SYSTEM` unless a test swapped it. An `UnknownHostException` or any other failure of the resolver passes through unchanged, so a name that does not resolve is still `network`, not a refusal.
2. **Decide whether to judge.** The answer is returned unjudged only when the current thread carries the HTTPS mark (below). In every other case it is judged, including when there is no mark at all. Judging is the default; the mark is the one way out of it.
3. **Judge.** Each `InetAddress` is turned into a `ParsedHost` from `address.address` alone: 4 bytes are a `ParsedHost.Ipv4`, 16 bytes a `ParsedHost.Ipv6` of eight groups; any other length is public. `HostClassifier.classify` gives the class. The rule never calls `getHostName`, `getCanonicalHostName` or `toString` on an address: the first two can start a reverse lookup, and all three produce text this module must not hold. An address passes when:
   - the name is `localhost` (its class as `HostClassifier.classify(parseUrlHost(hostname))` gives it is `LOOPBACK`) and the address is `LOOPBACK`; or
   - the name is any other name and the address is `LOOPBACK` or `PRIVATE_LAN`.
   
   The passing addresses are returned in the resolver's order, as the same objects, so an IPv6 scope id survives. When none passes, the rule throws `OctaveHttpException(HttpRefusal.RESOLVED_PUBLIC)`. An `Inet4Address` the JDK made from IPv4-mapped bytes (Facts) is judged as the 4 bytes it holds, which gives the same class.

`HttpRefusal` gains `RESOLVED_PUBLIC("resolved-public")`: a plain-HTTP name whose answer holds no loopback or private-LAN address. `TransportCodes` needs no change; the entry maps to `refused` like the others, and `TransportCodesTest` checks that.

**The refusal is not an `UnknownHostException`, and a comment on `lookup` says so.** `Dns.lookup` declares only `UnknownHostException` in Java; Kotlin can throw `OctaveHttpException` from it and it reaches `execute()` as the same object (Facts). The comment states that the refusal must stay an `OctaveHttpException`: turned into an `UnknownHostException` it would reach the core as `network`, a server that is off or mistyped, and `SessionTransport` would resend it once. `ResolvedAddressTest` pins the code and the class.

Do not override `newCall`. OkHttp then gets the default `LookupDnsCall` and calls `lookup` directly on the call's thread (Facts).

### How the scheme reaches the rule

`Dns` is given a host name, and through `newCall` a port; never the scheme (Facts). `https://nas.local` and `http://nas.local:8096` look the same to it, and item 3 says the first behaves as before. So the interceptor tells the rule.

- `SessionInterceptor` wraps `chain.proceed(authorised)` in `ResolvedAddressRule.proceeding(request.url) { ... }`. That function **always** sets a `ThreadLocal` mark to the call's own scheme (`url.isHttps`, so `false` for plain HTTP), runs the block, and restores the previous value in `finally`. A plain-HTTP call started on a thread that is already inside an HTTPS call's `proceed` (from a resolver or a request body) therefore overwrites the mark and is judged; it never inherits the outer call's.
- `lookup` reads the mark, each time it is called. OkHttp runs the lookup on the thread that runs the interceptor chain, for `execute` and for `enqueue` (Facts), so an HTTPS call's lookup sees its own mark. A lookup made through the rule from inside a resolver, on that thread, reads the same mark; the HTTPS twin uses this.
- **It fails closed.** If a later OkHttp moved the lookup to another thread, the mark would be absent and every lookup would be judged: plain HTTP stays safe, and HTTPS to a public name would be refused, which `ResolvedAddressScopeTest` turns red at the upgrade. The mark is per thread and every call sets its own, so a plain-HTTP call's lookup reads `false` or nothing. Item 3 pins both ways it could go wrong: two calls on two threads do not share it (the concurrency case), and a call nested on one thread does not inherit it (the nested case).
- The mark is the only state the function holds. It takes the URL, not a boolean, so no caller can pass `true` for a plain-HTTP call.

Alternatives weighed and rejected (decision log): resolving in the interceptor and dialling the IP literal with a `Host` header (one address only, so no fallback between addresses; drops IPv6 scope ids; one lookup per request, not per connection); a network interceptor that reads the connection's address (frozen `OneClientTest` forbids one, and it runs after the TCP connect); judging every private-suffix name whatever the scheme (changes HTTPS, which the Product Owner left out, `tasks/product-owner-log.md:87`); a second client or a derived client per scheme (hard rule: one client).

### What happens in order

For a plain-HTTP call to `http://nas.home.arpa:8096/...`:

1. `ServerAddress.parse` classified the address when the session opened or the tokenless call was built: literal host, decision 0001, unchanged.
2. `SessionInterceptor` runs `RequestPolicy` (origin pin, check 6 on the literal host, base path). Unchanged; a refusal here never reaches the resolver.
3. `chain.proceed`. If the pool holds a connection for this address, OkHttp reuses it: the same socket to an address that was judged when it was opened. No lookup.
4. Otherwise OkHttp asks the rule. The rule resolves, judges every address, and returns the passing ones or throws. OkHttp builds its routes from the returned list only, and may fall back between them.
5. A refusal reaches `execute()` as the `OctaveHttpException`; `SessionTransport.send` rethrows it without a resend, and the call resolves `{ error: "refused" }`.

For an IP-literal host step 4 does not exist. For an HTTPS call step 4 returns the answer unjudged.

### The resolver seam

The tests need to choose the answer. The seam replaces **where answers come from**, never the judge.

- `ResolvedAddressRule` holds `@Volatile private var resolver: Dns = Dns.SYSTEM` and one function, `internal fun <T> withResolver(resolver: Dns, block: () -> T): T`, which swaps it, runs the block and restores it in `finally`.
- Whatever resolver is in place, steps 2 and 3 of the rule run on its answer. So the seam cannot widen what plain HTTP dials. For HTTPS it could change the address dialled, where the certificate check still stands; the caller would have to be code in the app's own process.
- It is `internal`, is not reachable from the module definition (`ModuleSurfaceTest`), and nothing in main source calls it: `ResolvedAddressScopeTest` scans the module's main sources and fails when `withResolver` appears outside `ResolvedAddressRule.kt`.
- A fake resolver is an `okhttp3.Dns`, a type main has today.

**Frozen Kotlin files name no symbol main lacks.** `ResolverTestSupport.kt` therefore reaches the seam by reflection: it reads `OctaveHttp.client.dns` (present today, `Dns.SYSTEM`), finds the one method whose name starts with `withResolver` (Kotlin appends the module name to an internal function's JVM name), calls it, and unwraps `InvocationTargetException`. With no such method it fails with "the one client's Dns has no resolver seam", which is the red reason today. Refusals are compared by code string, `resolved-public`, through `OctaveHttpException.refusal.code`. The probe in `src/androidTest` is written by the implementer and calls `withResolver` directly.

`ResolverTestSupport` offers: `withAnswers(answers: (String) -> List<InetAddress>, block)`; a `RecordingResolver` that records the names it was asked, in order; `address(vararg bytes)` built with `InetAddress.getByAddress`, never `getByName`; `emptyPool()`, which calls `OctaveHttp.client.connectionPool.evictAll()`; and `reenter(name)`, which calls `OctaveHttp.client.dns.lookup(name)` from where it stands and returns either the list or the refusal's code. `withAnswers` swaps one field for the whole process, so a test that uses `enqueue` or a second thread waits, inside the block and with a timeout, until every call it started has finished.

### What the JVM tests dial

**No test lets the client dial anything but `127.0.0.1`.** A public answer (`203.0.113.7`, TEST-NET-3, RFC 5737), `0.0.0.0`, `::` and the other refused addresses are only ever given where the lookup must refuse or filter them before a socket exists, or to a lookup that no call is waiting on. Nothing is given to a call that may connect except `127.0.0.1` (Facts: the JDK turns `0.0.0.0` into the machine's own address). No test calls `InetAddress.getByName`, `getLocalHost` or the system resolver. Names are made up: `nas.home.arpa`, `nas.local`, `tls.home.arpa`, `plain.home.arpa`, `refused.home.arpa`, `outside.home.arpa`. In `ResolvedAddressScopeTest` each name has one answer throughout: `tls` and `plain` answer `[127.0.0.1]`, `refused` and `outside` answer `[203.0.113.7]`; `refused` is the name a plain-HTTP call is made to, and `outside` is only ever looked up.

**The pool rule.** The pool reuses a connection by name and port and never asks the resolver again (Facts). So every case that expects a lookup starts its own `TestServer` (a new port, so no pooled connection can match) or calls `emptyPool()` first, and **asserts that the recording resolver was asked for its name**, with the count it expects. A case that passes without that assertion proves nothing about the rule. The one exception is "one lookup per connection" below, which expects the second request not to ask. Every class empties the pool in `@AfterEach`.

`ResolvedAddressTest` (item 1), each through `OctaveHttp.callFactory(session)` or `SessionTransport`, with MockWebServer on `127.0.0.1`; every case has its own `TestServer` and asserts the resolver was asked:

- A `.home.arpa` session and a `.local` session whose answer is `127.0.0.1`: 200, and the server sees `Host: <name>:<port>` and the header.
- The same sessions with the answer `203.0.113.7`: `OctaveHttpException`, code `resolved-public`; the server accepted no connection (`TestServer.connections`).
- The error carries no address: it is an `OctaveHttpException` and not an `UnknownHostException`, its message equals the code, its cause is null, and neither its `toString`, its message, nor any suppressed exception's holds `203.0.113`, the host name or the port.
- `SessionTransport.signIn` (password) to a name with a public answer resolves `{ error: "refused" }` and the server saw nothing; so does a tokenless `GET /System/Info/Public`. The resolver was asked once for each: a refusal is not resent.
- `endSession` for a session whose name answered `127.0.0.1` (one 200), then `emptyPool()`, then the answer `203.0.113.7`: `{ error: "refused" }`, the resolver was asked a second time, the server saw no logout, and the session is gone.
- CGNAT `100.64.0.1`, `0.0.0.0`, `::`, NAT64 `64:ff9b::c0a8:101` and `2001:db8::1` as the only answer: each refused, the resolver asked once each, no connection accepted.

`ResolvedAddressAnswerTest` (item 2):

- Through `OctaveHttp.client.dns.lookup(name)` under `withAnswers`, outside any call (so judged, and no pool is involved): `[203.0.113.7, 10.0.0.5, 100.64.0.1, 192.168.1.20, fe80::1, 8.8.8.8, fd00::5, 127.0.0.1]` returns exactly `[10.0.0.5, 192.168.1.20, fe80::1, fd00::5, 127.0.0.1]`, the same objects in that order; an all-public answer throws; a resolver's `UnknownHostException` comes back as itself.

It builds each address with `InetAddress.getByAddress` from that parsed host alone: the four octets, or the eight groups as 16 bytes, high byte first. It never builds one with `InetAddress.getByName`, from the URL's text, or with a pattern of its own, so a vector that is public as written but private by its bytes, or a name that looks like an address, is never selected. Each address, as the single answer for `nas.home.arpa`, is returned when the vector's class is `loopback` or `private-lan` and refused `resolved-public` when it is `public`. The test asserts floors on what the rule selected, in `HostClassTest`'s style, so a selection that silently shrinks fails: at least 49 vectors, of which at least 8 `loopback`, 17 `private-lan` and 24 `public` (Facts; the Tests step confirms the numbers with the Kotlin before freezing). The returned address is compared with `equals` to the one given, not by byte length: the JDK hands back 4 bytes for IPv4-mapped input (Facts).

- Mixed through the client, own `TestServer`: `[203.0.113.7, 127.0.0.1]` answers 200, the resolver was asked once and the server accepted one connection.
- Rebinding through the client: answer `127.0.0.1`, 200; `emptyPool()`; answer `203.0.113.7`, refused; the resolver was asked twice and the server saw one request.
- One lookup per connection (the exception to the pool rule): two requests on one kept-alive connection ask the resolver once, and the server accepted one connection.

`ResolvedAddressScopeTest` (item 3):

### The HTTPS twin

The twin shows that an HTTPS call's answer is not judged, and that the same answer in a plain-HTTP call is. It never lets a call connect to a public address, or to `0.0.0.0` (Facts): the HTTPS call itself connects to `127.0.0.1`, and the public answer is one that no call is waiting on.

The fake resolver answers `tls.home.arpa` and `plain.home.arpa` with `[127.0.0.1]` and `outside.home.arpa` with `[203.0.113.7]`. When it is asked for either of the first two, it first calls `reenter("outside.home.arpa")` on the thread it is on, records what came back, and then returns `[127.0.0.1]`. `reenter` goes through `OctaveHttp.client.dns`, so through the rule and its mark; it catches the refusal, so the outer call's result does not depend on it.

- `https://tls.home.arpa:<port>` on its own `TestServer`: the call fails with an `IOException` that is not an `OctaveHttpException` (the server speaks no TLS; the spec check saw `javax.net.ssl.SSLException`, and the class is not pinned); the server's accepted connections rose by at least one (the check saw one; OkHttp's TLS retry behaviour is not pinned here); the resolver was asked for `tls.home.arpa`; and the re-entry returned exactly one address, the `203.0.113.7` object the fake gave (the address is pinned, not the list instance). No request the server recorded carries an `Authorization` header: the handshake fails before the header is written. What MockWebServer records for a TLS hello on a plain socket is unverified, so its request count is not pinned.
- The same on `enqueue`, where the lookup runs on OkHttp's dispatcher thread; the test waits for the callback before it leaves `withAnswers`.
- `http://plain.home.arpa:<port>` on its own `TestServer`: 200; the resolver was asked for `plain.home.arpa`; and the re-entry was refused `resolved-public`.
- `reenter("outside.home.arpa")` outside any call: refused `resolved-public` (no mark means judge).

**Unverified by run:** the re-entry itself. It needs the rule, and `AGENTS.md` forbids writing an implementation to prove a test before the implement step. It rests on two things this spec fixes: the rule reads the mark on every `lookup`, on the calling thread, and its resolver field is the fake for the whole `withAnswers` block. If the implementer finds the re-entry cannot work as written, that is a frozen-test ruling, not a change to the test.

No TLS test library is added.

### The emulator check

`pnpm tv:e2e` cannot control what a name resolves to on the emulator (Facts), so the device check uses the same seam, in the module's test APK, through the one client.

- `CleartextProbe.onCreate` reads `check`. Absent, it runs exactly what it runs today. `resolved-address` runs `ResolvedAddressCheck` and reports only that check's keys.
- **One name and one session per case.** The probe may not read `OctaveHttp.client` (`pnpm lint:network`, K4), so it cannot empty the pool, and three cases on one name and port would ride the first case's connection (Facts). Each case has its own name, so its own origin, session and pool entry. The fake resolver is one fixed table, set once for the whole check; any other name gets an `UnknownHostException`:

  | Name | Answer | Used by |
  |---|---|---|
  | `octave-probe-private.home.arpa` | `[10.0.2.2]` | `resolved-private` |
  | `octave-probe-mixed.home.arpa` | `[203.0.113.7, 10.0.2.2]` | `resolved-mixed` |
  | `octave-probe-public.home.arpa` | `[203.0.113.7]` | `resolved-public` |
  | `octave-probe-tls.home.arpa` | `[10.0.2.2]` | `https-call` |
  | `octave-probe-outside.home.arpa` | `[203.0.113.7]` | the re-entry lookups only; no session, no call |

- `ResolvedAddressCheck`, with the canary header of `CleartextProbe`, in this order:
  - `resolved-private`: a session on `http://octave-probe-private.home.arpa:<port>`; `GET /octave-probe/resolved-private`; reports the status.
  - `resolved-mixed`: a session on `http://octave-probe-mixed.home.arpa:<port>`; `GET /octave-probe/resolved-mixed`; reports the status.
  - `resolved-public`: a session on `http://octave-probe-public.home.arpa:<port>`; `GET /octave-probe/resolved-public`; reports `refused-<code>`, or the status if one came back.
  - `resolved-asked`: how many of those three names the fake resolver was asked for, `0` to `3`. Without it, a pooled connection would pass as a judged one.
  - `http-outside`: what the re-entry lookup gave inside the `resolved-private` call (below).
  - `https-call`: a session on `https://octave-probe-tls.home.arpa:<port>` and one GET; reports `refused-<code>` for an `OctaveHttpException`, `failed-<class simple name>` for anything else, or the status if one came back. The host's server speaks no TLS, so a `failed-` value is expected. The connection goes to `10.0.2.2`, the host's own server, like the plain cases; nothing in this check dials `0.0.0.0` or a public address.
  - `https-asked`: `yes` when the fake resolver was asked for `octave-probe-tls.home.arpa`, else `no`. Without it, a failure before the lookup would pass as "not refused".
  - `https-outside`: what the re-entry lookup gave inside the `https-call` lookup.
  - `done=yes`. It reports fixed words, statuses, counts and class names only, and logs nothing.
- **The re-entry on the device.** When the fake resolver is asked for `octave-probe-private.home.arpa` or `octave-probe-tls.home.arpa`, it first calls `ResolvedAddressRule.lookup("octave-probe-outside.home.arpa")` on the thread it is on, then returns its own answer. The value reported is `unjudged` when that lookup returned the one public address, `refused-<code>` for an `OctaveHttpException`, `filtered` for any other list, `failed-<class simple name>` for anything else, and `not-run` when the resolver was never asked for the outer name. This is the device's showing that an HTTPS call's public answer is not judged and a plain-HTTP call's is. The probe names the rule object, not the client.
- `scripts/tv-resolved-address.mjs` exports `RESOLVED_REPORT_KEYS`, `judgeResolvedAddress(report, served, expected)` and `runResolvedAddressProbe({ adbPath, serial, apk, evidenceDir })`. The run starts its own host server, installs the probe APK, runs `am instrument -w -e check resolved-address -e hostPort <port>`, reads the report with `parseInstrumentation`, uninstalls, writes `release-evidence/tv/e2e-resolved-address.txt`, and judges.
- `judgeResolvedAddress` returns `ERROR tv e2e: resolved-address ...` lines, empty only when:
  - every key of `RESOLVED_REPORT_KEYS` is present and `done` is `yes`;
  - `resolved-private` and `resolved-mixed` are `200`;
  - `resolved-public` is exactly `refused-resolved-public`;
  - `resolved-asked` is `3`;
  - `http-outside` is exactly `refused-resolved-public`;
  - `https-call` starts with `failed-`, `https-asked` is `yes`, and `https-outside` is `unjudged`;
  - the server saw exactly one request for `/octave-probe/resolved-private`, with the canary header and `Host` `octave-probe-private.home.arpa:<port>`, and exactly one for `/octave-probe/resolved-mixed`, with the canary header and `Host` `octave-probe-mixed.home.arpa:<port>`;
  - it saw none for `/octave-probe/resolved-public`, and no other request.
- The HTTPS call's TLS hello reaches the host's server as bytes that are not an HTTP request. Expected, unverified by run: Node's HTTP server raises `clientError` for them and calls no request handler, so nothing is recorded. The script's server records in its request handler only; milestone 3's run shows it.
- `scripts/tv-e2e.mjs` calls it after `runCleartextProbe`, exits 1 on any error, and prints `tv e2e: resolved-address private ok, mixed ok, public refused`.

The probe must pass `pnpm lint:network` as written: it does not read `OctaveHttp.client`.

- **"Treat every new native module method or event as an architecture change"** and **"Keep the native session surface to the methods decision 0005 lists"**: no method, event, property or constant is added. `withResolver` is Kotlin-internal and outside the module definition.
- **"Never add a generic player command, property, option, or header bridge"**: not touched.
- **Tests rules**: no frozen file changes; nothing is skipped and no case depends on the machine's host name or routing (the HTTPS twin dials `127.0.0.1`); no stub.
- **"Call out changes to invariants, `docs/security.md`, release signing, or CI in the PR"**: the pull request calls out the one client's new `Dns`, the new refusal, `docs/security.md` section 3 and the I5 row.
- **Parallel work**: native module work is serial; `pnpm tv:e2e` runs on the agent's own emulator under the device lock, never the Shield.
- **Owner's standing priority** (2026-11-21, `tasks/product-owner-log.md:108`): a self-hosted install must never become a way into someone's local network. This task closes the way **out** to a public address. It does not close a spoofed answer that points at another private host; see Risks.

## Risks and out of scope

- **A spoofed answer inside the private ranges is not refused.** A name pointed at `192.168.1.1` passes; that host receives the probe, and after confirmation the password. The rule cannot tell one private host from another; the confirmation (server `Id` and origin) and HTTPS are the protections, and the `Id` is public (decision 0001, accepted residual risk). `docs/security.md` says so. Not in this task; the implementer appends a backlog entry only if the review finds a concrete, testable narrowing.
- **HTTPS to a private-suffix name is not judged.** Left out by the Product Owner (`tasks/product-owner-log.md:87`). The certificate check stands in for it.
- **The mark depends on OkHttp running the lookup on the call's thread.** True in 5.5.1 for both exchange finders, by bytecode and by the spec check's run (Facts). It fails closed, and `ResolvedAddressScopeTest` goes red if it stops holding. An OkHttp upgrade must rerun the three classes; the phase's dependency re-check already reruns `pnpm tv:native:test`.
- **`Dns.newCall` is new API in OkHttp 5.** The rule relies on the default implementation calling `lookup`. If a later version resolved through another path, plain HTTP would be judged or fail; it would not pass unjudged, because the client has no other resolver.
- **The HTTPS twin shows "not judged" by a re-entered lookup, not by a connection to a public address.** No test can dial one. What stands between the rule's answer and the socket is OkHttp building its routes from the list `lookup` returned, which the mixed and rebinding cases show for plain HTTP. The re-entry is unverified by run until the rule exists (Approach, "The HTTPS twin").
- **The device's HTTPS case sends a TLS hello to the host's plain server.** Expected to be recorded as no request (Approach); if Node recorded one, the judge's "no other request" would fail the run loudly, and the fix is in the script's own server, not in the judge.
- **IPv6-only networks with DNS64.** A synthesised `64:ff9b::/96` address is public (decision 0001, edge case 3) and is filtered; the name works when the answer also holds a private address the device can reach. Unverified on a real network.
- **mDNS on Android.** Whether `InetAddress.getAllByName` resolves `.local` depends on the Android version. This task changes nothing there: the rule calls the same resolver as before.
- **The seam is a mutable field in the shipped module.** It can only replace the source of answers, and the judge runs on whatever it returns. Nothing in main calls it, and a scan keeps it so. A reviewer may still prefer no seam; the emulator check then has no way to exist (decision log).
- **Lookup time.** No added lookup: OkHttp resolved once per new connection before, and still does.
- **The viewer cannot tell this refusal from another.** The core gets `refused`. If T4's sign-in screens want their own words for "this name points outside your home network", that needs a transport code and the owner's wording. The implementer appends one backlog entry saying so; no wording is chosen here.
- Out of scope: any change to the classifier, the vectors, the confirmation, discovery (T4-01), the core, the TypeScript adapter, the network security configuration, a decision record, iOS and tvOS, the player's data source (T8; it will send through `OctaveHttp.callFactory` and so through the same interceptor and `Dns`).
