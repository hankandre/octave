## Goal

While a card's picture loads, the card shows a soft, blurred version of that same picture instead of a flat grey box. When the picture arrives, it fades in over the preview.

The hash comes from the server's `ImageBlurHashes[type][tag]` for the exact image the card draws. The core already carries it as `ImageRef.blurHash` (see "Where the hash comes from"). React passes that string, and nothing else, through a sixth prop, `blurHash`, on the existing `OctaveArtworkView`. Kotlin validates it against a fixed bound, decodes it off the main thread into a 32×32 bitmap with the module's own decoder (no dependency, no network), and caches the bitmap by hash so a recycled card draws it at once.

The slot draws two instances of the same native view, in this order:

- a **preview view**, beneath, that gets only `blurHash`;
- the **picture view**, as T3-11 has it, that gets the five T3-11 props.

React fades the picture view in on `loaded` over `durSlow` with `easeInOut`, or over `reducedMotion.durSlow` (120 ms) when reduced motion is on. So the motion uses the design tokens and `useReducedMotion`, and none of it lives in Kotlin. With no hash, nothing changes from T3-11: the plain surface shows, the picture appears without a fade, and a failure shows the title.

- **No Robolectric.** The artwork module's tests are JUnit 5 on the JVM (`modules/artwork/android/build.gradle`). Android view code cannot be unit-tested here, so the logic goes in plain Kotlin under `load/` and the view stays thin.
- **The BlurHash format** (reference decoder `woltapp/blurhash`, `TypeScript/src/decode.ts`, `base83.ts`, `utils.ts`, read 2026-11-23 at `master`, latest commit `712a47f946b98c30097eb1ada086ea00b18681ec`, 2024-05-21):
  - **Size.** The first character, base83, is the size flag: `numY = floor(flag/9)+1` and `numX = flag%9+1`, so each is 1 to 9. The length must be `4 + 2·numX·numY`, so the longest valid hash is 4 + 2·81 = **166** characters and the shortest is 6.
  - **Components.** The second character is the quantised maximum, `(q+1)/166`. Characters 3 to 6 are the DC value, 24-bit sRGB. Each later pair is an AC value: `quantR = v/361`, `quantG = (v/19)%19` and `quantB = v%19`, each mapped with `signPow((q-9)/9, 2)·max`.
  - **Pixels.** A pixel is `Σ cos(πxi/W)·cos(πyj/H)·c[i,j]` in linear light, then converted back to sRGB with the reference `linearTosRGB` (clamp, `trunc(... * 255 + 0.5)`).
  - **What the reference does not check.** It does not refuse a character outside its 83-character alphabet (`decode83` uses `indexOf`, so a stray character becomes −1). It does not refuse a DC value above `0xFFFFFF` or an AC value above `19³−1 = 6858`.
- **Hashes in the fixtures.** The recorded Jellyfin fixtures hold 76 non-null hashes of 44 to 54 characters (5×4 and 5×5 components). That is a count over `packages/core/tests/fixtures/**` with a one-off script in this session. One is `packages/core/tests/fixtures/jellyfin/12.4.0/home-latest.json`'s `"Primary": {"id-2": "diE|rGDNI9tmPpMca0tSO@xFs9R%xuofWARiNGkWWVso"}`. They come back with `fields=PrimaryImageAspectRatio` (`CARD_FIELDS`, `packages/core/src/jellyfin/gateway.ts:53`), so no extra field is needed.

## Where the hash comes from

The hash is the server's own hash for the image type and tag that the card draws. The core takes it as `item.ImageBlurHashes[type][tag]`, with the same `type` and `tag` as the `ImageRef`, in `imageRef(itemId, type, tag, blurHash)` (`packages/core/src/jellyfin/cards.ts:57-58`):

- the own Primary, `cards.ts:12`;
- the series Primary for an episode with no picture of its own, `:23`;
- the Backdrop, `:31`;
- the Logo and Thumb, own or the parent's, `:45-52`;
- the detail images, `item-detail.ts:168-171`.

A null or empty hash leaves `blurHash` off the ref. `packages/core/src/jellyfin/cards.test.ts:12-127` already holds this for each source.

**The core's card fields add nothing.** `ImageRef.blurHash?: string` (`packages/core/src/domain/catalog.ts:25`) already carries the hash to the slot, and the gateway already receives `ImageBlurHashes`. No core file changes. Where a card has no hash (Jellyscale today, an image the server has not hashed, a hash the native side refuses), the card shows the plain `surface2`. A failed image still shows the title (`MediaCard`, T3-08's frozen `media-card.test.tsx` item 6).

## Approach

### The native decoder (`load/BlurHash.kt`, plain Kotlin)

- **Interface.** `decode(hash: String): IntArray?` returns 32×32 ARGB pixels (alpha 255) or `null`. It never throws: a `Throwable` inside is `null`.
- **Validation, before any arithmetic:**
  1. length 6 to `MAX_LENGTH` (166);
  2. every character in the 83-character alphabet `0-9A-Za-z#$%*+,-.:;=?@[]^_{|}~` (a fixed table; anything else, non-ASCII included, refuses);
  3. length is `4 + 2·numX·numY`;
  4. DC ≤ `0xFFFFFF`;
  5. each AC ≤ 6858.
- **Decoding** follows the reference: `maximumValue = (q+1)/166`, punch 1. The cosine tables are computed once per decode (`cosX[x·numX+i]`, `cosY[y·numY+j]`, 32×9 each). The sRGB conversions are the reference `sRGBToLinear` and `linearTosRGB`.
- **Output size.** It is always `SIZE`×`SIZE` (32×32), whatever the component count. The view stretches it to the card (`FIT_XY`), which maps the hash's normalised coordinates onto the frame. With bitmap filtering on, the upscale reads as a blur (D3).

### The preview loader (`load/PreviewLoader.kt`, plain Kotlin)

```kotlin
class PreviewLoader(
    private val decode: (String) -> Decoded?,   // BlurHash.decode + BitmapPreviews in production
    budgetBytes: Long,                           // 1 MiB
    private val work: CoroutineDispatcher,       // Dispatchers.Default.limitedParallelism(2)
) {
    fun cached(hash: String): Decoded?           // synchronous; a map read under the LRU's lock
    suspend fun load(hash: String): Decoded?     // cached, or decoded on `work` and cached; null when refused
}
```

- It is keyed by the hash string alone. The hash describes the picture's colours and is not a credential (D5), so no session is in the key.
- A refused hash is not cached and is refused again on the next mount. Validation is a length check and a table lookup, so that costs little.
- No bitmap is recycled on eviction (the T3-11 rule, held by the frozen `ArtworkModuleSourceTest`).

### The native view

- `var blurHash: String?` is set by the prop.
- In `propsUpdated()`, the preview is handled first. When the hash changed, the view cancels the preview job and clears the preview layer. A non-null hash draws `previews.cached(hash)` at once if there is one. Otherwise it launches `previews.load(hash)` on `ArtworkRuntime.scope` and draws the result on the main thread if the hash is still current. A `null` result leaves the layer empty, so the plain surface shows.
- **The picture.** When none of `session`, `itemId`, `imageType`, `tag` and `width` is set, the view loads no picture and emits no event. That is the preview view. Otherwise the picture path is T3-11's, unchanged: any missing or bad prop is `failed`.
- **Layers.** The preview `ImageView` uses `FIT_XY` and is added before the picture `ImageView`, so it draws beneath it. `onLayout` lays out both. `destroy()` cancels both jobs and clears both layers. The cache keeps them.
- The view emits nothing about the preview: `onArtworkState` keeps its two words. The view logs nothing (the frozen `ArtworkNoLogTest`).

### The JavaScript side

`createNativeArtwork` keeps its options and its T3-11 behaviour, with these additions:

- `const hash = typeof image.blurHash === "string" && image.blurHash.length > 0 ? image.blurHash : undefined`. The bound is enforced natively, as the one place it is checked (item 4).
- With a session and a hash, inside the `surface2` wrapper it draws `<NativeView key={"preview/" + hash} blurHash={hash} style={absoluteFill} />` first, then the picture.
- The picture is a child component keyed by the T3-11 key. It holds an `Animated.Value`, which starts at 0 when a hash is drawn and at 1 otherwise. It wraps the native view in `<Animated.View style={[absoluteFill, { opacity }]}>`. On `loaded`, when the value is not already 1, it starts `Animated.timing(value, { toValue: 1, duration: reduced ? reducedMotion.durSlow : motion.durSlow, easing: Easing.bezier(...motion.easeInOut), useNativeDriver: true })`. The existing `failed` handling is unchanged.
- With no session it draws neither view and calls `onFailed` once, as in T3-11.
- No new prop reaches the picture view. The preview view gets `blurHash` and `style` only: no `testID`, session, URL, header or token.

### Decode cost and recycled cards (item 7)

- **Per card**, at most one decode per distinct hash:
  - 1 024 pixels × up to 81 components × 3 channels ≈ 249 000 multiply-adds;
  - 2 × 288 cosines;
  - 3 072 `pow` calls.
  This runs on `Dispatchers.Default` with at most two decodes at once, never on the main thread. My estimate is well under 2 ms each on a Shield-class core **[judgment, unverified]**. The implementer records a measured figure: the median of 1 000 decodes of a 9×9 hash on the JVM, from an unfrozen test that asserts nothing about time. Memory is 32×32×4 = 4 096 bytes per preview.
- **Recycled cards.** A card that scrolls back, or a row that remounts, gets the same hash. `previews.cached(hash)` draws it on the main thread in `propsUpdated()` with no decode and no coroutine. The budget is 1 MiB, which is 256 previews, more than every card of a Home of 16-item rows that is visible or one screen away. Evicted bitmaps are dropped, not recycled.
- **The fade.** There is one native-driver opacity animation per newly loaded card that has a hash, on Android's render thread. Decision 0004 found that an animated *lift* cost frames on the Shield. Opacity is a cheaper property than scale and shadow, but whether that holds on the Shield is **unverified**. Item 7's measurement shows it on the emulator, and T3-12 and T3-14 measure it on the Shield.

### Decision log

- **D1. Two instances of one view, not one view with both layers.** One instance with six props would need the crossfade in Kotlin. Kotlin would then hard-code a duration (`AGENTS.md`: "never hard-code ... durations"), and it would read reduced motion from a different source than `useReducedMotion()`. With two instances, the motion is React's, with the tokens, and Jest can test it. That is the crossfade T3-11 D4 planned for. The cost is one more native view per card with a hash. Item 7 measures it.
- **D2. The bound is 166 characters**, the longest valid BlurHash (9×9 components). Every valid hash fits, and anything longer is malformed by definition. Native code is the one validator, so React passes the hash as it came.
- **D3. Decode at a fixed 32×32 and stretch it.** The cost is fixed and small whatever the card size, and the bitmap is the same for a poster and a thumb, so one cache entry serves both. A 9-component hash has at most 8 half-cycles across, which 32 samples carry. Where the picture's aspect differs from the frame's, the stretched preview shows the whole picture, while the picture is centre-cropped. Under blur, the difference is small (Risks).
- **D4. The crossfade reuses `DESIGN.md` §7.2's approved behaviour:** the BlurHash shows first, then the picture crossfades over `durSlow` with `easeInOut`, and over 120 ms on opacity only under reduced motion (§5). Per the Product Owner's rule of 2026-11-23, this is taken and listed for the owner's veto, not parked.
- **D5. No fade without a preview.** A card with no hash behaves exactly as T3-11 shipped it, so this task changes no look the owner has not chosen.
- **D6. The preview cache is keyed by hash alone.** A hash is a few colours, it already sits in the core's catalog data in JavaScript, and it carries no credential. Sharing a blur across sessions reveals nothing that JavaScript does not already hold.
- **D7. The decoder is our own code**, not a dependency. It is about 100 lines with a shared vector file, which Swift can mirror. The acceptance allows it, and it avoids a maintenance check and a new artifact in the dex.
- **D9. The decode runs as a plain task on `work`, not as a coroutine there** (implement step). `PreviewLoader.load` suspends with `suspendCancellableCoroutine` and runs `decode` through `work.asExecutor()`. Under `withContext(work)`, kotlinx.coroutines' debug mode (on whenever JVM assertions are, as in the unit tests) renames the worker thread `<name> @coroutine#n`, which the frozen `PreviewLoaderTest` thread check does not expect. The decode cannot be interrupted part-way in either form, and a load cancelled meanwhile still resumes with the cancellation and caches nothing.
- **D8. The baseline for item 7 is measured now.** T3-11 recorded wire counts but no frame figures (`docs/specs/T3-11.md`, "Implementation record"). So "what T3-11 measured" is read as T3-11's build (origin/main `3e692771`) under the same procedure as the task head, on the same emulator.

### Item 7: frames under a held key (both builds, per run)

Procedure as in "Device measurement (item 7)", with two departures, the same for both builds:

- **The harness.** `artwork-canary` redraws the Home every 1.5 s, so the run uses a measurement-only wire test, `artwork-frames` (task `T3-39-frames`, mock only, appended to `wire-tests.json`), that signs in and holds the same fixture Home for 30 s. A host driver waits for the app's `artwork-canary` line, waits 8 s, runs `dumpsys gfxinfo dev.octave.tv reset`, sends the key script, waits 2 s and reads `dumpsys gfxinfo`. The harness was applied identically to both builds and is not committed.
- **The keys.** Emulator console key events do not reach this headless image, so the script runs on the device as `input keyevent <code>; sleep 0.042` per press: 8 Down, 12 Right, 8 Up, 28 presses in 1.7 to 2.0 s (about 15 a second, not 20).

Baseline: origin/main `3e692771` in a throwaway worktree with milestone 4's `artwork-fixture-ids.ts` and `artwork-fixture-home.tsx` (same eight rows of twelve, same refs and hashes; `3e692771` ignores `blurHash`). Head: the task branch at milestone 5. Each run is a cold start (the runner force-stops and relaunches the app), image hold off, builds alternated.
