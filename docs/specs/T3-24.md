## Goal

T3-16 refuses a request path with a `.` or `..` segment, as written or percent-encoded up to four rounds. Its two reviews found forms that still pass both sides of the rule and C2, while `docs/security.md` says a session's call cannot leave its base path. After this task both sides refuse, before anything is sent:

1. a path that holds a `;`, as written or after any decoding round (`/Items/..;/x`);
2. a path that holds a control character after any decoding round (`/Items/..%00/x`);
3. a segment made only of dots and characters a server or proxy may fold to a dot (`/Items/%ef%bc%8e%ef%bc%8e/x`);
4. an escape that is not UTF-8 in any round (`/Items/%25c0%25ae%25c0%25ae/x`);
5. a path that still holds a percent-escape after the fourth round (`%252525252e`).

The one client applies the same rule to the encoded path of every session and closing call. No native method, event, refusal code or dependency is added.

## Approach

### The rule as built

A path is refused unless all hold. "Round 0" is the path as written; rounds 1 to 4 are that text percent-decoded once more each time (`DECODING_ROUNDS` stays 4).

- P1. It starts with `/` and not with `//`, and holds no `?` or `#`. Unchanged; round 0 only.
- P2. It holds no backslash. Unchanged; round 0 only. A decoded backslash still separates segments in P4.
- P3. **Changed.** No round holds a control character: U+0000 to U+001F or U+007F to U+009F. Today it is U+0000 to U+001F and U+007F, round 0 only.
- P4. **Changed.** In no round, split on `/` and `\`, is a segment `.` or `..`, or made only of `.` and dot-like characters with at least one dot-like character ("The dot-like characters"). A segment of ASCII dots alone is refused only as `.` or `..`, so `/Items/...` stays accepted.
- P5. **Changed.** In round 0 every `%` begins two ASCII hex digits. In every round, each maximal run of escapes (`(?:%[0-9A-Fa-f]{2})+`) decodes as UTF-8: no overlong form, no encoded surrogate, nothing above U+10FFFF, no lone continuation byte. In rounds 1 to 4 a `%` that begins no escape is a literal, so `/Items/100%25` stays accepted.
- P6. **New.** No round holds a `;`.
- P7. **New.** Round 4 holds no escape (`%` and two hex digits). A path encoded deeper than the rule can read is refused.

Order: P1 and P2 on round 0; then for each round P3, P6, P5 and P4 on that round's text; stop when the text holds no `%`; after round 4, P7. The order does not change a result, since every failure refuses.

After P5 has passed a round, decoding it is unambiguous: every escape run is UTF-8, so no U+FFFD is ever produced and the two sides cannot decode a passing text differently. That removes the caveat in `request-path.ts:13-15`.

Decoding stops early only when a text holds no `%`. A text with a literal `%` and no escape (`100%`) is decoded again to itself; that costs four passes over a short string and needs no special case.

Kotlin: `RequestPath` gains one internal function that holds P2 to P7 (suggested name `holdsRefusedForm(path: String): Boolean`); `isSafe` is P1 and not that function. `holdsDotSegment` and `escapesAreUtf8` have no other caller and may become private or fold into it. The strict per-round check lives in `RequestPath`; `PercentDecoding.decode` is not changed, because the token search and `CredentialQuery` share it. The dot-like characters and the control ranges are constants in `RequestPath.kt`, written as `\uXXXX` escapes.

TypeScript: `isSafeRequestPath` follows the same steps. The UTF-8 check is `decodeURIComponent` on each escape run inside `try`; `decodeLeniently`'s fallback branch becomes unreachable and goes. The dot-like characters are one constant, written as `\uXXXX` escapes. No `String.prototype.normalize` and no `java.text.Normalizer`: Hermes, Node and Android may ship different Unicode versions, and a hard-coded list gives both sides the same answer.

### The dot-like characters

Nine code points, the same list on both sides, each a single UTF-16 unit:

| Code point | Name | Why it is listed |
|---|---|---|
| U+2024 | ONE DOT LEADER | NFKC gives `.` |
| U+2025 | TWO DOT LEADER | NFKC gives `..` |
| U+2026 | HORIZONTAL ELLIPSIS | NFKC gives `...` |
| U+3002 | IDEOGRAPHIC FULL STOP | UTS #46 maps it to `.` in a host name |
| U+FE19 | PRESENTATION FORM FOR VERTICAL HORIZONTAL ELLIPSIS | NFKC gives `...` |
| U+FE30 | PRESENTATION FORM FOR VERTICAL TWO DOT LEADER | NFKC gives `..` |
| U+FE52 | SMALL FULL STOP | NFKC gives `.` |
| U+FF0E | FULLWIDTH FULL STOP | NFKC gives `.`; UTS #46 maps it to `.` |
| U+FF61 | HALFWIDTH IDEOGRAPHIC FULL STOP | UTS #46 maps it to `.` |

The first seven are every code point Unicode 17.0 normalises to full stops alone (Facts). U+3002 and U+FF61 fold only in host names; they are listed because refusing a segment made only of them costs nothing.

The rule is "only dots and dot-like characters, at least one dot-like", not "folds to `.` or `..`". So a segment of three fullwidth full stops, or one U+2026, is refused although `...` is accepted. That is stricter than a fold-and-compare rule and needs no arithmetic on what each character expands to. A dot-like character beside any other character is accepted: `/Items/%EF%BC%8Ea`.

## Risks and out of scope

Risks:

- **A legitimate path refused.** An id that holds `;`, a control character, only dot-like characters, or text still encoded after four decodings is refused as `refused`. So is an id that holds a literal `%` and two hex digits that are not UTF-8 (`50%ff`, sent as `/Items/50%25ff`): P5 refuses it in round 1 (spec-check note 5). None is recorded (Facts). It fails closed and the app shows its plain error copy.
- **A base path that holds a form.** C2 judges the whole encoded path. A server address such as `https://host/jf;x` signs in (the tokenless calls run no path rule), and then every session call and the logout are refused, so the token stays valid on the server. The same already holds on main for a base path with a twice-encoded dot. It does not open a path out of the base path. Logged to the backlog (below).
- **The dot-like list is a list.** A proxy that folds a character outside it is not covered; the document says so. Characters that fold to a separator or a `;` (U+FF0F and U+FF3C to `/` and `\`, U+FF1B, U+FE54 and U+037E to `;`) are not refused: `/Items/..%ef%bc%8fx` passes P1 to P7 (spec-check note 1). The document and both comments state it as a limit, and a backlog line leaves extending the rule to the Product Owner.
- **Later callers of the call factory** (the player, the image loader) send `/Videos/…`, `/Items/…/Images/…` and playlist and segment paths. None in the Jellyfin routes Octave uses holds a `;` (unverified for every route a later task adds); a refused one fails closed with `outside-base-path`.
- **The two sides drift.** Held by the shared vectors and by the same case lists in the Kotlin classes and `request-path-forms.test.ts`.
- **T3-25 changes the same package next** (`SessionTransport.kt`, the parser) and `docs/security.md`; it depends on this task and rebases.

Out of scope, each appended to `tasks/backlog.jsonl` by the implementer in the same PR:

- Refuse a server address whose base path fails the path rule, in `ServerAddress.parse` and the core's address handling, so no session opens on it. Size S.
- The query string is not judged by the path rule (only credential names and the token are); whether a `;` or a control character in a query needs a rule. Size S.
- Characters that fold to a separator or a `;` (spec-check note 1): whether the rule should refuse them. Size S.

Out of scope, already on the backlog and left there:

- Entry 189, a path-prefix allowlist for the native request. Not adopted, for T3-16's reason: it would put the gateway's route list in Kotlin.
- Entry 191, a token echoed after two or more rounds of encoding. It is `TokenStrip`'s rule for response bodies, not the path rule; its rounds are not changed here.
- Entry 192, the `AGENTS.md` wording for C2.

Also out of scope: the answer parser's depth bound and the response-cap tests (T3-25); the wire evidence (T3-26); a Swift implementation; any change to `PercentDecoding`, `TokenStrip` or `HostClassifier`.
