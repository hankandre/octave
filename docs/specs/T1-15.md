## Goal

The task workflow (`.claude/workflows/task.js`) gets three fixes:

1. **Resume at Ship.** A task that is already implemented, reviewed and green can be resumed at Ship with `from: "ship"`. Before Ship, the run checks the frozen tests and the green gate again, and it ships only when both pass.
2. **The green gate trusts the JSON.** The green gate (`check-red.mjs --expect green`) decides from the JSON result that check-red prints, not from the exit code the gate agent relays. On 2026-11-22 a relayed exit code of `-1` with nothing red ended T3-23 as "blocked: acceptance items ? still fail" (backlog entry 226).
3. **Three gate defects from the #208 review.** Backlog entries 83 to 85 cover these:
   - after an escalation, the implement gate passes a result that still lists failures;
   - a follow-up result that blocks can carry an empty reason;
   - ciOnly items from an attempt that was not green can reach Ship.

## Facts this spec rests on

- **`from` today.** `runTask` turns `opts.from` into four skip flags (`task.js:317-321`). It knows `check`, `tests`, `implement` and `review`. Any other value, `"ship"` included, skips nothing, so the run starts again at Spec. The Review block (`task.js:531-580`) always runs.
- **The batch loop passes `from` only to a single task.** `items.length === 1 ? input : { risk, native, root }` (`task.js:621`). `{tasks: [one]}` therefore counts as a single task, as it does today.
- **The branch sync is not a phase.** It runs on every run, after the Spec block and before `// 2. Check` (`task.js:451-456`). A frozen T1-14 test pins it there: the first `branch-sync.mjs` in the source must lie between `// 1. Spec` and `// 2. Check` (`task.test.mjs:783-795`).
- **`decideGreen` reads the exit code** (`task.js:187-194`). `if ((json.red || []).length || gate.exitCode !== 0) return { action: 'blocked', detail: \`acceptance items ${(json.red || []).join(', ') || '?'} still fail\` }`. A relayed `-1` with `red: []` therefore blocks with "?". `decideGreen` takes no `final` argument. On the second unreadable output, `runGate` (`task.js:386-397`) returns `{action: 'retry', unreadable: true}`, and `runTask` turns that into `blocked`, with no word saying it was the second try.
- **check-red's exit code follows from its JSON.** `scripts/check-red.mjs:125` returns `status: unexpected.length > 0 ? 1 : result.problems.length > 0 ? 2 : 0`. With `--expect green`, `unexpected` is `red`. It prints the result on one line (`:137`) before `process.exit(status)` (`:139`). So `red: []` and `problems: []` mean exit 0, and dropping the relayed exit code loses no information. A crash before the print leaves no result object, and the scanner then reports the output as unreadable.
- **The implement gate** (`task.js:526`) is `if (!impl.done || !impl.checksPassed) return result('blocked', …)`. `work()` (`task.js:369-376`) escalates once the retry fails and returns the escalated result whatever it says. A result with `done: true, checksPassed: true, failures: ['…']` therefore passes the implement gate (backlog entry 83).
- **The follow-up gate** (`task.js:571`) blocks with `(followUp.blockers || []).concat(followUp.failures || [])`. When the result holds only `ciOnly` items, with `checksPassed: false` or `done: false` and nothing pending, that detail is `[]` (backlog entry 84).
- **The ciOnly carry.** In `work()`, `attempt()` (`task.js:361-368`) merges every attempt's `ciOnly` into `carried` and writes it back onto each result. An item from a red first attempt therefore rides on a later green result into `ciSteps` (`task.js:528`, `:574`) and so into the Ship prompt (backlog entry 85). `decideStep` itself already returns `ciOnly: []` for a result that is not green (`task.js:227-235`).
- **Frozen files.** `.claude/workflows/task.test.mjs` is listed by `docs/specs/T1-14.tests.json` and `docs/specs/T2-02.tests.json`. The acceptance item forbids changing it. Its assertions that this design must keep are listed under Test plan.
- **`pnpm test:workflow`** is `node --test .claude/workflows/*.test.mjs` (`package.json:12`). It is part of `pnpm check` (`package.json:35`), and CI runs it (`.github/workflows/ci.yml:54`). A new `*.test.mjs` file in that folder is picked up with no config change.
- **The whole workflow can be run in a test.** I loaded `task.js` with `src.replace('export const meta', 'const meta')` into `new AsyncFunction('args', 'agent', 'log', src)` and passed a fake `agent` that answers by label. `{task: 'T9-01', from: 'review', root: '/nonexistent'}` called the agent in the order `sync T9-01`, `review T9-01`, `fixtures down T9-01` and returned `needsAttention` with outcome `failed` ("The reviewer returned nothing."). No command or network call ran: every command is only a string in a prompt. The tests below use this harness.

**Hard rules and invariants this task touches** (all are process rules; no playback, token or network rule applies):

- **Never change or delete a frozen test.** `task.test.mjs` is frozen by T1-14 and T2-02, and item 4 repeats the rule. Every new test goes in `task-resume.test.mjs`.
- **One review round; never review your own change** (AGENTS.md, Models and Working). `from: "ship"` skips the Review phase. It exists only for a task whose review round already ran in an earlier run. WORKFLOW.md says so. The frozen-test check and the green gate still run again before Ship.

- **When a command is denied, stop and report it.** A denied frozen check or green gate under `from: "ship"` gives outcome `denied`, which stops the batch.
- **`STOP_OUTCOMES` stays `['denied', 'tests-green', 'frozen-tests']`.** A green gate that is unreadable twice is `blocked`.
- **Merge only with green CI.** Ship is unchanged.

## Risks and out of scope

- **Skipping review.** `from: "ship"` trusts that an earlier run reviewed the branch. Someone could resume at Ship a branch that was never reviewed. The re-run frozen-test check and green gate catch broken or changed tests, but not unreviewed code. WORKFLOW.md limits the option to reviewed tasks. Enforcing that, for example by reading a review marker, is out of scope.
- **A wrong `from` value** still restarts the run at Spec, as today. Rejecting an unknown `from` is outside the acceptance. The implementer may append a backlog line for it (`WORKFLOW.md` §2a).
- **`decideRed`, `decideFrozen` and `decideSync` still read the exit code.** A frozen test pins `decideRed`'s retry on exit 1. The others were not part of the T3-23 failure. Out of scope.
- **The follow-up gate still passes `done && checksPassed` with failures listed.** The acceptance limits the "no failures" rule to the implement gate after escalation. The green gate that follows still reruns every frozen test. This change is left out, so the follow-up's hand-over to Ship keeps working.
