## Goal

The files `pnpm tv:wire` writes to `release-evidence/wire` are uploaded by the CI `wire` job with `if: always()`, and security claims quote them. After this task:

1. no evidence file can hold a known secret, even when the app under test leaks one into a URL;
2. a run that fails or is stopped leaves no result from an earlier run behind;
3. the logcat judge reads the whole log of the run, and the run fails when it cannot show that;
4. a run stopped by a signal leaves the emulator as it found it;
5. the `lint:logs` command cannot pass by never running.

## Approach

### The evidence (item 1)

"Known secrets" are what the runner already collects in `secrets`: the canary, the placeholder password, each fixture password and each token a recorder saw issued. "Holds" means `holdsSecret`: the text, as written or percent-decoded up to four rounds, contains any form `findSecret` knows (raw, percent-encoded one to four rounds, base64, base64url).

`scripts/tv-wire-judge.mjs` exports its existing `holdsSecret(text, secrets)`. `scripts/tv-wire-evidence.mjs` exports:

- `STAND_IN`: the fixed text `[holds a secret]`.
- `safeUrlParts(rawUrl, secrets)` returns `{ path, queryNames, secretInUrl }`. `secretInUrl` is true when the whole raw URL holds a secret. The path is `STAND_IN` when the path holds one; each query name that holds one is `STAND_IN`. When the whole URL holds a secret but neither the path, nor any single query name, nor any single query value does (a secret that spans the `?` or an `&`), the path and every query name are `STAND_IN`. A URL whose only secret is in a query value keeps its path and names; values are never stored. The query is split on `&`, each part on its first `=` into a name and a value, and every part (path, name, value, and the whole raw URL) is checked both as the raw text and as parsed (decoded once, `+` a space), because a secret holding `+` or `=` (the canary holds both) is found only in the raw text; `holdsSecret` decodes further rounds itself. A secret that is in the URL and in none of those parts (it spans `?`, `&` or `=`) replaces the path and every name.
- `safeRecord(record, secrets)` returns a copy in which every string field (`method`, `path`, `host`, `scheme`, `retryAfter`) and every query name that holds a secret is `STAND_IN`. `secretInUrl` is true when it was true or when the path or a query name was replaced. It never turns `secretInUrl` false.
- `safeLines(lines, secrets)` returns the lines with each line that holds a secret replaced by `STAND_IN`.
- `writeEvidence(dir, { captures, appLines, deviceLines, proxyLines, secrets })` writes `<name>.jsonl` for each `{ name, records }` through `safeRecord`, and `app-lines.txt`, `device.txt` and `global-proxy.txt` through `safeLines`. It then reads every file in `dir` back, as text and, for `.jsonl`, as parsed values. A file that still holds a secret is overwritten with one `STAND_IN` line. It returns `ERROR tv wire: ...` lines, one per replaced line group or overwritten file, naming the file and never the value; empty when nothing was replaced.
- `writeSummary(dir, lines, secrets)` writes `summary.txt` through `safeLines`, so it is scanned too (spec check issue 6); it holds only test, target and task names.
- `evidenceDir(env)` and `clearEvidence(dir)` (next section).

The recorder builds its record from `safeUrlParts(incoming.url, [...secrets])` and passes the finished record through `safeRecord`, so `records` in memory never hold a known secret in a path, a name, the `Host` or the scheme. The upstream request still uses the real `incoming.url`. The frozen item 1 tests assert this on the recorder's in-memory `records` (spec check issue 2).

The runner judges first and writes second. `judgeCapture` and `judgeRecords` read the recorder's records with the final secrets set, as today. A record with a stand-in fails: `secretInUrl` is true (judge line 64), a replaced `host` is not the recorder's, and a replaced `scheme` is not `MediaBrowser`. Then `writeEvidence` runs, and its errors join `runErrors`, so any stand-in written at this stage (a token learned after the request, an app line, a proxied `Host`) fails every pair of the run. The run-level judging is the pure exported function `judgeRun(input, { write })` of `scripts/tv-wire.mjs` (spec check issue 3): it returns the summary lines, the errors to print and whether a pair failed, and calls `write` (the evidence writer) once. The deviceLines it hands over end with the kept-log line (issue 12). `scripts/tv-wire.mjs` writes only through `writeEvidence` and `writeSummary` and holds no `writeFileSync`. `summary.txt` is written last.

The kept logcat is never written under the evidence directory. Only how it was kept is.

### Removing old evidence (item 2)

- `evidenceDir(env = process.env)` returns `<repo>/release-evidence/wire`, or `env.OCTAVE_WIRE_EVIDENCE` when it is set. The override must be an absolute path that ends in `release-evidence/wire`; any other value throws, because the directory is removed recursively. The override exists so a test can run the real CLI without touching the checkout's evidence.
- The first statement of `main` calls `clearEvidence(evidenceDir())`, before the arguments are parsed. When `evidenceDir` throws, `main` removes the default directory and then fails.
- The entry guard becomes `if (process.argv[1] && fileURLToPath(import.meta.url) === realpathSync(process.argv[1])) await main(process.argv.slice(2));`, so an invocation through a symlinked path runs `main` (Facts). With both changes no exit that `main` reaches comes before the removal. Not literally every exit: static imports are evaluated before `main`, so a module that fails to load exits with the old `summary.txt` in place (spec check issue 5; `docs/commands.md` says so). Importing the module still runs nothing.
- `--list` removes the directory too. It is an exit of `pnpm tv:wire` like any other, the item says "before its first possible exit", and one rule with no exception is the one that can be tested and trusted: after any invocation, a `summary.txt` in the directory is from that invocation.
- The later `rmSync` at line 321 goes; `writeEvidence` makes the directory.
- A run stopped by a signal writes no `summary.txt`. A signal landing during `writeEvidence` can leave evidence files without one, so a directory without `summary.txt` is not a result (spec check issue 7).

### The kept log (item 3)

**Choice: streaming.** Reasons:

- A larger buffer still rotates when a run logs more than it holds, so the run would need a per-buffer rotation check anyway. `logcat -G` changes a device setting, and a device may clamp or refuse it (unverified for the CI image).
- A stream attached before the app starts moves each line to the host as logd emits it. The device's buffer size stops mattering, and the size on the CI image does not need to be known.
- It replaces the once-a-second `logcat -d` poll for the done line with a read of memory.

`scripts/tv-wire-logcat.mjs` exports:

- `startLogKeeper({ stream, mark, nonce, waitMs = 10_000, tickMs = 5_000 })`. `stream()` starts and returns a child-like object (`stdout`, an `exit` event, `kill()`); `mark(text)` writes one log line on the device. The keeper splits the stream into lines (a line can span chunks), calls `mark("start <nonce>")`, and resolves when that line arrives or `waitMs` passes. From then on it writes a numbered interval marker `tick <nonce> <n>` every `tickMs`. It returns `{ lines(), finish(), stop() }`.
- `finish()` calls `mark("end <nonce>")`, waits up to `waitMs` for that line, stops the stream and returns `{ how: "stream", lines, start, end, open, markers, missed }`: the line count, whether each marker was seen, whether the stream was still open when the end marker was asked for, how many interval markers were written and how many of them never arrived.
- `logKeptErrors(kept)` returns `ERROR tv wire: cannot tell that the run's whole log was kept: <reason>` when `start`, `end` or `open` is false, there are no lines, or an interval marker never arrived (`missed > 0`); otherwise an empty list.
- `describeLogKept(kept)` returns the `device.txt` line, for example `logcat kept by streaming from before the app started (the default buffers): 5210 lines, start marker seen, end marker seen, 4 of 4 interval marker(s) seen, stream open to the end`.

In the runner, per attempt: `logcat -c`; start the keeper with `stream = () => spawn(adb, ["-s", serial, "logcat", "-v", "threadtime"])` and `mark = (text) => shell("log", "-t", "OctaveWireRun", text)`; then start the app. The nonce is `randomUUID()`. The done-line loop reads `keeper.lines()`. At the end the runner calls `finish()`, and still takes one `logcat -d`.

- **Only `judgeLogcat` reads both copies** (the kept lines followed by the final dump), so a line either copy holds is judged.
- **`wireLines` reads the kept lines alone.** The app's `OCTAVE_WIRE` lines, `judgeWire` and `app-lines.txt` come from the stream only. Fed both copies, every result line would appear twice and `judgeWire` would fail every pair (`scripts/tv-wire-judge.mjs:182`).

The stream starts with no `-b`, so it reads the same default buffers as the final dump (spec check issue 11). To check on the emulator: that `adb shell log -t OctaveWireRun "start <nonce>"` appears in the stream.

- The attempt that counts must pass `logKeptErrors`; its errors join `runErrors`.
- A void attempt (the adb connection dropped) loses its stream with the connection. Its kept lines and its final dump are still judged with the second attempt's, as today, and `device.txt` records its kept-log line, but only the second attempt must be whole. The second attempt runs the same tests with the same canary, so a leak recurs there.
- A closed stream on an attempt that is not void fails the run. It is not retried.
- The stream's arguments hold the serial; it is never printed or written.

What the markers show: the stream was attached before the app started, was still delivering at the end, and delivered every numbered interval marker written during the run, so a gap that held a marker would show. They do not show a gap shorter than the interval between two markers, nor a line logd dropped for a slow reader between two markers that arrived. The earlier claim that the final `logcat -d` is a second copy for that case does not hold: a line pruned before the stream read it is not in the dump either (spec check issue 1). logd's slow-reader behaviour was not read from the AOSP source or tested, so it is unverified; `docs/security.md` states the residual limit and does not claim the dump covers it.

### Signals (item 4)

`scripts/tv-wire-device.mjs` exports `openDevice({ adb, appId, proc = process })`. `adb(...args)` is the runner's own function. The device object is created once per run, after the device check, and holds the state a handler needs:

- `clearProxy()` and `setProxy(devicePort)` run `settings put global http_proxy` with `:0` or `127.0.0.1:<port>`.
- `reverse(devicePort, hostPort)` runs `adb reverse`, throws when it fails, and remembers the port. `reversed()` returns the remembered ports; `listReverses()` returns the output of `adb reverse --list`.
- `onStop(fn)` adds a host cleanup (stopping the log stream).
- `restore()` clears the proxy first, force-stops the app, removes each remembered reverse with `adb reverse --remove tcp:<port>`, and forgets them. It never uses `--remove-all`, which would take reverses the runner did not make. Calling it twice is safe.

The device object registers one listener each for `SIGINT` and `SIGTERM` on `proc`, once, at the first `reverse` or `setProxy` call, not when it is opened. Until then a signal stops Node as it does today, so the fixture steps, the APK build and the install are not held open by a handler. The listener calls `restore()`, runs the `onStop` cleanups, prints `ERROR tv wire: stopped by <signal>; the device's http_proxy and adb reverses were restored`, and exits with 130 for SIGINT or 143 for SIGTERM.

`scripts/tv-wire.mjs` reaches the proxy setting and the reverses only through this object: the start-of-run clear, the attempt's `finally` (`device.restore()`), and `missingReverses(device.listReverses(), ...)`. The attempt copies `device.reversed()` before its `finally`, because `restore()` forgets the ports and the count is read afterwards (`adbRestartErrors`, the `device.txt` lines). Its own code then holds no `http_proxy` and no `"reverse"` literal, which a test asserts.

Limits, to state in `docs/commands.md`:

- Node runs a handler only between synchronous calls. While the proxy is set, the runner makes only short `adb` calls and waits with a timer, so the handler runs promptly. During `fixture:up`, the APK build or `adb install` nothing is set and no handler is registered yet.
- SIGKILL and a hung `adb` cannot be handled. The next `pnpm tv:wire` still clears the proxy at its start.

## Test plan

**Item 1, `scripts/tv-wire-evidence.test.ts`.** Uses a real `startRecorder` in front of a local `node:http` upstream on 127.0.0.1, with a token and a canary that percent-encoding and base64 change.

## Risks and out of scope

Risks:

- **Stream and adb.** The stream is one more consumer of the adb connection. A drop already voids the attempt; a stream that closes alone now fails the run. If the CI job turns flaky on this, report it; do not loosen `logKeptErrors`.
- **A blocked event loop loses stream lines only by delay.** The keeper reads between the runner's synchronous `adb` calls. Keep those short while the stream is open; do not add a long `spawnSync` inside the attempt.
- **Recursive removal of an overridden path.** The suffix rule in `evidenceDir` is the guard; do not weaken it.
- **Spawned CLI tests.** They run the real runner. The explicit environment without `ANDROID_SERIAL` is what keeps them off a device.
- **How CI stops a step** (which signals, and how long before a kill) is unverified. The handler makes about a dozen short `adb` calls.
- **Record shape.** Stand-ins change `path` and `scheme` values in the `.jsonl`. `tasksWithWireTests` and T10-01 read the list and `summary.txt`, not the records.
