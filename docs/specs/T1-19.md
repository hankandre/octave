# T1-19: Give each task a lane and run each lane without a relaunch

Implementer: `implementer`. The task touches TypeScript and JavaScript workflow code, the task CLI and docs only. Nothing goes under `modules/` or `apps/tv/android/`, and the PlayerEngine port is not touched, so `touchesNative` is false. It is not a playback task, so no Jellyscale wire test applies. No dependency is adopted.

Depends on T1-18, which is `done` with `passes: true` on origin/main (`pnpm task show T1-18`, commit c54b0294).

## Goal

Today the coordinator starts every task by hand, and only the coordinator knows which work must run serially and which can run in parallel. The owner decided on 2026-11-22 (`docs/specs/decisions-process.md`, "Lanes that run themselves (T1-19)") how this changes:

- every task records a lane;
- a lane runner pulls its lane's next ready task when the current one finishes, without being relaunched;
- where `AGENTS.md` requires serial work, only one native or on-device lane runs at a time.

After this task:

1. Every task in `tasks/prd.json` has a `lane` taken from a fixed list (below).
   - `pnpm task` reads it.
   - `scripts/task-owner.mjs` writes it.
   - `scripts/prd.test.ts` fails a task with no lane or an unknown lane.
   - Only a Product Owner pass sets it.
2. `.claude/workflows/task.js` gains a lane mode, `args: {lanes: [...]}`. It runs one loop per lane side by side. Each loop takes the lane's next ready task as soon as the lane's last task ends.
3. Lanes follow four rules:
   - At most one lane from the serial set has a task running at a time.
   - One lane never runs two tasks at once.
   - A task whose dependency is in another lane waits for it.
   - A denied command stops every lane.
4. `WORKFLOW.md` describes lanes and the runner.

## The lanes (the fixed list this spec sets)

`LANES`, in this order. Serial lanes are marked: at most one of them has a running task at any moment.

| Lane | Serial | What it holds | Why serial or not |
|---|---|---|---|
| `workflow` | no | The task workflow, agents, skills, the task CLI, CI rules, process docs | Node and git only. |
| `core` | no | `packages/core` TypeScript: gateway, negotiation, catalog fetches, redaction rules, the tripwire | Node and Docker fixtures only. Each worktree has its own Compose project (`fixtures-down.mjs`; T3-27 gives each one its own ports). |
| `ui` | no | `apps/tv` React Native screens, shared controls and design tokens | Runs `pnpm tv:e2e` on the agent's own emulator. `AGENTS.md` says "use only your own emulator", not "serial". |
| `apk-checks` | no | Scripts that inspect a built APK: dex, manifest, inspector, cleartext and network-path checks | Gradle in its own worktree, plus offline inspection. |
| `tv-scripts` | no | TV build, e2e, wire and fixture scripts | Own emulator, as for `ui`. |
| `release` | no | Store, signing and bundle work (Distribution) | Build configuration and docs. A task that touches native paths is caught by the switch below. |
| `native-session` | **yes** | Kotlin under `modules/` other than the player: the native HTTP client and session, artwork through it, the install id, the Keystore | `AGENTS.md`: native module work is serial. |
| `player` | **yes** | `modules/player`, Media3, the PlayerEngine port, playback on the device | `AGENTS.md`: player work is serial. |
| `device` | **yes** | Work on a real TV or a device lab: Shield checks, device purchases, real-device runs | `AGENTS.md`: on-device work is serial. Every task proposed for it is `human: true`, so the runner never takes one. The lane is serial so that a later non-human device task stays serial. T11-06 (a release build on a 1 GB emulator profile) is `human: false` and uses an emulator of its own, so it is in `tv-scripts`, not here. |

`SERIAL_LANES = ['native-session', 'player', 'device']`.

The first seven names follow the owner's example list ("native-session, apk-checks, tv-scripts, ui, core, player, workflow"). `release` and `device` are added because Distribution and Device lab tasks fit none of the seven, and every task needs a lane, including done and human ones.

**Native routing in lane mode.** A task in `native-session` or `player` runs with `native: true`, so it goes to `native-engineer` and gets a `guardian` review. A task whose `model` is `fable` runs with `risk: 'high'` (the Product Owner sets `fable` on high-risk tasks, for example T3-33: "Model fable: the owner's first worry", product-owner-log). Every other task runs with `risk: 'routine'`.

**A task in a parallel lane that turns out to be native.** If `goNative` switches a parallel-lane task to native after its spec or check, or the review finds native files, the task waits for the serial slot before its next work step (Tests, Implement or the follow-ups). It holds the slot until it ends. The run logs `<ID>: lane <lane> holds native work; the serial slot is taken` so that the Product Owner can move the task.

3. **Lane runner (milestone 3).**
   - Add the `LANES` block, `runLanes`, and the two `opts` hooks in `runTask`.
   - The loop for each lane:

     ```
     while (!halt) {
       laneState[lane] = 'querying'; seen = changes
       gate = await laneGate(lane)                         // top-level relay, see below
       if gate.action === 'denied': set halt; break
       if not pass: lane stopped 'lane-state'; break
       if changes !== seen: continue                      // stale snapshot: ask again
       d = pickLane({state, lane, snapshot: gate.json})   // and, with no await in between:
       if d.action === 'run' and lane is serial: slot.take(lane)
       switch d.action:
         'stop': record; break loop
         'wait': laneState[lane] = 'waiting'; await stateChanged; continue
         'run':  laneState[lane] = 'running'; state.attempted.add(id)
                 try   out = await withTeardown(() => runTask(id, {risk, native, root, models, halted, holdSerial}), () => tearDownFixtures(id, root))
                 finally release the slot if this task holds it; laneState[lane] = 'querying'; changes += 1; signal stateChanged
                 if out.outcome === 'denied' or out.fixtures.denied: set halt
                 else if STOP_OUTCOMES or ruling-unlogged: lane stopped by out.outcome
     }
     ```

     `laneGate` is `runLanes`'s own top-level gate relay: `runGate`, `gate` and `result` are closures inside `runTask` (`task.js:477,504-517`) and `runLanes` cannot call them. It builds the same relay prompt with the denial sentence, calls `agent` with label `lane state <lane>`, `model: models.gate`, `schema: GATE` and phase `Spec`, and retries once on an unreadable result, as `tearDownFixtures` does. It adds no `guarded(` call (the frozen count is 3).

     The whole loop body sits in a `try`. A throw ends that lane `failed` with the message, marks it `stopped`, counts a change and signals, so `Promise.all` never rejects and no lane waits forever.

   - `pickLane` reads `state.laneStates`, `state.attempted`, `state.slotHolder` and `state.halted`. Its order:
     1. `halted` means stop.
     2. Any `inFlight` task not in `attempted` means stop `lane-busy`.
     3. The first task not in `attempted` with an empty `waitingOn` is the candidate. If the lane is serial and the slot is held by another lane, wait `serial`. Otherwise run.
     4. With no candidate: if any other lane is `querying` or `running`, wait `dependency`; otherwise stop `none-ready` with the waiting tasks and their `waitingOn`.

## Risks and out of scope

- **Concurrency is unverified.** Whether the Workflow tool runs overlapping `agent()` calls in parallel is unverified; no doc in the repository or under `~/.claude` says so.
  - The scheduler is correct either way: tasks would only interleave, never break a rule.
  - If the runtime refuses overlapping calls, the fallback is one run per parallel lane, plus one run holding all the serial lanes together, so the serial rule still holds without a cross-run lock.
  - The PR records what the first real lane run showed (do the two lanes' `agent()` calls overlap?). If the calls serialise, the implementer files a `tasks/backlog.jsonl` line for the fallback above.
- **Two runner invocations do not see each other.** A lane's in-flight check sees other runs' worktrees and branches (`lane-busy`), but two separate lane runs that both hold a serial lane would each think the slot is free. WORKFLOW.md says: start all serial lanes in one run.
- **Existing worktrees.** On main today (`git worktree list`, re-read on this branch), `todo` tasks T3-08, T3-09, T3-29, T3-33, T4-09, T5-02 and T9-07 have worktrees, and T1-17 is `in_progress`. T3-30 is `done` on main (`111a3317`), and T3-02, T3-03 and T3-23 are done, so their worktrees do not count. A lane holding a `todo` or `in_progress` one stops `lane-busy` until the coordinator finishes it with `{task, from}` or removes it. This is deliberate: two sessions in one worktree would break "two tasks of one lane never run at once". The runner offers no way to take over such a task, because a run with no `from` on a branch that is already implemented ends `tests-green` at the red gate.
- **The main checkout is shared.** Lanes run `git fetch`, `git worktree add` (in the Spec step) and Ship's `git pull --ff-only` in one main checkout at once. `lane-state.mjs` retries a locked fetch. A `worktree add` or a `pull` that hits a lock fails its own step, and that task ends `failed` without stopping the other lanes.
- **The run blocks once by design (Approach, step 4).** The backfill needs a Product Owner commit, and today's workflow has no step that makes one inside a run. Adding such a step is out of scope.
- **`tasks/prd.json` size.** The file is 243,693 bytes on main (measured at HEAD 20f74667). With the lanes it becomes 248,296 bytes, 1,704 under `MAX_FILE_BYTES` (250,000). Each merged task can add up to 600 bytes of evidence, and `scripts/task.test.ts:269` checks the real file, so main goes red after about three merges. Making room is a required part of the Product Owner commit (Approach, step 4), and the implementer re-measures before asking for the pass.
- **A Product Owner pass that lands on main first.** Main's `task-owner.mjs` has no `lane`, so a pass that adds tasks before this PR merges adds them with no lane, and after the branch sync the real-file lane test is red on this branch. The fix is a new lane-edit Product Owner commit on the branch (`edit {lane}` for each such task, with a log entry and the trailer). The coordinator holds Product Owner passes on main between the lane commit and the merge.
- **A native task in a parallel lane runs Implement outside the slot when only the review finds it native.** `holdSerial` prevents parallel native work when the spec or the check shows native paths, but when the review finds native files, Implement has already run. The follow-ups wait for the slot and the run logs the mismatch, so the limit is detection, and it is written in WORKFLOW.md's Lanes text. The cure is a correct lane from the Product Owner.
- **`task.js` grows past 1,000 lines.** Splitting it is out of scope (as in T1-16); log it in `tasks/backlog.jsonl` if the review asks for it.
- **A denial halts at the next phase boundary, not mid-step.** A step already running (for example a Ship waiting on CI) finishes first. A halted task keeps its branch and is resumed with `from:`. This reads "stops every lane" as stopping work already under way as well as new tasks (question 5).
- **Lane lists in the spec are proposals.** The Product Owner decides each task's lane, and the owner can veto it.
- **Out of scope:**
  - priorities across lanes;
  - a lane for each phase;
  - automatic lane assignment from changed paths;
  - re-ordering `pnpm task next` (it keeps file order across lanes);
  - changes to `STOP_OUTCOMES` or batch mode.
