# T9-09: Keep the account's settings on the server's display preferences

Task: `T9-09` (phase T9, domain Server Connection & Identity, lane `core`, skill `jellyfin-api`, verify `pnpm check`). Depends on T9-02 (done, commit 1f327bfa) and T2-08 (done, PR #244), both `passes: true` on origin/main (`node scripts/task.mjs show T9-02`, `show T2-08`).

Implementer: `implementer` (TypeScript only: `packages/core`, `apps/tv/src/host`, `tests/integration`, documents). No file under `modules/` or `apps/tv/android/` and not the PlayerEngine port. Not a playback task: it builds no media URL and sends no PlaybackInfo, so it has no Jellyscale wire test; its Jellyscale evidence is the recorded contract fixtures and the endpoint inventory (below).

## Goal

Store the per-account settings that exist (auto-play and its countdown, the intro and credits skip modes, the Continue watching window; no subtitle setting, by the Product Owner's ruling below) in one Octave-owned display preferences record on the signed-in account, read and written only through the core's gateway, so they follow the account to every device and switch with the account. Values read pass T9-02's allowlist; a save writes only Octave's own keys, built from that allowlist, and never a token, URL or play-session id. A failed read gives the defaults. A failed save puts the old value back and tells the caller.

## Decisions

Provisional under the Product Owner and the owner's veto, as every refiner decision.

- **D1. One record, Octave's own.** Address: `GET` and `POST /DisplayPreferences/octave` with query `userId=<session user id>&client=octave`, in that order (the gateway's `params` `{ userId, client }`, so the transport encodes them; R1). `client=octave` keeps the record apart from every other app's (Jellyfin's web client uses `usersettings` with `client=emby`, `compat/captures/jellyfin-web-12.4.json`); because a Jellyfin POST replaces every custom key of its record, writing into another app's record would erase that app's settings. Every Octave app (TV now, mobile later) shares this one record, which is what makes the settings follow the account. `userId` is sent as other gateway calls send it; Jellyscale ignores it.
- **D2. Octave's keys and their text.** `CustomPrefs` values are strings, one key per setting, all prefixed `octave.` so no reserved Jellyfin key (`homesection*`, `landing-*` and the six named ones) can match:

  | Key | Field | Values written |
  |---|---|---|
  | `octave.continueWindow` | `continueWindow` | `30`, `90`, `180`, `365`, `all` |
  | `octave.autoPlay` | `autoPlay.enabled` | `true`, `false` |
  | `octave.autoPlayCountdown` | `autoPlay.countdownSeconds` | `5`, `10`, `15` |
  | `octave.skipIntro` | `skipModes.intro` | `button`, `auto`, `none` |
  | `octave.skipCredits` | `skipModes.credits` | `button`, `auto`, `none` |

  Reading maps each key back (exact, case-sensitive text) and passes the result through `sanitizeAccountPreferences`, so a missing or wrong value falls back to its own default and `"7"` or `"14"` reads as `"90"`. No subtitle key (R2); a future account field (subtitle style) adds one row and one entry in `ACCOUNT_PREFERENCE_KEYS`. The table's row order is the order the five keys are written in `CustomPrefs` (R1).
- **D3. A save changes one or more fields, never the others.** `saveAccountPreferences(change)` reads the record fresh, applies `change` to the decoded values, posts, and returns the values it posted without reading again (one GET, one POST, R1). So two devices that change different settings do not undo each other, and a save after a failed launch read cannot write defaults over the account's other values. Saves run one at a time on their own queue; no signal (leaving Settings must not abandon a write half-way), as `saveAccountLanguages`. A fresh read that fails, or whose body has no `CustomPrefs` object, throws (`AccountPreferencesUnreadable` for the second) and posts nothing.
- **D4. The body is built, never echoed.** The POST body is a constant DTO, its fields in this order (`Id: "octave"`, `Client: "octave"`, `SortBy: "SortName"`, `SortOrder: "Ascending"`, `RememberIndexing: false`, `RememberSorting: false`, `ScrollDirection: "Horizontal"`, `ShowBackdrop: true`, `ShowSidebar: false`, `PrimaryImageHeight: 250`, `PrimaryImageWidth: 250`, the same defaults Jellyscale answers for an empty record) then `CustomPrefs` last, holding first the **kept keys** and then the five keys of D2 in the table's order, written from sanitized values (R1). For the golden's read and save this gives exactly `b13` in R1. A kept key is a key read from the record that starts `octave.`, is not one of D2's, matches `^octave\.[A-Za-z][A-Za-z0-9]{0,31}$`, and whose value matches `^[A-Za-z0-9]{1,16}$`. Kept keys let a newer Octave's setting survive a save from an older build on another device; the value pattern cannot hold a URL (no `:` or `/`), a 32-hex token or play-session id (too long), or an authorization value. Every other key and every typed field read is dropped. The record is Octave's own (D1), so dropping a foreign key there touches no other app's settings; Jellyfin rebuilds its reserved keys from defaults.
- **D5. Where the code lives.** Mapping in a new `packages/core/src/jellyfin/account-preferences.ts` (pure, no HTTP import); two thin gateway methods in `gateway.ts` whose path is the template `` `/DisplayPreferences/${ACCOUNT_PREFERENCES_RECORD.id}` `` written inline in the `this.get`/`this.post` call, so the T2-08 parser reads `GET` and `POST /DisplayPreferences/{}` and matches the inventory and the golden (R1). The path is never held in a variable or built by a helper, which would hide the route from the parser. The port type `AccountPreferenceSource` (`read(): Promise<AccountPreferences>`, `save(change: Partial<AccountPreferences>): Promise<AccountPreferences>`) goes in `packages/core/src/preference-store.ts`; the gateway satisfies it structurally through `accountPreferenceSourceOf(gateway)` in the new file.
- **D6. The TV store follows the active account.** `createDevicePreferenceStore` gains:
  - `useAccount(source: AccountPreferenceSource | undefined): Promise<void>`: puts the account fields back to their defaults at once (the last account's values never show under the next), notifies if they changed, then reads from `source`. The promise settles, never rejecting, when the read has landed or failed. A failed read (rejection, synchronous throw) keeps the defaults. A read that lands after another `useAccount` call is ignored. A read sets only the fields not changed on this account since the switch. `undefined` (signed out) leaves the defaults and reads nothing.
  - `saveAccount<K extends AccountPreferenceKey>(key: K, value): Promise<"saved" | "failed" | "no-account">`. It never rejects.
    - **With an account:** sets the value (through `sanitizePreferences`), notifies once, then calls `source.save({ [key]: value })` on a chain. Success resolves `"saved"`. On failure (rejection, or the source throws synchronously) it puts the previous value back only if that field has not changed again on this account since, notifies, and resolves `"failed"`, so the screen shows its sentence and the restored value. A result that arrives after a switch changes nothing on the new account and resolves `"failed"` or `"saved"` without touching `get()`.
    - **With no account** (before any `useAccount`, or after `useAccount(undefined)`): sets the value in memory (through `sanitizePreferences`), notifies once, calls nothing, restores nothing, and resolves `"no-account"`. This is T9-02's behaviour for account keys, which the frozen T9-02 tests rely on (`scripts/tv-preferences.test.ts`, "T9-02 item 3: updates of autoPlay, skipModes and continueWindow change get() and write nothing": three updates, `flush()`, `get()` holds the new values, exactly 3 notifies, no write; and "a device write after account updates holds version and streamingLimits only", whose final `get()` holds the account values). The value is dropped at the next `useAccount`, which resets the account fields.
  - `update(key, value)` on an account key calls `saveAccount` and drops the result, so the core's views (`autoPlayOf`, `skipModesOf`, `continueWindowOf`) save through it unchanged. Device keys behave as in T9-02. No account field is ever written to the device record.
  - The type `DevicePreferenceStore` is renamed nowhere; it gains the two methods. `hostPreferences()` returns the same store.
- **D7. Another device's change shows at the next `useAccount`** (launch with a restored session, sign-in, or a switch). No polling and no refresh on Settings open: no screen exists yet, and T9-03 can call `useAccount` again if it needs a fresh read.
- **D8. No migration from the device.** The TV has never stored a window on the device (Facts), so there is nothing to move. A stale `"7"`/`"14"` read from anywhere (a device record or the account's record) is `"90"` by `continueWindowOrDefault`, and the next save writes `90`.
- **D9. Who calls `useAccount`.** The task that makes an account active (restore at launch, T4-05; sign-in, T4-03/T4-04; switch, T4-06/T9-05). A backlog line is appended so that task wires it (below). This task provides and tests the method.

## Risks and out of scope

Risks:

- **The hand-written golden fixes the wire.** R1's baseline was written before the methods exist; the code must match it byte for byte (path, query order, body field and key order). A mismatch is fixed in the code. Only a baseline that D1, D2 or D4 contradicts goes back in `frozenTestProblems`. Writing the path through a variable or a helper to slip past the T2-08 parser is not allowed: it would hide the route from the inventory.
- **Changing a shared recorder helper.** The `client` option on `call`/`callStatus` is additive with today's header as default; an existing recorder that changed its header would change recorded fixtures. `pnpm fixture:check-jellyscale` and the existing fixture tests catch it.
- **The no-account result.** `"no-account"` keeps T9-02's in-memory behaviour; a screen that saves before `useAccount` would show a value that is lost at the next `useAccount`. No screen exists yet; T9-03 decides what Settings shows when signed out.
- **Concurrent saves from two devices.** Each save reads fresh then posts the whole Octave set; two saves within one round trip can lose one change (last write wins). Accepted: settings change rarely.
- **Jellyfin's GET of an unwritten record creates it** (Facts). Harmless: an empty Octave record.
- **Jellyscale replaces the stored JSON whole and returns it from `jsonb`.** Key order and spacing may change; the decoder reads by key. Unverified until milestone 0 that its answer round-trips every value byte for byte.
- **The 12.4 image vs tag.** The Jellyfin 12.4 facts come from tag `v12.4`; the pinned image is a dated build. Milestone 0's recording is the check.
- **A newer Octave build's setting** survives an older build's save only if its key and value fit D4's patterns; a later field that needs a longer value must widen them in both builds' sense (a value outside the pattern is dropped by an older build's save).
- **No screen shows a failed save yet**; T9-03 shows the sentence and the restored value.

Out of scope:

- Wiring `useAccount` into sign-in, restore and switching (backlog line, D9), and any Settings screen or copy (T9-03).
- A subtitle setting (R2; backlog line), the account's languages and subtitle language (T9-04), and remembered sort per library (T6-03).
- Live refresh of another device's change while signed in (D7).
- Moving the streaming limits or any device field to the server.
