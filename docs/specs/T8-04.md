## Goal

The player screen a viewer can drive with the remote alone:

1. Only the picture shows until a key is pressed. An arrow shows the controls with focus on the scrubber; the select key shows them with focus on Play or Pause.
2. Left and Right on the scrubber move 10 s per press; the centre key and the play-pause key pause and resume; the controls hide 3 s after the last key while playing and stay while paused.
3. The top bar says what is playing. Before the first frame the title stands over its backdrop with one honest status line; "Buffering…" shows only after half a second.
4. Back stops the player first and then returns to the card the viewer came from; a player that did not stop keeps the screen, says so, and offers the one way out.
5. The screen stays awake while the picture plays and may sleep while it is paused.
6. Every colour, size and duration of the screen is a design token read in React; Kotlin draws none (D14).

## Approach

### D1. The chrome is React Native views over the native video view; the video and the wake state are native

**Confirmed by the Product Owner, 2026-11-26** (provisional; the owner can veto). The reasons and the conditions are at the end of this section.

This is the hard question of the task, and the rules pull two ways (Facts, "What 'native' means").

**What a Kotlin chrome would cost.** Each line is a surface change, which `AGENTS.md` makes an architecture change with a decision record and an allowlist edit:

- The title block, the backdrop's image reference and the status line are not in the launch request, so they need view props or launch keys; `LaunchRequestReader` and its frozen tests refuse unknown keys.
- Pause, seek and Back belong to the Playback Session, in TypeScript: the coordinator reports on pause and seek, `Viewing` decides what a stop means, and T8-22's retry position is kept there. A Kotlin chrome either calls the engine behind the coordinator's back, or sends its intents to JavaScript as new events.
- Every later panel needs TypeScript data in Kotlin: the Settings panel is the Settings screen's own sections (`DESIGN.md` §7.14), the info sheet reads the plan (T8-06), Up Next reads the next episode and the auto-play setting (T8-15).
- The shared controls, `FocusFrame`, the Tabler icon font and reduced motion are React. A Kotlin chrome needs a second set, against "Build screens from the shared controls", and a third in Swift for Apple TV; decision 0003 chose React Native because it "reaches Android TV and tvOS with one UI".

**What a React chrome costs.** No surface change at all. What is lost:

- Key handling runs on the JavaScript thread: a key reaches the chrome one bridge crossing later than it would natively, and a stalled JavaScript thread means no chrome. During playback that thread does one small update a second. **Unmeasured on the Shield and the cheap box**; the wire test proves it works on the emulator, not how it feels.
- The chrome cannot show while the React tree is down. The video would keep playing; the unmount path stops it.
- Keys arrive on key up, and a held key by react-native-tvos's own 300 ms rule (Facts). T8-05 owns the hold and decides whether that rule is good enough for scrubbing.

**Decision.** The chrome is drawn in React Native over the module's view. React Native on Android draws platform views in the app's window, the same window a Kotlin chrome would use, so it is not a painted or web layer (`PRODUCT.md` pillar 2), and it is exactly "Streamyfin's shape", which decision 0003 names as the model. Native are the things only native code can do: decoding and the surface (T8-02), the picture's frame in its own shape (its own task, D12), and the screen staying awake (D12). They cross inside Kotlin, through a slot beside `VideoSurfaceSlot`, never through JavaScript.

**What must be recorded, because the words in force say otherwise.** `ARCHITECTURE.md:69` and `T8-01` D8 say the chrome is native. So:

- **This task amends decision 0003, in milestone 0, before any chrome code.** A section is appended at the end of the record, "Amendment, 2026-11-26 (T8-04): what 'the player screen is native' means". No existing line of the record is edited: line 95 and the risk at line 89 stay as written, because a decision record is history (`WORKFLOW.md:38`). The section says:
  - The player is a native view in an Expo module, with native decoding, surface and wake state. Its controls are React Native views drawn over it, which is what the precedent the decision names does (Streamyfin's `components/video-player/controls/hooks/useRemoteControl.ts` reads `useTVEventHandler`, branch `develop`, read 2026-11-26).
  - The module's surface does not grow for the chrome; every panel reads its data in TypeScript.
  - `docs/specs/T8-01.md` D8's reason ("the chrome is native, so React only places the view") is replaced; its rule, a view with no props, stands.
  - **Unmeasured:** the time from a key to the chrome on the Shield and on the cheap box. Keys reach React at key up, on the JavaScript thread; a held key is named only after 300 ms.
  - **Revisit if** (as the Review ruling of 2026-11-26 rewrote it, because no task held the first wording) either finding is made. (1) T8-05's spec, the next task of the player lane, finds that react-native-tvos's hold rule does not carry hold to scrub; that spec states its finding either way (backlog line 380). (2) The median time from a remote key to the controls being drawn, with the picture playing and the controls hidden, is over the budget the owner sets in T3-12 for a key press to a focus change, on the Shield or on the cheap box. T3-12's script is what measures it, by the method it uses for key to focus, and T8-21 is where the Shield's reading is judged. Neither task holds that yet: a pass adds one item to each (backlog line 379, `needsPass`), and until it does, finding (2) is not in force and the amendment says so. The remedy is a native key source that feeds the same key rules, which is a surface change with its own decision record; it is not a rewrite of the chrome.
  - It is a Product Owner call under `decisions-owner-chat-2026-11-25.md` §1, provisional, and the owner can veto it.
- `ARCHITECTURE.md` line 15 and line 69 are reworded to match in the same milestone, and `DESIGN.md` §7.14's first sentence in milestone 5.
- **What the code must keep so the remedy stays cheap:** the key rules stay pure and know no key source (`chrome-keys.ts`, D4), and exactly one file reads the remote (`use-remote-keys.ts`, D2).
- **The PR says so plainly**, under "untested gates": key-to-chrome time on the Shield and the cheap box is unmeasured; the emulator's wire run proves the keys arrive, not how they feel.
- No Swift-mirrorable chrome interface is needed. The native additions are plain Kotlin a Swift engine can mirror: `PictureState` and the listener contract of `PictureSlot`.

**Why the Product Owner confirmed it.** The words "native player screen" were written to keep the picture off a painted layer and on the device's decoders (`PRODUCT.md` pillar 2), and D1 keeps both: React Native on Android draws platform views in the app's window. The alternative buys a faster key path, unmeasured, at the price of a growing module surface (each panel's data, each an architecture change), a second control set in Kotlin and a third in Swift, against decision 0003's own reason for React Native ("one UI"). If the measurement goes against D1, the remedy above is one narrow native key source, not a Kotlin chrome.

### D3. `Viewing` gains pause, seek, leave and what the screen shows

```ts
export type ViewingTitle = { name: string; seriesName?: string; season?: number; episode?: number };
export type ViewingState = {
  itemId?: string;
  phase: ViewingPhase;
  session: PlaybackSessionState;
  title?: ViewingTitle;        // from the item read
  backdrop?: ImageRef;         // the item's, when it has one
  opening?: "original";        // a direct-play plan is known; absent before a plan and for a conversion
  seekingTo?: number;          // seconds; the target of a seek that has not landed
};
setPaused(paused: boolean): void;
togglePaused(): void;           // from the latest snapshot's `paused`
seekBy(deltaSeconds: number): void;
leave(): Promise<void>;         // Back
```

- `setPaused`, `togglePaused` and `seekBy` do nothing unless the phase is `playing` (so nothing before the first frame, after the end or after a failure). They call the engine and return; a rejected call changes no state and its filtered reason goes to the `FailureLog`. The reports follow from the engine's own `state` events (`coordinator.ts:389-393`), so nothing here reports.
- `seekBy`: the base is `seekingTo` when a seek is pending, else the snapshot's position; the target is clamped to 0 and, when the duration is known, to the duration; `seekingTo` is published at once and cleared by the next `state` event with cause `seek`. One `engine.seek` per call. T8-05's hold builds its pending position on top of this and commits once.
- `title`, `backdrop`: published when the item read returns (`viewing.ts:173-175`).
- `opening`: the coordinator's new `onPlan` callback fires when the plan is set and before the launch; `Viewing` publishes `"original"` for `delivery: "static"`. A converted plan publishes nothing here: its line is T8-09's.
- `leave()`: the same stop as `stop()`, but its promise settles when the engine has stopped (or at once when nothing was launched), not when the reports flushed; the conclusion, the flush and `afterViewing` run on as today. When the engine did not stop it rejects with `PlayerStopError`, and the state becomes `failed` with `stop-failed`. Called again in that state, it tries the coordinator's stop once more.
- `stop()` keeps its contract, with one fix: called when no viewing is running and the last stop failed, it tries the stop again instead of returning the settled promise (`viewing.ts:135-137`).

### D4. The key rules

`chromeState(state, input)` is a reducer over `{ shown: boolean; zone: "top" | "scrubber" | "controls" | "none"; idleAt?: number }` with a `switch` on the input, and it returns the next state and at most one command (`show-scrubber`, `show-play`, `seek-back`, `seek-forward`, `toggle`, `pause`, `resume`). The screen runs the command and owns the one timer.

| Chrome | Key up | What happens |
|---|---|---|
| hidden | `up`, `down`, `left`, `right` | Show with focus on the scrubber. No seek |
| hidden | select, read as the focus holder's `onPress` | Show with focus on Play or Pause. No toggle |
| any | `playPause` | Toggle; pausing shows the chrome with focus on Play or Pause |
| any | `play`, `pause` | Resume, pause; the same showing rule |
| shown, focus on the scrubber | `left`, `right` | `seekBy(-10)`, `seekBy(10)` |
| shown, focus on the scrubber | select, read as the scrubber's `onPress` | Toggle |
| shown, focus on a control | select, read as that control's `onPress` | Back, back 10, Play or Pause, forward 10 |
| any | the hardware `select` and `longSelect` events | Never a command. While shown they restart the idle timer, as any key does |
| shown | any key, a `long…` name included | The 3 s idle timer starts again |
| shown, playing | no key for `motion.chromeIdleMs` | Hide, with a control focused or not; focus returns to the focus holder |
| shown | paused, a `hold`, loading or failed | No idle timer |

- **One select, one path.** A select press reaches JavaScript twice: `ReactRootView` first sends the hardware event `select` and then hands the key on, so the focused `Pressable` fires `onPress` at the same key up (Facts, "Keys"; the spec check's issue 3). Every select is read from `onPress` and from nowhere else, because something is always focused (D5) and every focusable of the screen is a `Pressable`:

  | Where focus is | What reads select | What reads the other keys |
  |---|---|---|
  | The picture, chrome hidden (the focus holder) | the holder's `onPress`: show, focus Play or Pause | hardware events: an arrow shows on the scrubber; `playPause`, `play`, `pause` |
  | Top bar (Back) | Back's `onPress` | hardware events restart the idle timer; `playPause`, `play`, `pause` |
  | Scrubber | the scrubber's `onPress`: toggle | hardware `left` and `right` seek; `playPause`, `play`, `pause` |
  | Control row | the focused control's `onPress` | hardware events restart the idle timer; `playPause`, `play`, `pause` |
  | Loading layer and the `stop-failed` row | the focused button's `onPress` | none: the key rules do not run |

  `use-remote-keys.ts` maps the hardware `select` and `longSelect` to the input `activity`, which can restart the idle timer and can return no command; `chromeState` has no case in which `activity` shows, toggles or seeks. Up, Down, Left and Right off the scrubber are focus moves made natively (D5); their hardware events are `activity` too.
- **The press that shows the chrome cannot also toggle.** The holder's `onPress` fires at key up; focus moves to Play or Pause after that render commits, so that control never saw the press begin and fires nothing. On the device the wire run proves it (D13, the `centre-wake` step).
- **One press in a test.** `pressRemoteSelect(element)` (`apps/tv/src/player/test-support/remote.ts`) is the only way a T8-04 Jest case presses select: it emits the hardware `select` key-up event first, as `ReactRootView` does, and then the frozen `pressSelect(element)`. It is one press delivered once on both paths, so a rule that read both would show twice or toggle twice, and the cases assert exact call counts (one show and no toggle on the holder; `togglePaused` once on Play or Pause; once on the scrubber). No T8-04 case calls `pressSelect` or emits a bare `select` by itself, except the `chrome-keys.test.tsx` case that feeds `activity` and expects no command.
- "Focus on the scrubber" is what the scrubber's `onFocus` and `onBlur` reported last, so a `left` that follows focus onto another control never seeks.
- Pausing with the play-pause key while the chrome is already shown leaves focus where it is; only a hidden chrome is shown on Play or Pause.
- A held Left or Right arrives as `longLeft` or `longRight` and seeks nothing in this task; it only keeps the chrome up. T8-05 gives it its meaning.
- **Key up only** (Product Owner ruling, 2026-11-26, Implement). `use-remote-keys.ts` reads a hardware event only when its `eventKeyAction` is 1 (key up) and drops every other, before the key rules see it. The reason is in the library (`ReactAndroidHWInputDeviceHelper.handleKeyEvent`, react-native-tvos 0.88.1-0): once a hold is detected it sends the `long…` name on the next key down and again on key up, so a rule that read both would act twice on one press. Only the four arrows and select start that detection (`isSelectOrDPadEvent`), so a held play-pause key arrives once, as `playPause`, at key up, and `longPlayPause` is never sent; mapping it to `playPause` stays harmless. This corrects the Facts' "its key up is sent under the long name": so is one key down. A key down does not restart the idle timer either; what a hold means is T8-05's.
- `rewind`, `fastForward`, `info` and `menu` do nothing yet (backlog line; `DESIGN.md` §9 names none of them for the player's transport).
- Skip and Up Next come before "show on Play or Pause" for select (`DESIGN.md` §7.14); T8-14 and T8-15 add their rows.

### D5. Focus

- **Something always holds focus**, so the root view always gets the keys (Facts, "Keys"). With the chrome hidden that is the focus holder: one full-screen focusable `Pressable` with no ring and no lift, labelled "Player controls" for TalkBack. It is the one place Octave shows no focus, which is `DESIGN.md` §7.14's "Pure video by default". While the chrome is shown the holder is not focusable. The holder names its own tag for `nextFocusUp`, `nextFocusDown`, `nextFocusLeft` and `nextFocusRight`, so the arrow that JavaScript reads at key up moves nothing natively at key down.
- **Three zones**, top to bottom, as §7.14 orders them: the top bar (Back), the scrubber, the control row (back 10, Play or Pause, forward 10).
- **Moves are stated, not searched.** Every focusable of the chrome names its neighbours with `nextFocusUp`, `nextFocusDown`, `nextFocusLeft` and `nextFocusRight` (tags from `tagOf`): Back's Down is the scrubber and its other three are itself; the scrubber's Up is Back, its Down is the control row's remembered control (Play or Pause until another was focused), and its Left and Right are itself, so those keys never leave it; each control's Up is the scrubber, its Down is itself, and the row's two ends trap. "Each zone remembers its last control" is that remembered tag.
- **How focus is drawn.** Back and the three transport controls are `IconButton`s, so they get `FocusFrame`'s two-tone ring and lift (and no scale under reduced motion). The scrubber draws focus as §7.14 item 2 says: the track grows from `scrubTrackH` to `scrubTrackHActive` and the `scrubThumb` thumb appears in `text1`; it has no ring and no lift.
- **Reaching a control without a pointer.** Arrow, then Down, is Play or Pause; arrow, then Up, is Back; select from the picture is Play or Pause. Nothing in the chrome is reachable only by pointer.
- **The hidden chrome cannot take focus.** While hidden, the top bar, the scrubber and the control row are not mounted: there is no view for Android's focus search to find, so the arrow that wakes the chrome cannot land on a control before JavaScript shows it. During the `durBase` fade out the chrome is still mounted but every control in it has `focusable={false}`, and the holder is focusable and focused from the first frame of the fade, not its last.
- **Still mounted from the first render of the fade** (Product Owner ruling, 2026-11-26, Implement). `useFade` (`apps/tv/src/design/fade.ts:41`) returns `show: visible || leaving`, and `leaving` is set in an effect, so in the render where hiding starts `show` is false: the element is dropped for one render and mounted again to fade. The chrome must not do that: a dropped and re-mounted control loses its tag, and D5's neighbours and the fade both rest on the same views staying up. The fix is in the player's use of the hook, not in the hook: the chrome keeps its own "was shown in the last render" and stays mounted through the render where hiding starts, then follows the hook's `show` until the fade ends. `fade.ts`, `Dialog` and `Toast` are not changed in this task (backlog line). Under reduced motion there is no fade and the chrome unmounts at once.
- **Where focus goes from the holder.** Showing is one render that mounts the chrome and makes the holder not focusable; in the effect after that commit, `focusView` moves focus to exactly one target: the scrubber for an arrow, Play or Pause for select and for a pause by the play-pause key. Nothing is left to `hasTVPreferredFocus` or to the platform's choice of a first focusable. Hiding is the reverse: the holder becomes focusable and gets `focusView`, then the chrome fades and unmounts.
- **Other layers.** While the loading layer or the `stop-failed` row is up, the holder is not focusable and the layer's one button holds focus and names itself in all four directions.

### D9. Back, and a player that did not stop (backlog 359)

- The player screen registers its own `hardwareBackPress` listener while mounted. It is registered after the shell's, so it is called first (Facts), and it returns true.
- While the viewing is being left, the screen keeps its layer: Back during loading shows the loading layer until the stop settles (Review follow-up, 2026-11-26).
- When the coordinator's own stop fails after the session ended (`ended` with `eof` or `error`), the viewing remembers it as it does a failed `leave()`, so the button and the next Back ask the player to stop again (Review follow-up, 2026-11-26).
- Back: `viewing.leave()`; when it resolves, `shell.close()`. The shell pops and restores the card, as today. Back does not wait for the Stopped report (`leave`, D3), so a slow server never holds the viewer on a stopped player.
- The Back control in the top bar and on the loading layer does the same.

### D13. The wire test `player-transport`

The riskiest belief in D1 is that the remote's keys reach React and move the transport on a real Android TV image. Jest has no focus engine, so the proof is on the emulator, in CI.

- **Keys from the host.** `WireContext.press(key)` writes one app line naming a key from a closed list and a count; the runner, which already streams the app's lines, answers each with one `adb shell input keyevent <code>` (`scripts/tv-wire-keys.mjs`: `DPAD_UP` 19, `DPAD_DOWN` 20, `DPAD_LEFT` 21, `DPAD_RIGHT` 22, `DPAD_CENTER` 23, `MEDIA_PLAY_PAUSE` 85, `BACK` 4). Any other name fails the run. `scripts/tv-first-focus.mjs:133` already sends a key this way. Each is one short `adb` call, as the runner's signal rule needs (`docs/commands.md`, "Signals").
- **The run**, on `jellyscale`, with the app's probe-backed gateway and the 60 s episode `Synthetic Show S01E01` (as `player-viewing`): sign in, clear the resume point, build a `Viewing`, and show the real `PlayerScreen` over it with the real view, playing from the start. The steps are ordered so that the server's records, not the app's words, carry each claim (below):
  1. **Wake.** Once the position passes 2 s: `DPAD_RIGHT` (chrome hidden, playing). The app writes `wake=no-seek` when the position did not jump.
  2. **Pause by key.** At once, `MEDIA_PLAY_PAUSE`; `pause=ok` when the snapshot is paused. The chrome was already shown, so focus stays on the scrubber, where step 1 put it. The runner reads the window (below).
  3. **Seek while paused.** `DPAD_RIGHT` twice (`seek=+20`), then `DPAD_LEFT` (`back=-10`).
  4. **The centre key.** `DPAD_DOWN` (focus to Play or Pause), `DPAD_CENTER` (`centre=resumed`); the runner reads the window; `DPAD_CENTER` (`centre=paused`); then, still paused, `DPAD_RIGHT` and `DPAD_LEFT` (`down=play-pause` when the position did not move); `MEDIA_PLAY_PAUSE` (`resume=ok`).
  5. **Select on the picture.** Wait `motion.chromeIdleMs` plus 1 s with no key, so the chrome hides. `DPAD_CENTER` (`centre-wake=shown` when the snapshot is still playing 1 s later), then `DPAD_CENTER` again (`centre-wake=focused` when the snapshot is paused: the first press toggled nothing, and the second toggled), then, still paused, `DPAD_RIGHT` and `DPAD_LEFT` (`centre-wake=play-pause` when the position did not move), then `MEDIA_PLAY_PAUSE` to resume.
  - **Why the two arrows** (Product Owner ruling, 2026-11-26, Review). Select on the scrubber toggles too (D4), so a centre press that toggles says only that focus was on Play or Pause or on the scrubber; on Rewind or Forward it would seek and toggle nothing. Right and then Left on the scrubber seek 10 s forward and 10 s back, each with a progress post of its own; from Play or Pause they move focus to Forward 10 and back and send nothing. A paused position cannot move by itself, so a paused run with one position rules the scrubber out. The arrows come after the centre presses, not before, because the row's ends trap: Right and Left before the press would also end on Play or Pause from Forward 10.
  6. **Back.** `BACK`; `stop=back` when the viewing's phase leaves `playing` and the engine stopped. The test file itself never calls `stop()` or `leave()` before it writes that word.
- **The judge**, `judgeTransportCapture(records, words, keys)`, after `judgeRecords` (the header and token on every request, no credential, no 3xx, no secret). `keys` is the runner's own list of the keys it injected, in order; the app cannot write it. The words must be as written above, and each is held by what the recorder took from the server's side of the wire (`report` on each playstate post: whole seconds of position, paused, failed, method), read in the order the posts arrived:
  - **Shape.** One `POST /Sessions/Playing`, then progress posts, then one Stopped that did not fail, each answered 2xx and naming `DirectPlay`; the media requests as `judgePlayerCapture` holds them (original file only).
  - **`wake=no-seek`.** Every progress post up to and including the first paused one has a position under 10 s. A seek sends a progress post of its own (`coordinator.ts:389-393`), and a seek from any position lands at 10 s or later, so an arrow that seeked would break the rule. A slow emulator that reaches 10 s of the film before the pause fails it; it cannot pass it wrongly.
  - **`seek=+20`, `back=-10`.** Within the first paused run, where the position cannot move by itself, the distinct positions in order are P, P+10, P+20, P+10, each within 2 s. This also proves step 1 left focus on the scrubber: with focus elsewhere the presses would seek nothing.
  - **`centre=resumed`, `centre=paused`, `centre-wake=shown`, `centre-wake=focused`.** The progress posts form exactly three paused runs with an unpaused post between each two, and the last progress post before Stopped is unpaused. `keys` holds three `MEDIA_PLAY_PAUSE` after step 1 and four `DPAD_CENTER`; six pause or resume changes on the wire from those seven presses is possible only if every play-pause press toggled, the two centre presses of step 4 toggled, the first centre press of step 5 did not, and the second did. A centre key that did nothing gives two runs; a first press of step 5 that toggled, or a chrome that never hid, leaves the last post paused; a focus holder that took no press gives a run with no resume. `keys` holds four `DPAD_CENTER`, and those toggle counts hold only for focus on Play or Pause or on the scrubber.
  - **`down=play-pause`, `centre-wake=play-pause`.** The second and the third paused run each hold one position, within 2 s, and `keys` holds `DPAD_RIGHT` then `DPAD_LEFT` after the second and after the fourth `DPAD_CENTER`. With focus on the scrubber each pair would put P+10 and then P into its run, as the first run's rule shows a seek while paused does. With the rule above, this is what says Down reached Play or Pause (step 4) and that select on the picture put focus there (step 5): item 2's second half, on the device.
  - **`stop=back`.** One Stopped post, after every progress post, not failed, at a position under 50 s, so the file's end did not stop it; `BACK` is the last entry of `keys`. Which caller stopped the player is the one thing the records cannot say: that word stays the app's own claim, and the reviewer reads the test file for a stray `stop()` or `leave()`.
  - The records and the app's lines share no clock (`docs/commands.md`, "What the files hold": a record holds no time), so no rule compares a word's place with a post's place; every rule above is over the posts' own order and the runner's `keys`.
- **The awake flag on the real window** (Product Owner ruling on the check's issue 2, 2026-11-26): after `pause=ok` (step 2) and after `centre=resumed` (step 4) the runner reads `dumpsys window` through `scripts/tv-adb.mjs`, and the judge requires the keep-screen-on flag on Octave's window while playing and its absence while paused. This replaces a reading pasted by hand into the PR. The flag's text: Android prints a window's flags by name in its attributes line (`fl=… KEEP_SCREEN_ON …`), and a view's `keepScreenOn` is carried to the window's attributes by the view root. **Unverified on the emulator**: no emulator was run for this spec, so the implementer confirms the text on the first run of milestone 4, and if the view's flag does not show there, stops and reports it instead of matching another line.
- **No host test of the judge or the key list** (Product Owner ruling, 2026-11-26). The pass of 2026-11-26 ruled on backlog line 362 that no new self-test of a wire judge is written, under the owner's rule that test tools prove themselves by running. The judge is proven by the device run and CI's `wire` job, and the reviewer reads it against this section. This stays in the task, though it is no acceptance item, for two reasons: a playback task passes only on its Jellyscale wire test (`AGENTS.md`), and it is the only proof that the remote's keys reach React on an Android TV image, which D1 rests on.
