## Goal

The player screen a viewer can drive with the remote alone:

1. Only the picture shows, in its own shape, until a key is pressed. An arrow shows the controls with focus on the scrubber; the select key shows them with focus on Play or Pause.
2. Left and Right on the scrubber move 10 s per press; the centre key and the play-pause key pause and resume; the controls hide 3 s after the last key while playing and stay while paused.
3. The top bar says what is playing. Before the first frame the title stands over its backdrop with one honest status line; "Buffering…" shows only after half a second.
4. Back stops the player first and then returns to the card the viewer came from; a player that did not stop keeps the screen and says so.
5. The screen stays awake while the picture plays and may sleep while it is paused.
6. What Kotlin draws takes its values from a native export of the design tokens that a test holds to the TypeScript source.

## Approach

### D1. The chrome is React Native views over the native video view; the video, its frame and the wake state are native

This is the hard question of the task, and the rules pull two ways (Facts, "What 'native' means").

**What a Kotlin chrome would cost.** Each line is a surface change, which `AGENTS.md` makes an architecture change with a decision record and an allowlist edit:

- The title block, the backdrop's image reference and the status line are not in the launch request, so they need view props or launch keys; `LaunchRequestReader` and its frozen tests refuse unknown keys.
- Pause, seek and Back belong to the Playback Session, in TypeScript: the coordinator reports on pause and seek, `Viewing` decides what a stop means, and T8-22's retry position is kept there. A Kotlin chrome either calls the engine behind the coordinator's back, or sends its intents to JavaScript as new events.
- Every later panel needs TypeScript data in Kotlin: the Settings panel is the Settings screen's own sections (`DESIGN.md` §7.14), the info sheet reads the plan (T8-06), Up Next reads the next episode and the auto-play setting (T8-15).
- The shared controls, `FocusFrame`, the Tabler icon font and reduced motion are React. A Kotlin chrome needs a second set, against "Build screens from the shared controls", and a third in Swift for Apple TV; decision 0003 chose React Native because it "reaches Android TV and tvOS with one UI".

**What a React chrome costs.** No surface change at all. What is lost:

- Key handling runs on the JavaScript thread: a key reaches the chrome one bridge crossing later than it would natively, and a stalled JavaScript thread means no chrome. During playback that thread does one small update a second. **Unmeasured on the Shield and the cheap box**; the wire test proves it works on the emulator, not how it feels.
- The chrome cannot show while the React tree is down. The video would keep playing; the unmount path stops it.
- Keys arrive on key up, and a held key by react-native-tvos's own 300 ms rule (Facts). T8-05 owns the hold and decides whether that rule is good enough for scrubbing.

**Decision.** The chrome is drawn in React Native over the module's view. React Native on Android draws platform views in the app's window, the same window a Kotlin chrome would use, so it is not a painted or web layer (`PRODUCT.md` pillar 2), and it is exactly "Streamyfin's shape", which decision 0003 names as the model. Native are the things only native code can do: decoding and the surface (T8-02), the picture's frame in its own shape, and the screen staying awake (D12). They cross inside Kotlin, through a slot beside `VideoSurfaceSlot`, never through JavaScript.

**What must be recorded, because the words in force say otherwise.** `ARCHITECTURE.md:69` and `T8-01` D8 say the chrome is native. So:

- Decision 0003 gains an amendment, "2026-11-26 (T8-04): what 'the player screen is native' means": the player is a native view in an Expo module with native decoding, frame and wake state; its controls are React Native views over it, as in the precedent the decision names; the module's surface does not grow for the chrome. Decision 0005 was amended in place the same way for T3-05 and T3-11.
- `ARCHITECTURE.md` line 15 and line 69 are reworded to match, and `DESIGN.md` §7.14's first sentence.
- This is a direction call. Under `decisions-owner-chat-2026-11-25.md` §1 it is the Product Owner's, provisional, and the owner can veto it. It is listed first under "For the owner's veto" and under "Open questions", because the spec check should not pass before the Product Owner has confirmed it.
- No Swift-mirrorable chrome interface is needed. The native additions are plain Kotlin a Swift engine can mirror: `PictureState`, `PictureFrame.fit`, and the listener contract of `PictureSlot`.

### D2. Layers

- `Viewing` (application layer, core) gains the transport, because it alone holds the engine and the latest snapshot. Screens still construct nothing (`DOMAINS.md` rule 4).
- The key and idle rules are pure TypeScript in `apps/tv/src/player/chrome-keys.ts`: presentation logic (`DOMAINS.md` §8 owns "focus, the D-pad, select, Back, and held keys"), with no React and no timer of its own.
- One listener reads the remote: `use-remote-keys.ts` is the only file that imports `TVEventHandler`. One listener reads Back: `use-player-back.ts`.

### D3. `Viewing` gains pause, seek, leave and what the screen shows

```ts
export type ViewingTitle = { name: string; seriesName?: string; season?: number; episode?: number };
export type ViewingState = {
  itemId?: string;
  phase: ViewingPhase;
  session: PlaybackSessionState;
  title?: ViewingTitle;        // from the item read
  backdrop?: ImageRef;         // the item's, when it has one
  opening?: "original";        // a direct-play plan is known; absent before a plan and for a conversion
  seekingTo?: number;          // seconds; the target of a seek that has not landed
};
setPaused(paused: boolean): void;
togglePaused(): void;           // from the latest snapshot's `paused`
seekBy(deltaSeconds: number): void;
leave(): Promise<void>;         // Back
```

- `setPaused`, `togglePaused` and `seekBy` do nothing unless the phase is `playing` (so nothing before the first frame, after the end or after a failure). They call the engine and return; a rejected call changes no state and its filtered reason goes to the `FailureLog`. The reports follow from the engine's own `state` events (`coordinator.ts:389-393`), so nothing here reports.
- `seekBy`: the base is `seekingTo` when a seek is pending, else the snapshot's position; the target is clamped to 0 and, when the duration is known, to the duration; `seekingTo` is published at once and cleared by the next `state` event with cause `seek`. One `engine.seek` per call. T8-05's hold builds its pending position on top of this and commits once.
- `title`, `backdrop`: published when the item read returns (`viewing.ts:173-175`).
- `opening`: the coordinator's new `onPlan` callback fires when the plan is set and before the launch; `Viewing` publishes `"original"` for `delivery: "static"`. A converted plan publishes nothing here: its line is T8-09's.
- `leave()`: the same stop as `stop()`, but its promise settles when the engine has stopped (or at once when nothing was launched), not when the reports flushed; the conclusion, the flush and `afterViewing` run on as today. When the engine did not stop it rejects with `PlayerStopError`, and the state becomes `failed` with `stop-failed`. Called again in that state, it tries the coordinator's stop once more.
- `stop()` keeps its contract, with one fix: called when no viewing is running and the last stop failed, it tries the stop again instead of returning the settled promise (`viewing.ts:135-137`).

### D4. The key rules

`chromeState(state, input)` is a reducer over `{ shown: boolean; zone: "top" | "scrubber" | "controls" | "none"; idleAt?: number }` with a `switch` on the input, and it returns the next state and at most one command (`show-scrubber`, `show-play`, `seek-back`, `seek-forward`, `toggle`, `pause`, `resume`). The screen runs the command and owns the one timer.

| Chrome | Key up | What happens |
|---|---|---|
| hidden | `up`, `down`, `left`, `right` | Show with focus on the scrubber. No seek |
| hidden | `select` (the focus holder's press) | Show with focus on Play or Pause. No toggle |
| any | `playPause` | Toggle; pausing shows the chrome with focus on Play or Pause |
| any | `play`, `pause` | Resume, pause; the same showing rule |
| shown, focus on the scrubber | `left`, `right` | `seekBy(-10)`, `seekBy(10)` |
| shown, focus on the scrubber | `select` | Toggle |
| shown, focus on a control | `select` | That control's own press: Back, back 10, Play or Pause, forward 10 |
| shown | any key, a `long…` name included | The 3 s idle timer starts again |
| shown, playing | no key for `motion.chromeIdleMs` | Hide, with a control focused or not; focus returns to the focus holder |
| shown | paused, a `hold`, loading or failed | No idle timer |

- "Focus on the scrubber" is what the scrubber's `onFocus` and `onBlur` reported last, so a `left` that follows focus onto another control never seeks.
- A held Left or Right arrives as `longLeft` or `longRight` and seeks nothing in this task; it only keeps the chrome up. T8-05 gives it its meaning.
- `rewind`, `fastForward`, `info` and `menu` do nothing yet (backlog line; `DESIGN.md` §9 names none of them for the player's transport).
- Skip and Up Next come before "show on Play or Pause" for select (`DESIGN.md` §7.14); T8-14 and T8-15 add their rows.

### D5. Focus

- **Something always holds focus**, so the root view always gets the keys (Facts, "Keys"). With the chrome hidden that is the focus holder: one full-screen focusable `Pressable` with no ring and no lift, labelled "Player controls" for TalkBack. It is the one place Octave shows no focus, which is `DESIGN.md` §7.14's "Pure video by default". While the chrome is shown the holder is not focusable.
- **Three zones**, top to bottom, as §7.14 orders them: the top bar (Back), the scrubber, the control row (back 10, Play or Pause, forward 10).
- **Moves are stated, not searched.** Every focusable of the chrome names its neighbours with `nextFocusUp`, `nextFocusDown`, `nextFocusLeft` and `nextFocusRight` (tags from `tagOf`): Back's Down is the scrubber and its other three are itself; the scrubber's Up is Back, its Down is the control row's remembered control (Play or Pause until another was focused), and its Left and Right are itself, so those keys never leave it; each control's Up is the scrubber, its Down is itself, and the row's two ends trap. "Each zone remembers its last control" is that remembered tag.
- **How focus is drawn.** Back and the three transport controls are `IconButton`s, so they get `FocusFrame`'s two-tone ring and lift (and no scale under reduced motion). The scrubber draws focus as §7.14 item 2 says: the track grows from `scrubTrackH` to `scrubTrackHActive` and the `scrubThumb` thumb appears in `text1`; it has no ring and no lift.
- **Reaching a control without a pointer.** Arrow, then Down, is Play or Pause; arrow, then Up, is Back; select from the picture is Play or Pause. Nothing in the chrome is reachable only by pointer.
- Showing moves focus with `focusView` on the target's ref after the chrome has committed; hiding moves it to the holder the same way.

### D6. The chrome's parts

- **Top bar** over `depth.scrimPlayerTop`: Back, then the title block (D7). The conversion chip is T8-09's.
- **Scrubber**: elapsed time left and remaining time right ("−1:21:40") in `typeMono`, from `seekingTo` when set, else the snapshot; the fill is `artDefaults.artAccent` (the art-derived accent waits for `artTint`, backlog line); the buffered range in `trackBuffered` from `bufferedSeconds` (D11). With no known duration it shows the elapsed time and an empty track, and Left and Right still seek. Chapters and the trickplay preview are T8-16's and the chapter task's.
- **Control row** over `depth.scrimPlayerBottom`: back 10, Play or Pause on the `playerPlayDisc` disc, forward 10. Only controls that work are drawn: Chapters, Audio & Subtitles, Settings and Info arrive with their own tasks, each adding its neighbours to D5's table.
- **Motion**: the chrome fades in and out over `durBase`, opacity only; under reduced motion it appears and goes with no fade (`DESIGN.md` §5).
- **Accessibility**: the title is the screen's one heading; Play or Pause says its action in its label ("Pause", "Play"); the scrubber is `adjustable` with the label "Seek" and its times as its value, set when it takes focus and when a seek lands, not every second (§11 rule 6).

### D7. The title block and the icons

- An episode: the series name in `typeMeta`, `text2`, over "S1 · E2 {title}" in `typeHeading`. A film: its title in `typeHeading`. The item's wording "S1 E2" is written with `DESIGN.md` §10's separator, "S1 · E2".
- Tabler names added to `glyphs`: `arrow-left` (Back), `player-play`, `player-pause`, `rewind-backward-10`, `rewind-forward-10`. Codepoints come from the bundled `tabler-icons-300.ttf` as the others did (`icon.ts:1-3`).

### D8. Loading and buffering

- **Before the first frame** (`phase === "loading"`): an opaque `void` layer over the view, so the empty surface is never seen. On it: the backdrop through the artwork slot at `backdropArt.playerOpacity` (40%) under both player scrims once `backdrop` is known, the title block once `title` is known, the status disc with one line, and Back with focus. The chrome's key rules do not run while loading: Back is the only control.
- **The line is honest about what is known.** "Loading…" until a plan is known (§10, "Player loading, before the server answers"); "Opening the original file…" once the plan is a direct play (§10, "Player loading"). A converted plan keeps "Loading…" until T8-09 gives it "Converting on server: {reason}…". The item's words "Opening the original file" are met for every file that plays today, since only originals launch (Facts).
- **At the first frame** the layer is removed and the picture shows alone; the chrome stays hidden until a key.
- **Buffering and seeking** after the first frame: when `snapshot.buffering` has been true for `motion.bufferingDelayMs`, the centred `playerStatusDisc` disc and "Buffering…" show over the picture, on a scrim-free `surface1` disc with `text1` text, and go with the first snapshot that is not buffering. A rebuffer shorter than 500 ms shows nothing.
- **The disc**: a ring that turns until T3-35 builds the Signal loader; under reduced motion a still ring with the same text (§5).
- These sit with T8-03's parts as layers of the one screen, bottom to top: view, loading layer or buffering disc, chrome, OSD notice, failure copy. A failed viewing hides the loading layer and the chrome and shows T8-03's failure copy.

### D9. Back, and a player that did not stop (backlog 359)

- The player screen registers its own `hardwareBackPress` listener while mounted. It is registered after the shell's, so it is called first (Facts), and it returns true.
- Back: `viewing.leave()`; when it resolves, `shell.close()`. The shell pops and restores the card, as today. Back does not wait for the Stopped report (`leave`, D3), so a slow server never holds the viewer on a stopped player.
- The Back control in the top bar and on the loading layer does the same.
- When `leave()` rejects, the screen stays, and T8-03's failure view shows the `stop-failed` row. The next Back calls `leave()` again and then closes whatever the answer: the row's own words are "Go back to try again". The row's button, "Back to details", is T8-17's with the other failure actions.
- A second Back while the first is still stopping is ignored.
- The unmount's `viewing.stop()` stays as the net for every other way out (the end of the file, a route reset).
- The frozen `T8-03 item 6` cases press the last-registered listener, which is now the player's; they expect the same outcome this path gives (Home, the hero focused, the engine stopped, no report). If one goes red, stop and return it to the Product Owner; do not edit it.

### D10. The failure log sink stays empty

T8-25 pointed the sink's wiring here. It is not wired: `pnpm lint:logs` forbids a value log, and where diagnostics are kept is T9-06's (`docs/specs/T8-25.md:156`). `SignedInApp` keeps `dropReason`; a backlog line carries it to T9-06.

### D11. The engine says when buffering starts and ends

`EngineCore.signal`: once `loaded`, `Buffering` emits `State(snapshot, "property")`, and so does a later `Ready`. Before `loaded` neither emits, so the frozen cases hold (Facts). The event kind and cause exist; the coordinator reports nothing for `property`. `HandleFacts.bufferedMs` fills `bufferedSeconds`. Without this the 500 ms rule would be measured from a tick that is up to a second late.

### D12. The picture's frame and the screen staying awake, natively

- `PictureState(awake, aspect)` is computed in `EngineCore` and handed to its `picture` callback whenever it changes: `awake` is "a launch is current, not ended, not failed, and play-when-ready is true"; `aspect` is the last `VideoSized` of the launch, null before one.
- `PictureSlot` (Android, beside `VideoSurfaceSlot`): the engine publishes, the view listens; the listener hears the current state at once and is called on the main thread. React is not on this path.
- `OctavePlayerView`: background `DesignTokens.VOID`; its `SurfaceView` is laid out to `PictureFrame.fit(width, height, aspect)`, the largest centred rectangle of that shape, or the whole view while the shape is unknown; `keepScreenOn = state.awake`.
- **Awake**: `View.setKeepScreenOn` is the view form of `FLAG_KEEP_SCREEN_ON` (Facts): no permission, no wake lock, cleared when the app leaves the foreground. The module's manifest keeps removing `WAKE_LOCK`. While paused the flag is off, so the TV's own screensaver timeout applies, which is the item's "may sleep while paused".
- No module function, event or prop is added, so `ModuleSurfaceTest`, `scripts/tv-module-surfaces.test.ts` and `scripts/tv-player-module.test.ts` stay green; if one reads the view's source for something this changes, stop and return it to the Product Owner.
