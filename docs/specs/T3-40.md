# T3-40: the focus ring's corners, and the side rail's rings and padding

Task: T3-40 (routine, lane `ui`, domain App Shell & Presentation). Implementer: `implementer` (TypeScript only; no native code). Source: the owner's first Shield session, `docs/specs/decisions-product-owner-2026-11-26b.md` calls 1 to 5.

## Goal

A focused control's ring keeps a 3 px gap all round, corners included. A focused rail entry looks like a row: ring and `surface3` fill, no lift, and nothing cuts its ring or lets it cover a neighbour. The rail's entries sit 16 px from all four of its edges.

## Causes, checked against the code

All values are canvas px unless marked dp. On a 960 dp, density-2 window (`px()` in `apps/tv/src/design/scale.ts`, scale 0.5), one canvas px is 0.5 dp, which is one device pixel. Every value below is a whole number of device pixels, so `PixelRatio.roundToNearestPixel` changes nothing.

**1. Ring corners.** `FocusRing` (`apps/tv/src/design/focus-frame.tsx:65-73`) places both overlays with dp outsets (`px(ringInset)`, `px(edgeInset)`), then sets `borderRadius: frameRadius + ringInset` and `frameRadius + edgeInset`, which adds the canvas values 6 and 7 as dp.

| `radiusControl` (10 → 5 dp) | Today | Correct |
|---|---|---|
| Ring outer radius | 5 + 6 = 11 dp | 5 + px(6) = 8 dp |
| Ring inner radius (outer − 1.5 dp) | 9.5 dp | 6.5 dp = control + offset |
| Edge outer radius | 5 + 7 = 12 dp | 5 + px(7) = 8.5 dp |

The gap along the corner's diagonal between a control of radius r and a ring at offset d with inner radius R is d√2 + (r − R)(√2 − 1). Today: 2.121 + (5 − 9.5) × 0.4142 = **0.26 dp**, half a device pixel, against 1.5 dp (3 device px) along the sides; that is the owner's "touches at the corners". Corrected: 2.121 − 1.5 × 0.4142 = **1.5 dp**. The error is the same 3 dp for every radius, so `radiusArt` (cards, first-screen tiles) also shows 0.26 dp today. `radiusPill` is clamped to half the box on both the control and the ring, so pills are already concentric and stay so.

A bordered control (TextField, 1 dp border) places the ring `px(ringInset) + borderWidth` from its padding box, which is `px(ringInset)` from its outer edge (T4-02 C11). Its `borderRadius` applies at that outer edge, so the ring's radius adds no `borderWidth`: 5 + 3 = 8 dp, not 9.

**2. Rail lift.** `RailItem` (`apps/tv/src/shell/side-rail.tsx:252-294`) uses `FocusFrame` without `still`, and its box has no fill and no `borderRadius`. Open, an entry is 400 − 2 × 16 = 368 wide; at `lift` 1.08 it grows 14.72 a side, and its scaled ring reaches 7 × 1.08 = 7.56 further: 22.28 past the entry against 16 of rail padding, so `overflow: "hidden"` on the rail (`:387`) cuts 6.28 off each side. Vertically the lifted reach is 2.56 + 7.56 = 10.12 against an 8 px gap: it covers 2.12 of the neighbour.

**3. Cropped rings.** Ring reach is 3 + 3 + 1 = 7. The ScrollView holding Home and the libraries (`:377`) is exactly as wide as its entries (the guide's 16 px side padding sits outside it) and has no padding, and `ReactScrollView.onDraw` clips to its padding box. So every scrolled entry's ring is cut left and right, and Home's on top too: "cropped on all sides". The guide's column has no gap between the Search group and the ScrollView, so Search's bottom edge touches Home's top: Search's ring (7, or 10.12 lifted) lies over Home. The same 0 gap separates a full scroll group from Settings.

**4. Padding.** The guide pads 54 (`space.safeY`) top and bottom and 16 (`EDGE_PAD`) at the sides (`:388`).

## Approach

**Ring.** In `FocusRing`, compute `ringOut = px(ringInset)` and `edgeOut = px(edgeInset)` once; use `outsetBy(ringOut + borderWidth)` as today and `borderRadius: frameRadius + ringOut` (edge: `frameRadius + edgeOut`). This fixes every user at once: Button (and through it Dialog, Notice, EmptyState, Toast actions), IconButton, TextField, Switch, `ServerRow`, rail entries, `FirstScreen` tiles (all through `FocusFrame`) and `MediaCard` (direct `FocusRing`). The player's scrubber draws no ring and is unaffected. Using the same dp value for placement and radius keeps the ring concentric at any density, not only density 2.

**Rail entry.** `still` on `FocusFrame` removes the lift and the press scale. Track focus in `RailItem` (wrap the `onFocus`/`onBlur` it already passes) and add `{ borderRadius: px(radii.radiusControl) }` plus `{ backgroundColor: colors.surface3 }` while focused to `contentStyle`. Collapsed entries take no focus (§7.1), so the fill only ever shows in the open rail. The bar (`top: 12`, i.e. 6 dp) stays clear of the 5 dp corner.

**Rail layout.**

| Box | Today | After |
|---|---|---|
| Guide | padding 54 vertical, 16 horizontal | padding 16 vertical, 0 horizontal |
| Search and bottom groups | gap 8 | gap 8, padding 16 horizontal |
| ScrollView content | gap 8 | gap 8, padding 16 horizontal, 8 vertical |

Room (need 7): rail edge 16 on all sides; scroll sides 16; scroll top and bottom 8; between entries 8; Search to Home 8. The ScrollView now spans the rail's full width, so its clip no longer meets a ring. Search's ring reaching 7 into the scroll's top padding is not clipped: the Search group is a sibling outside the ScrollView. Entry widths are unchanged: 368 open, 64 collapsed.

Vertical budget at 1080: 16 + 64 (Search) + scroll + 136 (Settings, 8, account) + 16 leaves an 848 viewport; the scroll content is 72n + 8 for n entries, so Home plus 10 libraries fit without scrolling.

**Overflow.** With 11 libraries or more, `ReactScrollView.requestChildFocus` → `scrollToChild` (react-native-tvos 0.88.1, `ReactScrollView.kt:546-624`) scrolls the focused Pressable flush with the viewport's edge (fading edge 0), so its ring is cut by 7 except at the very ends. Set `scrollsChildToFocus={false}` on the ScrollView and, on a scrolled entry's focus, call `scrollTo({ y, animated: !reduced })` with `y = revealOffset(...)` from `rail-reveal.ts`: the smallest change of the current offset that keeps `[top − 8, bottom + 8]` inside the viewport, clamped to `[0, content − viewport]`. Track the offset with `onScroll` and each entry's `top` with `onLayout`. Whether Android still moves focus into an off-screen entry with `scrollsChildToFocus` off is **unverified** (it goes through `ScrollView.arrowScroll`); the overflow capture on the emulator proves it, and if it fails, see question Q1.

## Spec check

Checked in a fresh context against `pnpm task show T3-40` (8 items; the table has 8, in order), `AGENTS.md`, `DESIGN.md` §§ 6, 7.1, 9, 12, `docs/specs/decisions-product-owner-2026-11-26b.md`, `apps/tv/src/design/focus-frame.tsx`, `apps/tv/src/shell/side-rail.tsx`, the frozen manifests and react-native-tvos 0.88.1-0 as installed.

**Geometry: verified.** At scale 0.5: ring outset `px(6)` = 3 dp, edge `px(7)` = 3.5 dp, ring width 1.5 dp, `radiusControl` 5 dp. Today the code adds the canvas 6 and 7 to dp radii (`focus-frame.tsx:69-70`): ring 11/9.5 dp, edge 12 dp. Diagonal gap g√2 + (r − R)(√2 − 1) with g = 1.5: today 0.26 dp, corrected (R = 6.5) 1.5 dp, equal to the side gap. Edge inner radius 8.5 − 0.5 = 8 = ring outer, so the two-tone ring stays concentric. TextField: Android's `borderRadius` is at the outer edge and the ring sits `px(ringInset)` from it, so no `borderWidth` in the radius is right. Rail: 368 × 0.04 = 14.72 a side, + 7.56 = 22.28 vs 16; vertical 2.56 + 7.56 = 10.12 vs 8; after: 16/16/8/8 all ≥ 7. Budget 1080 − 16 − 64 − 136 − 16 = 848; content 72n + 8, so n = 11 (Home + 10) fits and Home + 11 overflows. The bar (top 6 dp) clears the 5 dp corner. The new item-1 test fails today (11 − 1.5 − 5 = 4.5 ≠ 1.5).

**Frozen tests: verified.** `side-rail.test.tsx` and `app-shell.test.tsx` are frozen (T3-09); no frozen file reads a `borderRadius`, a rail entry's transform, the rail's padding or its ScrollView (grep over every file in `docs/specs/*.tests.json`). `focus-motion.test.tsx` reads only the ring's colour and width; `controls-states.test.tsx`'s lift cases do not include a rail entry. The non-frozen `rail-motion.test.tsx` and `app-shell-review.test.tsx` read the width and focus wiring only.

**`scrollsChildToFocus={false}`: reachability verified from source.** The prop exists (`ScrollView.d.ts:342`, Android only) and does exactly two things in `ReactScrollView.kt`: `requestChildFocus` (`:546-558`) skips `scrollToChild`, and `requestChildRectangleOnScreen` (`:566-572`) returns false. It does not touch `arrowScroll`. D-pad Up and Down inside the list reach `ReactScrollView.arrowScroll` (`:513-537`) → AOSP `ScrollView.arrowScroll`, which finds the next focusable, computes `computeScrollDeltaToGetChildRectOnScreen`, scrolls with `doScrollY`, and only then calls `requestFocus` (AOSP `ScrollView.java` `arrowScroll`, checked against the `aosp-mirror/platform_frameworks_base` main branch). The RN override of that delta returns 0 only when `scrollEnabled` is false or while `blockScrollDelta` is set inside `requestChildFocusWithoutScroll`, so an adjacent off-screen entry (72 px away, well inside `getMaxScrollAmount()` = half the viewport) is still scrolled flush into view and focused. Focus arriving from outside the list (Up from Settings, Down from Search, the rail opening on a deep library through the registered views) gets no native scroll at all; there the JS reveal is the only thing that brings the entry into view, which the planned 14-library test and the `rail-overflow-last` capture cover. No entry becomes unreachable. The spec's "unverified" can be replaced by this.

Verdict: **Approved**

Issues (none blocks):

1. Medium. Two scroll animations race on an in-list D-pad move with overflow. `arrowScroll` starts the native `OverScroller` (`smoothScrollBy`, flush with the edge), and the JS `scrollTo({ animated: true })` goes through `reactSmoothScrollTo` → `ReactScrollViewHelper.smoothScrollTo` (`ReactScrollViewHelper.kt:334-362`), a separate fling animator that does not abort the scroller. Both call `scrollTo` each frame; if the native one finishes last the entry ends flush and its ring is cut, failing item 3 for 11+ libraries. Fix in the spec: set `scrollAnimationEnabled={false}` on the ScrollView (TV only: `computeScroll` then finishes the native scroll at once, `:576-586`, and `reactSmoothScrollTo` becomes an instant `scrollTo`, `:1223-1230`), and call the reveal with `animated: false`, as rows already do (T3-08's `scrollToOffset(..., animated: false)`). Name the `onScroll`-staleness: the reveal is computed from the offset JS last saw, which is right as long as the JS scroll lands last.
2. Low. Line citations in "Causes" point at a different revision: `RailItem` is `side-rail.tsx:55-97`, the ScrollView `:180`, `rail` style `:190`, guide `:191`.
3. Low. With overflow and a scroll left mid-list, Search's ring (a sibling drawn before the ScrollView) is drawn under scrolled content, and Settings' ring over a partly visible entry above it, when the rail opens on Search or Settings without passing through Home or the last library. Reset the offset to 0 when Search takes focus and to the end when Settings does (or accept and log it under Q1's backlog line).
4. Low. The overflow capture focuses the last library through the registered views, the from-outside path only. Add one capture after D-pad Down presses within the list on your own emulator, the path issue 1 concerns.
