## Goal

1. The player module's `initialize` answers what this device can play, read from the platform's codec list through Media3: each video decoder per codec and profile with whether it is hardware, the audio decoders, the HDR types the display supports and the passthrough formats. Any failure answers "cannot tell".
2. The app hands that answer to the gateway, so the core's source decision (T2-07) direct-plays what the device decodes with one PlaybackInfo request, and sends the one forced-conversion request for what it does not.
3. The DeviceProfile stays the same on every device, and the app cannot be composed without a capability source (the core's `"full"` default never reaches the app).
4. An emulator wire test shows both paths against the pinned Jellyscale and Jellyfin 12.4, judging the requests on the wire.

## Facts this spec rests on

- **The port** (`packages/core/src/domain/player-engine.ts:76-101`): `VideoDecoder { codec, hardware, profile?, maxBitDepth?, maxWidth?, maxHeight? }`; `PlayerCapabilities` is `{ probe: "complete", videoDecoders, audioDecoders, hdr, passthrough }` or `{ probe: "failed" }`. The comment on `profile` already states the rule this task implements: matching is exact, so a probe lists one entry per supported profile ("a High decoder also lists Main and Constrained Baseline") or omits the profile when the decoder decodes any. Vocabularies: `VIDEO_CODECS` (h264, hevc, av1, vp9, vp8, mpeg2video, mpeg4, vc1), `AUDIO_CODECS`, `HDR_TYPES` (hdr10, hdr10-plus, hlg, dolby-vision), `PASSTHROUGH_FORMATS` (ac3, eac3, eac3-joc, dts, dts-hd, truehd).
- **The decision** (`packages/core/src/domain/device-capabilities.ts`): `devicePlayability` answers false for a failed probe; a video is playable when some decoder entry has the source's codec, the same profile (case-insensitive, trimmed) or no profile, and the source's bit depth, width and height within any limit the entry states. A stated limit needs the source to give a value (`within`). A source with no `Profile` is refused by an entry that states one: frozen by T2-07 (`device-capabilities.test.ts:51-55`). Hardware and HDR are not read by the decision.

So the probe must never emit a profile outside the pattern (D5).

## Approach

### The probe (milestone 1)

**Reading the platform** (`DevicePlatformReader.read(context: Context?): PlatformReport?`; null when `context` is null):

- Video: for each codec, `MediaCodecUtil.getDecoderInfos(mime, /* secure */ false, /* tunneling */ false)`. MIME per codec (`PlatformNames`): h264 `video/avc`, hevc `video/hevc`, av1 `video/av01`, vp9 `video/x-vnd.on2.vp9`, vp8 `video/x-vnd.on2.vp8`, mpeg2video `video/mpeg2`, mpeg4 `video/mp4v-es`, vc1 `video/wvc1`. For each Media3 `MediaCodecInfo`: `hardware = hardwareAccelerated && !softwareOnly` (as `DecoderFacts` reads them; below API 29 these are Media3's name-based guess), profiles from `getProfileLevels()` mapped through `PlatformNames` (a decoder of a codec with a profile table that reports profile levels none of which has a name, say only `High422`, is left out of the report, so an empty profile list always means the platform reported none), `maxWidth`/`maxHeight` from `capabilities?.videoCapabilities?.supportedWidths?.upper` and `supportedHeights?.upper` (absent when not given). Media3's list is used rather than raw `MediaCodecList` so the probe reports the decoders this engine will actually try (Media3 filters its known-broken ones) (D1).
- Audio: a codec is listed when `getDecoderInfos` returns any decoder for its MIME: aac `audio/mp4a-latm`, mp3 `audio/mpeg`, ac3 `audio/ac3`, eac3 `audio/eac3`, truehd `audio/true-hd`, dts `audio/vnd.dts`, flac `audio/flac`, alac `audio/alac`, opus `audio/opus`, vorbis `audio/vorbis`. `pcm_s16le` and `pcm_s24le` are listed always, because Media3's audio sink takes linear PCM without a codec: Media3 1.11.1's `DefaultAudioSink.getFormatSupport` (lines 687-705) turns any linear PCM encoding, 24-bit included, into 16-bit or float through its audio processors (verified; cited in `PlatformNames.kt`).
- HDR: the default display (`DisplayManager.getDisplay(Display.DEFAULT_DISPLAY)`); on API 34 and later `display.mode.supportedHdrTypes`, earlier `display.hdrCapabilities?.supportedHdrTypes`. Map `HDR_TYPE_HDR10` to `hdr10`, `HDR_TYPE_HDR10_PLUS` to `hdr10-plus`, `HDR_TYPE_HLG` to `hlg`, `HDR_TYPE_DOLBY_VISION` to `dolby-vision`; others dropped.
- Passthrough: `AudioCapabilities.getCapabilities(context, AudioAttributes.DEFAULT, null, emptyList())`, the current four-argument overload of Media3 1.11.1 (`AudioCapabilities.java` lines 145-151; the three-argument one is deprecated at line 127; verified, cited in `DevicePlatformReader.kt`), `supportsEncoding` for `C.ENCODING_AC3` → `ac3`, `E_AC3` → `eac3`, `E_AC3_JOC` → `eac3-joc`, `DTS` → `dts`, `DTS_HD` → `dts-hd`, `DOLBY_TRUEHD` → `truehd`.

**Profile names** (`PlatformNames`, from `MediaCodecInfo.CodecProfileLevel`; the names are Jellyfin's `MediaStream.Profile`, which is ffprobe's profile name). A constant not listed maps to nothing (that profile is not reported):

| Codec | Platform constant → reported name (bit depth) |
|---|---|
| h264 | `AVCProfileConstrainedBaseline` → Constrained Baseline; `AVCProfileBaseline` → Baseline; `AVCProfileMain` → Main; `AVCProfileExtended` → Extended; `AVCProfileHigh` → High; `AVCProfileHigh10` → High 10. Not mapped: `ConstrainedHigh` (ffprobe never reports it), `High422`, `High444` (their names hold `:`; D5) |
| hevc | `HEVCProfileMain` → Main; `HEVCProfileMain10`, `Main10HDR10`, `Main10HDR10Plus` → Main 10; `HEVCProfileMainStill` → Main Still Picture |
| av1 | `AV1ProfileMain8` → Main (8); `AV1ProfileMain10`, `Main10HDR10`, `Main10HDR10Plus` → Main (10) |
| vp9 | `VP9Profile0` → Profile 0; `VP9Profile1` → Profile 1; `VP9Profile2`, `2HDR`, `2HDR10Plus` → Profile 2 (10); `VP9Profile3`, `3HDR`, `3HDR10Plus` → Profile 3 (10) |
| mpeg2video | `MPEG2ProfileSimple` → Simple; `Main` → Main; `High` → High; `SNR` → SNR Scalable; `Spatial` → Spatially Scalable. Not mapped: `422` (`:`) |
| mpeg4 | `MPEG4ProfileSimple` → Simple Profile; `AdvancedSimple` → Advanced Simple Profile; `Main` → Main Profile; `Core` → Core Profile |
| vp8, vc1 | none: one entry with no profile (D6) |

The spellings are libavcodec's profile names (`libavcodec/profiles.c`). Verified at FFmpeg `n7.1.3` and `n8.1.3`, the bases of the jellyfin-ffmpeg builds in the fixture images (`ffmpeg -version` reads `7.1.3-Jellyfin` in `jellyfin/jellyfin:10.11.7` and `8.1.3-Jellyfin` in `jellyfin/jellyfin:12.4.20261026-211555`): `ff_h264_profiles` lines 72-87, `ff_hevc_profiles` 97-103, `ff_mpeg2_video_profiles` 116-122, `ff_mpeg4_video_profiles` 127-143, `ff_vp9_profiles` 155-159, `ff_av1_profiles` 163-166, the same lines in both tags; the recorded fixtures hold High, Main and Main 10. Cited in `PlatformNames.kt`. The Android constants are named, not written as numbers, so the compiler takes them from the SDK's `CodecProfileLevel` and `HdrCapabilities` and Media3's `C`, and `PlatformNamesTest` pins each by name.

**Building the answer** (`CapabilityMap.capabilities(report)`, plain Kotlin):

1. Drop a codec outside the port's vocabulary (the Kotlin list mirrors `VIDEO_CODECS`, `AUDIO_CODECS`, `HDR_TYPES`, `PASSTHROUGH_FORMATS`; the vectors include an unknown name to pin it).
2. Expand each reported profile by the implication table (D4): h264 High 10 ⇒ High, Main, Constrained Baseline; High ⇒ Main, Constrained Baseline; Main ⇒ Constrained Baseline; Baseline ⇒ Constrained Baseline. hevc Main 10 ⇒ Main. mpeg2video High ⇒ Main, Simple; Main ⇒ Simple. mpeg4 Advanced Simple Profile ⇒ Simple Profile. av1 and vp9: none (the bit depth carries it).
3. One `VideoDecoder` per (decoder, profile): `{ codec, hardware, profile, maxBitDepth?, maxWidth?, maxHeight? }`. `maxBitDepth` is set only for av1 and vp9 (8 or 10 from the table); h264 and hevc state none, since their profile fixes the depth and a stated limit refuses a source that gives no `BitDepth`.
4. vp8 and vc1 decoders get one entry with no profile, whatever they report. A decoder of any other codec whose profile list is empty (the platform reported no profile level) gets an entry with no profile only where Media3 would play any profile on it, and no entry otherwise (spec check issue 1, settled against Media3 1.11.1): `MediaCodecInfo.isCodecProfileAndLevelSupported` answers true when the source's profile is unknown (line 346, "If we don't know any better") and otherwise looks for the profile in the decoder's levels, so an empty list refuses it (the loop at line 399 finds nothing; line 406 logs no support). `CodecSpecificDataUtil.getMediaCodecProfileAndLevel` parses a profile only for `avc1`/`avc2`, `vp09`, `hev1`/`hvc1` and `av01` among the video codecs here (lines 876-910). So a silent **h264, hevc, av1 or vp9** decoder gets **no entry**, and a silent **mpeg2video or mpeg4** decoder gets **one entry with no profile**. A decoder whose profiles all fail the pattern (for example only `High 4:2:2`) gets no entry. Pinned by the new `CapabilityMapEmptyProfilesTest.kt`.
5. Every emitted profile must match `^[A-Za-z0-9 .+-]{1,32}$`; one that does not is dropped with its entry, never emitted (D5).
6. Dedupe on (codec, hardware, profile, maxBitDepth, maxWidth, maxHeight), keep first-seen order. No video decoder entry left after steps 1 to 5 ⇒ `Capabilities.Failed` (D7). The rule is judged on the mapped list, not on the platform report (spec check issue 2): a report whose only decoders are an unknown codec or a `High 4:2:2`-only AVC decoder is "cannot tell" (`CapabilityMapTest.report_whose_decoders_all_map_to_nothing_is_failed`), and the vectors' `High 4:2:2` and unknown-codec cases carry a second, mapped decoder so their answer is complete with the entry missing.

**Running it** (`CapabilityProbe.probe()`): `try { read()?.let(CapabilityMap::capabilities) ?: Failed } catch (_: Throwable) { Failed }`. `Media3Engine` holds `CapabilityProbe { DevicePlatformReader.read(if (closed()) null else context()) }` and `capabilities()` returns `probe.probe()`. It runs on the module's command thread, not through `MainThreadGate` (the existing T8-02 source test expects that), probes afresh on every `initialize` (Media3 caches the codec lists per process; the display and the audio route can change), and logs nothing.

### The app (milestone 2)

```ts
export type CapabilityProbe = () => Promise<PlayerCapabilities>;
export function createAppGatewayFactory(host: GatewayHost, probe: CapabilityProbe): GatewayFactory;
```

- Throws `new Error("No device capability source.")` synchronously when `probe` is not a function (item 9). `hostGateway` builds its factory on first use, so the first call fails, before any request.
- Each call: `let answer; try { answer = readCapabilities(await probe()); } catch { answer = { probe: "failed" }; }`, then `createGatewayFactory(host)(serverUrl, { ...stores, deviceCapabilities: { get: () => answer } })`. The app's own source wins over a caller's store. `readCapabilities` turns anything that is not a capability list, `"full"` included, into "cannot tell" (item 9's second half, item 5).
- `createCapabilityProbe(engine)` returns `async () => { try { return await engine().initialize(); } catch { return { probe: "failed" }; } }`, so a module that cannot load (tvOS) is "cannot tell".
- One probe per gateway built (each server probe, sign-in or relaunch), not per negotiation (D8).

### The wire test (milestone 3)

`player-capabilities.ts`, with the app's gateway (the probe-backed factory):

1. Sign in (`signIn`). Open the rig (`PlayerRig.open`, which calls `initialize`); from that answer write `probe=complete|failed`, `h264main=listed|absent` (an h264 entry with profile `Main` or none) and `hevcmain=listed|absent` (an hevc entry with profile `Main` or none). The rig's `initialize` and the gateway's probe are separate calls; both reach the same native probe.
2. `Synthetic H264` (exact title `Synthetic H264` or `Synthetic H264 (2024)`, kind Movie; the no-decoder sample likewise, Product Owner ruling 2026-11-23, Implement): `planForSample`, the test's own lookup; `h264plan=original|transcode|direct-stream|<plan-code>`; when original, `rig.play` and `h264=first-frame|<code>|timeout`, then stop.
3. `Synthetic No Decoder`: its own catch around `createPlaybackPlan`, since `player-run.ts`'s `planFor` turns every error into `plan-<code>` and `codeOf` does not read `PlaybackRefusedError.reason` (spec check issue 4); a refusal (`PlaybackRefusedError`) gives `nodecoder=refused reason=<reason>`; another error `nodecoder=plan-<code>`; an hls plan gives `nodecoder=transcode|direct-stream client=<clientConversionReason or none>`; a static plan `nodecoder=original`. Not launched (T8-08; Product Owner ruling on item 6): the test never hands the converted plan to the rig, and the run's judge fails any fetch of the converted plan (`judgePlayerCapture` through `PLAYS`).
4. `outcome=ok` and the words; fixed words only.

The recorder adds, for every `POST …/PlaybackInfo`, `playbackInfo: { body: Flags, query: Flags, profile: string | null }` where `Flags` holds the six `PLAYBACK_INFO_FLAGS` names, each `true`, `false` or `null` (body: the JSON boolean; query: exactly one parameter of that name whose value is `true` or `false` in any case, else `null`), and `profile` is the SHA-256 hex of the canonical JSON (keys sorted at every level) of the body's `DeviceProfile` with `MaxStreamingBitrate` removed, or `null`. No other value of the body or query is kept.

`judgeCapabilityCapture(records)` (and the pair's words), per pair:

- PlaybackInfo records in order: exactly one for the H.264 item, then exactly two for the no-decoder item (items are told apart by their path's item id; anything else fails).
- The first request of each item: every flag `true` in body and query except `AutoOpenLiveStream` `false`.
- The second no-decoder request: `EnableDirectPlay` and `AllowVideoStreamCopy` `false` in body **and** query; `AllowAudioStreamCopy` `true` (the sample's AAC plays on the emulator); every other flag as on the first.
- Every PlaybackInfo carries `profile === OCTAVE_PROFILE_DIGEST`.
- Words: `probe=complete`, `h264main=listed`, `hevcmain=listed` when `pair.decoders.hevc.type` is true, `h264plan=original`, `h264=first-frame`, and the no-decoder words from `CAPABILITY_EXPECTATIONS[target]`: `jellyscale` → `nodecoder=refused reason=device-cannot-play`; `jellyfin-12` → `nodecoder=transcode client=DeviceCannotPlay`.
- Header, token, credential names and Host are `judgeRecords`'s, and the play's media requests `judgePlayerCapture`'s (through `PLAYS`).

### Decision log

- **D1. Media3's decoder list, not raw `MediaCodecList`.** The probe should say what this engine will play; Media3 skips decoders it knows are broken and resolves aliases. T8-02's `DecoderFacts` reads the same `MediaCodecInfo`.
- **D2. A new app factory instead of making `createGatewayFactory` reject.** The frozen T4-09 test builds gateways with `createGatewayFactory` and no capability source. `createAppGatewayFactory` is the one the app composes; a source scan holds every app caller to it.
- **D3. The T8-02 player wire tests keep stating "full".** `player-samples`' frozen judge needs the no-decoder sample to reach the engine as a static plan (`decoder-unavailable`), and the mock's H.264 stream states no profile, so a probe-backed gateway would convert or refuse both. Those three tests check the engine behind a host that states no limit (the engine's own refusal is the second guard, T8-02 D5); `gatewayStatingFull` exists only in `e2e/wire`, and the scan of item 9 pins that.
- **D4. Expand profiles by an explicit implication table.** Hardware AVC decoders often report only High; exact matching (frozen) would convert every Main file. The table lists only supersets that hold by the codec standards (High ⊇ Main ⊇ Constrained Baseline; HEVC Main 10 ⊇ Main; MPEG-2 High ⊇ Main ⊇ Simple; MPEG-4 ASP ⊇ SP). Baseline (with FMO/ASO) is not implied by Main or High.
- **D5. Never emit a profile the reader would widen.** `readCapabilities` keeps a decoder whose profile fails its pattern and drops the profile (frozen), which would make it "any profile". Profiles with `:` (`High 4:2:2`, `High 4:4:4 Predictive`, MPEG-2 `4:2:2`) are not emitted at all, so such sources convert. The vectors' TypeScript test asserts `readCapabilities(case.capabilities)` equals `case.capabilities` for every case.
- **D6. A source that states no profile.** Strict, as frozen in T2-07: it converts when every decoder entry for its codec states a profile (h264, hevc, av1, vp9, mpeg2video, mpeg4 on most devices), and plays when an entry states none (vp8, vc1, or an mpeg2video or mpeg4 decoder that reports no profile levels; a silent h264, hevc, av1 or vp9 decoder gets no entry, step 4). No recorded stream lacks a profile; the forced conversion is visible with its reason, so the cost is a shown conversion, not a failed play.
- **D7. "Cannot tell" covers a throw, no context, a destroyed module, and a list with no video decoder.** Android's compatibility definition requires an AVC decoder, so an empty list means the read failed. Every such case is `Failed`, which the core treats as nothing playable.
- **D8. One probe per gateway.** `DeviceCapabilitySource.get` is synchronous, and a probe per negotiation would add a native round trip to every play. A receiver or display change is seen at the next sign-in or relaunch (backlog line).
