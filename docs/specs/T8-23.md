## Goal

1. Every conversion answer the core would hand to the engine is judged against the device first: a conversion on the first answer, a disc's forced fallback, and the answer to the forced conversion.
2. An answer that may copy a stream the device cannot play costs the one forced-conversion request; an answer whose encode target the device cannot decode ends in the typed refusal `device-cannot-play`. Neither stream reaches the engine.
3. The source decision reads level, frame rate and audio channel count beside codec, profile, bit depth and size, when the device reports them.
4. The DeviceProfile stays the same on every device, and no new kind of request is added.

## The rules

### What a conversion can deliver

Read from the rebuilt master URL (`decideConversion`'s result) and the source:

- **Encode target, video:** the first codec of the URL's `VideoCodec` list. Its size and frame rate are the source's first video stream's, lowered by the URL's `MaxWidth`, `MaxHeight` and `MaxFramerate` when present; a value neither gives is not judged. Its profile, bit depth and level are not known and are not judged.
- **Encode target, audio:** the first codec of the URL's `AudioCodec` list, judged by decoder or passthrough. Its channel count is not known and is not judged (Risks).
- **Copied video** (D5, Product Owner ruling of 2026-11-23): possible only when the URL does not carry `AllowVideoStreamCopy=false` **and** the URL's `VideoCodec` list (read with the `codecList` that `copiesEverything` uses) holds the source's first video stream's codec. A stream that states no codec counts as held (cannot tell is never can play). A possible copy is judged exactly as rule 3 judges the stream.
- **`VideoCodec=copy`** (exactly `copy`, any case): the pinned Jellyscale's way of saying it copies the video. The copy is possible and judged as the source's first video stream, and there is no video encode target to judge.
- **Copied audio:** possible only when the URL does not carry `AllowAudioStreamCopy=false` and the `AudioCodec` list holds the stream's codec (a stream with no codec counts as held). The stream is the one the URL's `AudioStreamIndex` names, else the request's index, else the source's default, else the first audio stream. It is judged with its channel count.
- A copy that is not possible leaves only the target to judge: a DTS or TrueHD track outside the list on a device without that decoder is encoded by the server and costs no request.
- **A source with no probed streams** (a Blu-ray folder): the copy can be any codec the URL lists, so the device needs a decoder (for audio, a decoder or passthrough) for every codec in the `VideoCodec` and `AudioCodec` lists. Limits are not judged: there is no value to compare (D4).
- An audio-only conversion (`mediaKind: "audio"`) has no video part, and a source with no audio stream has no audio part. A missing or empty list is "cannot tell" and counts as not playable.

### The verdict (`judgeConversion`)

| Capabilities | Verdict |
|---|---|
| `"full"` | Accept. Nothing is judged; requests are exactly today's |
| `{ probe: "failed" }` | Targets are not judged. A possible copy counts as not playable (cannot tell is never can play). So an answer that may copy needs the forced conversion, and the forced answer, which copies nothing that was turned off, is accepted: it is the last stream Octave can ask for, and the engine's own refusal stays the guard |
| `{ probe: "complete" }` | 1. A target the device cannot decode: **Refuse** `device-cannot-play`, detail `conversion target not playable`, with no further request (asking again cannot change the target). 2. Else a possible copy the device cannot play: **needs the forced conversion** (`cannotPlay` names video, audio or both). 3. Else accept |

- On a first answer, a plain answer or a disc's fallback answer, "needs the forced conversion" becomes the existing `force-conversion` decision, and the gateway's existing branch sends the one forced request: `EnableDirectPlay: false`, `AllowVideoStreamCopy: false`, and `AllowAudioStreamCopy: false` when `cannotPlay.audio`, everything else as on the first request (T2-07 rule 5, unchanged).
- On the forced answer, `decideForcedConversion` runs first and unchanged (copy shown off, else `stream copy not turned off`). Then `judgeConversion` runs once more: an undecodable target refuses as above, and a copy that is still possible and not playable refuses `device-cannot-play`, detail `copied stream not playable`. There is no second forced request.
- A plan built after the forced request carries `clientConversionReason: "DeviceCannotPlay"` and `playOriginalAvailable: false`, as today. A conversion accepted as the server built it carries no client reason.

### The source decision reads more (acceptance 4)

The port gains three optional limits. Absent means the device states no limit, so every existing list and test value behaves as today.

| Field | Where | Compared with | Missing source value |
|---|---|---|---|
| `maxLevel?: number` | `VideoDecoder` | `MediaStream.Level`, in Jellyfin's scale for the codec: h264 ten times the level (4.1 is `41`), hevc thirty times (`general_level_idc`; 3.1 is `93`), av1 `seq_level_idx`. Only for h264, hevc and av1, the three scales a recorded stream shows | **Not judged.** Jellyscale states no `Level` (recorded), Media3 itself assumes support when it does not know (`MediaCodecInfo.isCodecProfileAndLevelSupported`, cited in `docs/specs/T8-07.md`), and size and frame rate are judged on their own |
| `maxFrameRate?: number` | `VideoDecoder` | `MediaStream.ReferenceFrameRate`, with the 0.05 slack `copiesEverything` already uses | Not playable (strict, as width and height) |
| `maxAudioChannels?: Partial<Record<AudioCodec, number>>` | the complete capability answer | `MediaStream.Channels` of the judged audio stream, for a codec played by a decoder. Passthrough is not limited by it: the receiver decodes | Not playable when a limit is stated for that codec |

`readCapabilities` copies a valid value. A decoder whose `maxLevel` or `maxFrameRate` is present and invalid, or whose `maxLevel` is stated for a codec outside h264, hevc and av1, is dropped; an audio codec whose channel limit is present and invalid is dropped from `audioDecoders`. A bad limit narrows the list and never widens it (unlike the frozen profile rule, `docs/specs/T8-07.md` D5).

**Which audio tracks are judged.** Only the chosen one: the track the request names, else the source's default, else the first. Tracks beside it are not judged, for three reasons: the engine decodes one audio track at a time, so another track costs nothing until it is picked; many original files carry a lossless track beside a compatible one, and judging every track would convert files the device plays as stored (I1); and a pick already comes back through negotiation with its index, where it is the judged track. Likewise only the first video stream is judged. A switch made inside the engine during a direct play does not come back through negotiation; a backlog line asks that the track menu (T8-10, T8-12) call `sourcePlayability` with the picked index before it switches.

### Requests

- No new kind of request. The forced conversion is sent at most once per negotiation, as before.
- New paths to it: a first-answer conversion (two requests), and a disc's fallback answer (three: first, disc fallback, forced conversion). With an audio pick whose first answer is refused and whose plain answer is a disc, four at most. `ARCHITECTURE.md` §3 says "at most three" today; the edit states the new bound.
- The DeviceProfile is not read or changed by any rule.

## Approach

```ts
// domain/device-capabilities.ts
export interface EncodeTarget {
  video?: { codec: string; width?: number; height?: number; frameRate?: number };
  audio?: { codec: string };
}
export function deviceDecodesTarget(target: EncodeTarget, capabilities: DeviceCapabilities): Playability;

// jellyfin/conversion-device-check.ts
export function judgeConversion(
  decision: Extract<SourceDecision, { kind: "convert" }>,
  context: SourceContext,
  options: { forced: boolean },
): SourceDecision;
```

1. Milestone 1 first: record, read the recordings, then write the failing tests. Stop and report if a recording names a target other than the first codec of the URL's list.
2. Domain: the port fields, the reader, the comparisons, `deviceDecodesTarget`. A limit is applied to a target only when the URL or the source gives the value.
3. `judgeConversion`: read the rebuilt URL's parameters with the same case-insensitive lookup `source-acceptance.ts` uses (export `param` and `codecList` rather than copy them); build the target and the copy candidates; return the verdict in the order of the table (target first, then copy).
4. Gateway: the judgement sits after the pick and disc logic and before the rule 5 branch, so every path that ends in `convert` passes through it once, and the forced answer once more with `forced: true`.
5. Docs and backlog.

### Decision log

- **D1. The target is the first codec of the URL's list.** Both Jellyfin versions do exactly that in source, and every recorded URL lists `h264` first. Milestone 1 turns the source reading into a recording.
- **D2. A target the device cannot decode refuses at once.** The forced request cannot change the target (the profile is the same on every device, item 5), so asking would spend a request to learn nothing.
- **D3. A failed probe does not judge targets.** Refusing would stop every play on a device whose probe threw. The frozen T2-07 test "converts when the probe failed" pins the same answer.
- **D4. An unprobed source is judged on the URL's codec lists.** The frozen T2-07 item 4 test requires that a list holding every listed codec sends no extra request for the Blu-ray folder, and strictness on unknowns (T2-07 D4) requires that a list lacking one does. Cost: a device without, say, an AV1 or E-AC-3 decoder re-encodes every unprobed disc folder.
- **D5. A copy is possible only when it is not turned off and the URL's list holds the source codec** (Product Owner ruling of 2026-11-23, which replaced "possible unless the URL says it is off"). A stream with no codec counts as held. `VideoCodec=copy` (any case) is a possible video copy with no video target. All three servers refuse a copy outside the list in source, and Jellyfin's recordings show none (`encode-target-no-decoder.json`). A server that keeps the video and re-encodes only an audio track outside the list is the better stream, and costs no request. Narrowing further by the URL's bitrate, size or frame-rate limits is not done. Tests: `conversion-device-check.test.ts` ("what a copy can be"; "the pinned Jellyscale's two VideoCodec forms") and the negotiation tests "sends no forced request for the no-decoder sample" and "sends the forced request when the answer says VideoCodec=copy".
- **D6. A missing `Level` is not judged; a missing frame rate or channel count is.** See the table. Strictness on a missing level would refuse every file on Jellyscale the day a device reports levels.
- **D7. The device does not report the new limits yet.** This task is core lane and its `verify` runs no native test. The Kotlin probe is unchanged, so on a device the three rules read nothing until a native task fills the fields (backlog line). T2-07 and T8-07 were split the same way.
- **D8. No new refusal reason and no new sentence.** The new refusals use `device-cannot-play` and the owner's confirmed copy (open question 1, settled as option A).
- **D9. Tracks beside the chosen one are not judged.** See "Which audio tracks are judged".
- **D10. The judgement runs after `selectSource`** (check note 3). With no requested version, a first-ranked conversion whose target the device cannot decode refuses even when another version of the item would play. Known limit; a backlog line asks that the ranking judge each version's conversion before it picks.
- **D11. The forced request's audio flag reads `cannotPlay.audio`.** For rule 3 it is the same value as before; for a judged conversion it is the possible copy the device cannot play, so an audio track outside the list does not turn the audio copy off.

## Invariants and hard rules touched
