# T1-16: Let the workflow's Product Owner step answer technical and placement questions and log every ruling

- Domain: Process (`DOMAINS.md` §Process and Workflow: the rule files, `tasks/`, `.claude/`, CI, and the checks in `scripts/`).
- Model: opus (spec). Implementer: **`implementer`**. The work is workflow JavaScript, one new script, one new test file, agent files and `WORKFLOW.md`. Nothing under `modules/`, `apps/tv/android/` or the PlayerEngine port changes, so `touchesNative` is false.
- Depends on: T1-15. It is done on origin/main: `node scripts/task.mjs show T1-15` gives status `done`, passes `true`, commit 6f7853da.
- Risk: routine. This is not a playback task, so no Jellyscale wire test applies. It changes no server call, token, network path or native code.

## Goal

`AGENTS.md` (Tasks) already says: "Send technical, placement, dependency, and scope questions to the Product Owner; send only look, wording, and direction questions to the owner." The task workflow (`.claude/workflows/task.js`) does not do this yet. Its inline Product Owner step is reached only through `frozenTestProblems` (`task.js:411-431`), so any other question stops the run for the coordinator or gets asked again, and the step's rulings never reach `tasks/product-owner-log.md`. T3-19 needed five rulings on one rule.

After this task:

1. Check and every guarded work step (Implement, follow-ups, CI fix) can return questions for the Product Owner in a field of their own, `productOwnerQuestions`. The inline step rules on technical, placement, dependency and scope questions, and the run goes on with the ruling. A look, wording or direction question parks the task for the owner.
2. A work step ends at its first question. It is not retried or escalated, and it is resumed with the ruling.
3. Every ruling, frozen-test rulings included, is a dated, committed section of `tasks/product-owner-log.md` on the task branch. A relayed script checks this mechanically, and a missing entry stops the run.
4. A second return on the same rule makes the step probe the fact and quote what it found. A third return blocks the task.

## Approach

1. **Pure parts first.** Add `ask` to `decideStep`, the RULING block, and `decideRulingLog`. Run `pnpm test:workflow` to confirm the frozen T1-12, T1-14 and T1-15 assertions still pass.
2. **The log script.** Write `ruling-log.mjs`. Find the commit with `git rev-parse --verify <sha>^{commit}` and `git merge-base --is-ancestor <sha> HEAD`. Read the branch with `git symbolic-ref --short HEAD`, which must equal `task/<ID>`. Get the files with `git diff-tree --no-commit-id --name-only -r <sha>`, the added lines with `git show --format= --unified=0 <sha> -- tasks/product-owner-log.md` filtered to `^\+## `, and the dirty state with `git status --porcelain -- tasks/product-owner-log.md`. Print one JSON line and exit 0 or 1. The heading regex escapes the task id.
3. **`ownerRuling` and the `guarded` loop.** The loop, in order, for each return of a guarded step:
   1. `decideStep` gives `owner` or `ask`.
   2. Frozen problems with `frozenRulingUsed` already set end `blocked`.
   3. `planRuling` runs. Owner kinds end `parked`. A third return, or the `MAX_RULINGS` cap, ends `blocked`.
   4. The step is called. `forOwner` ends `parked`, and `needsPass` ends `blocked`.
   5. A missing `logCommit` ends `ruling-unlogged`. Otherwise the log gate runs.
   6. A probe-marked key with no probe ends `blocked`.
   7. The counts and notes are recorded, and the step is rerun with the rulings.

   Then the existing frozen gate runs as today.
4. **Check.** After `check` returns, run `ownerRuling` for its `productOwnerQuestions` before the `approved` branch, and add the rulings to `specNotes` and to the revise prompt.
5. **The batch stop, and `.gitattributes`.**
6. **Docs and agent files**, as in Files to touch.

Decisions this spec makes (technical, the Product Owner's to veto; logged in the implementer's plan):

- **Who names the rule.** The asker cites the rule, and the run matches keys after `ruleKey`. Every later prompt lists the earlier keys so the asker can reuse one. Matching on free text would never fire, and letting the step re-key a question after the fact would make the probe rule depend on the step's own judgement.
- **Who classifies.** Both. The asker's kind is checked first, so a `look`, `wording` or `direction` question never reaches the step. The step can still send a question to `forOwner`.
- **"The run stops"** (item 3) is read as a batch stop, matching WORKFLOW.md's "The run stops early on …" bullet. An unlogged ruling breaks the audit trail, like a changed frozen test. It is a separate clause because `STOP_OUTCOMES` is frozen at three.
- **Counts are per task, read back from the log.** At the first ruling of a run, `ruling-log.mjs --history` reads the task's own `## <date>, <ID> ruling` sections from `tasks/product-owner-log.md` at HEAD and returns `{sections, counts, firstRulings}`: one count per `- [<rule key>] ...` line, the first ruling text per key, and the number of sections. The run seeds `ruleCounts`, `firstRulings` and the ruling total from it, so the third-return block, the probe and `MAX_RULINGS` hold across parked and resumed runs. An unreadable history leaves the run counting from zero (logged); a denied one ends `denied`. `frozenRulingUsed` still starts false on a resumed run, as `rulingUsed` did; `approvedFrozen` carries a frozen ruling.
- **`MAX_RULINGS = 6`.** It counts sections of rulings, earlier runs included. Only the per-rule limit is in the acceptance, and an agent can mint new keys. Six covers the T3-19 case (five rulings) with room to spare, and is the Product Owner's to change.
