# T3-42: draw artwork at the size of its frame (rename the artwork view's `width` prop)

Task: `pnpm task show T3-42`. Approval: `docs/specs/decisions-product-owner-2026-11-26d.md`, call 1 (the surface change and, in advance, the frozen-test ruling). Finding: `docs/research/ux-review-2026-11-26.md`, F1. Implementer: `native-engineer` (one Kotlin line, the TypeScript slot and types, documents).

Not a look or layout decision: nothing in `DESIGN.md` changes, and no design skill was needed. The fix makes the app draw what 7.2, 7.5 and 7.14 already say.

## Goal

Every artwork picture view is the size of its frame. The native view's prop `width` becomes `drawnWidth`, with the same value and meaning (the drawn width in whole canvas px, which sizes the image request). Nothing else about the view's surface or the image request changes.

## Root cause (verified in the installed source)

Installed: `react-native-tvos` 0.88.1-0, `expo-modules-core` 58.1.0 (resolved from `apps/tv/node_modules/react-native`).

1. `apps/tv/src/host/native-artwork.tsx` passes `width={width}` to the native view beside `style={StyleSheet.absoluteFill}`. The value is canvas px (248, 416, 1920).
2. Expo registers the view with its own prop names as valid attributes (`expo-modules-core/src/NativeViewManagerAdapter.native.tsx`, `validAttributes: addAttributeProcessing(expoViewConfig.validAttributes)`), so `width` crosses to native as a top-level prop, where a flattened style's `width` would also be.
3. Fabric's layout reads that top-level name: `ReactCommon/react/renderer/components/view/propsConversions.h:339` (`convertRawProp(context, rawProps, "width", …)` into `yoga::Dimension::Width`) and `YogaStylableProps.cpp:149` (`REBUILD_FIELD_YG_DIMENSION(dimension, setDimension, "width", "height")`). Yoga takes the number as dp.
4. The same name is in React Native's own base view config: `Libraries/NativeComponent/BaseViewConfig.android.js:276` (`width: true`, under "@ReactProps from LayoutShadowNode") and in `Libraries/Components/View/ReactNativeStyleAttributes.js`.
5. On a 1080p TV one dp is two px, so 416 canvas px becomes 416 dp = 832 px. This matches the review's measured bounds (thumb 832×234, poster 496×372, backdrop 3840×1080). The preview view gets no `width`, so it is the right size. The bounds were not re-measured for this spec.

Checked against the same files: `session`, `itemId`, `imageType`, `tag`, `drawnWidth`, `blurHash` and `onArtworkState` appear in none of `BaseViewConfig.android.js`, `TVViewConfig.js`, `ReactNativeStyleAttributes.js` or `propsConversions.h`. `drawnWidth` is safe; `width` is the only clash.

## Test plan

New file `apps/tv/src/host/native-artwork-layout.test.tsx` (jest, behaviour: it renders the slot with a recording fake view, as the two frozen slot tests do, and reads the props the view received; it scans no source):

- **"T3-42 item 2:"** the picture view receives `drawnWidth` 248 for a poster slot and 416 for a thumb slot, 248 for a slot 247.6 wide, and 1920 for a slot the width of the canvas (the 400 px Primary cap is native and is not applied here).
- **"T3-42 item 3:"** render a slot whose image has a BlurHash, so both instances mount. For every instance, every received prop key other than `style` must be absent from the set of names React Native itself reads on a view: the keys of the installed `react-native/Libraries/NativeComponent/BaseViewConfig` `validAttributes` (which holds the layout names, `BaseViewConfig.android.js:276`) joined with the keys of `react-native/Libraries/Components/View/ReactNativeStyleAttributes`. The set comes from the installed package, so an upgrade that adds a layout name is covered. Guard against an empty set: the test first asserts the set holds `width`, `height` and `flex`. Red today on `width`.
- **"T3-42 item 3:"** the style each instance receives, flattened, holds no `width` and no `height`, so only the frame sizes the view.

What these cannot prove: that a view's bounds equal its frame. jest runs no Yoga and no native view; that is the device gate. The Kotlin `Prop` names are tied to the allowlist and the types by the frozen surface tests, so a native prop React never passes needs no further test. TypeScript also refuses `width=` on the view once the type drops it (`pnpm check`).

Manifest: item 1 `gate: device`; item 2 `run` jest `-t "T3-42 item 2:"`; item 3 `run` jest `-t "T3-42 item 3:"`; item 4 `gate: ci`; item 5 `gate: review`; item 6 `gate: device`.

## Risks and out of scope

- **A stale native build.** The e2e and release APKs must be rebuilt after the Kotlin change; a JavaScript bundle that sends `drawnWidth` to an old binary draws no picture (the view never gets a width, so no request is made). `pnpm tv:wire` rebuilds a stale APK.
- **`height`.** The view takes no height prop today and must not gain one under that name; the item 3 test holds it.
- **Other native views.** `modules/player`'s view was not audited for the same clash here; if the implementer sees one, it goes to `tasks/backlog.jsonl`.
- Out of scope: reading the width from the view's own layout (call 1, "Not chosen"); the hero's contrast (F10, measured again after this merges); any change to the image request, the cap, the cache or the fade.
