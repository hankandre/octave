# T9-02: Store non-secret preferences

Task: `T9-02` (phase T9, App Shell & Presentation, lane `ui`, verify `pnpm check`). Depends on T9-01 (done, PR #294) and T3-02 (done, PR #251), both `passes: true` on origin/main (`scripts/task.mjs show`).

Implementers: `native-engineer` for milestone 1 (the new native module `modules/preferences`, Kotlin, its JVM tests); `implementer` for milestones 2 to 4 (TypeScript in `packages/core` and `apps/tv/src/host`, documents). The native milestone is serial native work (AGENTS.md, Parallel work).

## Goal

Give the TV one persisted, versioned, non-secret preferences record that holds only the per-device settings, and keep the per-account settings behind the same allowlist so T9-09 can store them on the server's display preferences. Every read and every write rebuilds the record from validated fields, so a token, credential, URL or play-session id can never be stored or read back, at two layers: the core's allowlist in TypeScript and a strict record check in the native store.

## Facts this spec rests on

Its header comment still says "one set of settings per computer, not per account" (lines 1-3), which T9-01 superseded.

## Decisions

Provisional under the Product Owner and the owner's veto, as every refiner decision.

- **D1. The device record holds `streamingLimits` only.** `{"version":1,"streamingLimits":{...}}`. Account fields are never written to the device (item 3). The version stays 1: no TV build has ever written a record (no store existed), and the existing version 1 reader already ignores the account fields it would now drop. Later device fields (passthrough, refresh rate) are added to the record's allowlist by their own tasks.
- **D2. One allowlist, two projections.** `PreferenceValues` stays the whole allowlist; `DEVICE_PREFERENCE_KEYS = ["streamingLimits"]` and `ACCOUNT_PREFERENCE_KEYS = ["continueWindow", "skipModes", "autoPlay"]` split it, and both projections are built by `sanitizePreferences`, so the account side "passes the same allowlist" (item 3). Subtitles have no preference field yet; the task that adds one adds it to the account keys.
- **D3. Storage is a new native module, `modules/preferences`, with two functions, `read()` and `write(record)`.** Same reasons as T4-09's decision log: no JavaScript storage package, `expo-file-system` fenced, the session module closed by decision 0005, and a file in the no-backup directory is excluded from backup by the platform. Two functions, not one, because unlike the install id the record changes. This is an architecture change (AGENTS.md, "Treat every new native module method or event as an architecture change"): recorded in `ARCHITECTURE.md` and `docs/security.md`, held by its own `ModuleSurfaceTest`, called out in the PR. No `docs/decisions/` file, as T4-09 ruled for a module outside the session surface.
- **D4. The native store checks the record too.** It is not a key-value store: `write` refuses, and `read` treats as absent, any text over 1024 UTF-8 bytes or that is not exactly the device record's shape: `{"version":1,"streamingLimits":{…}}` with both names exactly once, and inside `streamingLimits` at most `localMbps` and `remoteMbps`, each at most once, each one of the limit choices (`120`, `80`, `40`, `20`, `10`, `8`, `4`, `2`). No whitespace, no escape, no `true`, `false` or `null`, no other name or number: the encoder writes none of them. The store can therefore hold only one of a few dozen fixed texts, so a token, URL, play-session id or password cannot be stored, as written or re-encoded, even if JavaScript tried (a looser token check would let digit groups carry about 128 bits; spec check, issue 2). The TypeScript encoder and the Kotlin check share one vector file so they cannot drift.
- **D5. The account fields live in the store's memory until T9-09.** The TV store keeps all four fields in memory (the views and the player read one store), writes only the device record, and starts the account fields at their defaults each launch. No user sees this: Settings (T9-03) depends on T9-09.
- **D6. Failures never throw to the caller and never fall back to storing anything else.** A read that rejects, answers `null`, or answers text that does not parse gives the defaults. A write that rejects or answers `false` keeps the new value in memory for this launch; nothing is logged. T9-09 owns the "failed save is reported" rule for the account fields; for the device record there is no caller that can show it yet (T9-03 decides the copy if it ever needs one), so it is logged to the backlog (below).
- **D7. Writes are ordered.** Each write is chained after the previous one, so the last update is what the file holds. A read that finishes after a device-field update is ignored, so a launch-time read never overwrites a newer choice.
- **D8. The file is `octave-preferences.json` in `getNoBackupFilesDir()`,** written to `octave-preferences.json.tmp`, synced and renamed over the file, under one process-wide lock, as `InstallIdStore` does.

## Approach

### Milestone 1: the native module (`native-engineer`)

Copy `modules/install-id`'s structure. `PreferencesStore.read()` returns the file's text when it exists, is at most 1024 bytes and passes `isAllowedRecord`; otherwise `null` (a missing file is `null`, not an error). `write(record)` returns `false` without touching the disk when `isAllowedRecord(record)` is false; otherwise temp file, `fd.sync()`, rename, `true`; any `IOException` or `SecurityException` gives `false` and leaves no temp file. `isAllowedRecord` is a small hand reader of D4's one grammar (no JSON library, so the store stays JVM-testable without Android stubs): it accepts only the device record's shape, with each name once and each number from the allowed set, and nothing after the closing brace. Nothing is logged. `ModuleSurfaceTest` mirrors install-id's: the functions are exactly `read` and `write`, both `AsyncFunction`, no `Property`, `Constants`, `Events`, `View`, `sendEvent`; the store package imports no Android class; the config names the class. `PreferencesStoreTest`: a round trip; a new store on the same directory reads what the first wrote (the relaunch case); every `accepted` vector writes and reads back unchanged; every `refused` vector is refused and a file planted with it reads `null`; a 1025-byte text is refused; a failed rename leaves no temp file.

### Milestone 2: the core split (`implementer`)

Add the key lists and helpers in `preference-store.ts` (D1, D2). `decodeDeviceRecord(text: unknown)`: not a string gives defaults; `JSON.parse` in `try`; then `parseStoredPreferences`. Keep `MemoryPreferenceStore` and the views unchanged. Add a core test (a new file) that `accepted` in `preference-records.json` is exactly the `encodeDeviceRecord` text of the 81 limit combinations, so the Kotlin check accepts what TypeScript writes, that every `accepted` vector decodes without falling back, and that no `refused` vector is one the encoder writes.

### Milestone 3: the TV store (`implementer`)

`createDevicePreferenceStore(native)`: values start at `DEFAULT_PREFERENCES`; it calls `native().read()` inside a `try` (a synchronous throw from the loader counts as a failed read) and sets `ready` to settle in every case. On a good answer, and only if no device-field update happened since creation, it replaces the device fields with `decodeDeviceRecord(answer)` and notifies when they changed. `get()` returns the same object until the next change. `update(key, value)`: `values = sanitizePreferences({ ...values, [key]: value })`; notify; when `key` is in `DEVICE_PREFERENCE_KEYS`, chain `native().write(encodeDeviceRecord(values))` after the previous write, catching everything (D6, D7). `subscribe` uses `LimitListeners`. The views (`streamingLimitsOf`, etc.) work on it unchanged. Then `preferences-module*.ts` and `host-preferences.ts`.

### Milestone 4: documents and backlog

As in Files to touch. The PR body calls out the two new native functions as an architecture change and the `docs/security.md` edits.

- **"Split files that grow past about 400 lines."** `preference-store.ts` stays under it.

## Risks and out of scope

Risks:

- A later device field (passthrough, refresh rate) needs a name added to the Kotlin set as well as the core; the shared vector file makes a missed one fail `pnpm tv:native:test` instead of silently dropping it.
- `pnpm tv:apk:check`'s dex checks list package entry points; a new `dev.octave.preferences` package holds no network sink and should pass unchanged. Unverified until milestone 1 builds the APK.
- That the record survives a relaunch and is cleared with app data is tested on the JVM only, not on a device (backlog line).
- On tvOS the loader throws, so the store reads defaults and its writes fail silently; correct until the Swift store exists (T14).

Out of scope:

- Storing the account fields on the server's display preferences (T9-09), and switching them with the account.
- Any Settings screen or copy (T9-03), and wiring the store into the player.
- A subtitles preference field, passthrough and refresh rate.
- Migration of old records (none exist on any device).
