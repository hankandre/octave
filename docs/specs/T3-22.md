## Goal

The release APK asks Android for nothing Octave does not use, and none of its data leaves the device through Android backup or a device-to-device transfer.

1. A config plugin removes the Expo template's unused permissions and package-visibility queries from the release manifest.
2. `pnpm tv:apk:check` reads the release APK's permissions and queries and fails on any entry outside a named list, so a later library cannot add one unnoticed.
3. Backup is off: `android:allowBackup="false"`, plus data extraction rules that exclude every storage domain from cloud backup and from device-to-device transfer. The same check reads both from the APK.
4. `docs/security.md` states the permission list and the backup rule.

This lands before T4-02, the first task that stores anything outside the no-backup directory (a LAN confirmation).

### What is removed and why

| Entry | Declared by | Why Octave does not use it |
|---|---|---|
| `android.permission.SYSTEM_ALERT_WINDOW` | Expo template (main, debug, debugOptimized) | Draws over other apps. Only React Native's developer FPS overlay reads it (`DebugOverlayController.kt`); a release build has no developer menu. Removed from the main manifest only; the debug manifests keep their own line |
| `android.permission.READ_EXTERNAL_STORAGE` (to API 32) | Expo template, `expo-file-system` | Reads shared storage. Octave streams from a server and reads no file from shared storage; nothing imports `expo-file-system`. It matters on Android TV 9 to 12 boxes |
| `android.permission.WRITE_EXTERNAL_STORAGE` (to API 32) | Expo template, `expo-file-system` | Writes shared storage. Octave writes only inside its own data directory; downloads are not in the product |
| `android.permission.VIBRATE` | Expo template | A TV has no vibrator and nothing calls React Native's `Vibration`. Not in the task's list; removed as well (decision log, D2) |
| query: `VIEW` + `BROWSABLE` + `https` | Expo template | Lets `Linking.canOpenURL` see browsers. Octave opens no link in another app and never calls `Linking` |
| query: `OPEN_DOCUMENT_TREE` | `expo-file-system` | Lets the app see document pickers for the Storage Access Framework. Octave picks no folder |
| query: `VIEW` + any MIME type | `expo-file-system` | Lets the app see which apps can preview any file. Octave hands no file to another app; it also makes most installed apps visible to Octave |

## Approach

### The plugin

`with-trimmed-manifest.js` follows `with-app-jvm-tests.js`: CommonJS, pure functions exported for the tests, `withAndroidManifest` from `expo/config-plugins` applying them.

`trimManifest(manifest)` works on the parsed main manifest (`modResults`) and returns it:

1. Ensure `xmlns:tools` on `<manifest>`.
2. Drop every `uses-permission` whose name is `SYSTEM_ALERT_WINDOW` or `VIBRATE`. No marker: only the template declares them, the debug manifests keep their own `SYSTEM_ALERT_WINDOW`, and item 2's check fails if a library ever adds either.
3. For `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE`: drop the template's line and add `<uses-permission android:name="…" tools:node="remove"/>`, as Expo's `ensureBlockedPermission` does, because `expo-file-system` declares them too.
4. Drop the template's https `VIEW` + `BROWSABLE` intent from `<queries>`.
5. Add to `<queries>` two intents marked `tools:node="remove"`, with the same children as `expo-file-system`'s: `OPEN_DOCUMENT_TREE`, and `VIEW` with `data mimeType="*/*"`.
6. Applying it twice gives the same manifest.

`setBackupRules(manifest)` sets `android:dataExtractionRules="@xml/octave_data_extraction_rules"` on the main `<application>`. A `withDangerousMod(["android", …])` step writes `DATA_EXTRACTION_RULES_XML` to `android/app/src/main/res/xml/octave_data_extraction_rules.xml` (creating `res/xml`); this is Expo's way for a plugin to write a file, and `expo prebuild --clean` rewrites it every time.

`android.allowBackup` is set in `app.config.ts`, not by the plugin, because Expo's `withAllowBackup` writes the attribute from the config and would overwrite a plugin that ran before it.

If the generated main manifest shows that Expo's manifest mods ran after the plugin (a template permission is back), move the plugin's work into a later mod and record how in the decision log. If a query marker does not remove the library's intent, try in this order and stop at the first that works, recording which: (a) the marker with the children in the library's exact order; (b) `tools:node="remove"` on the main manifest's `<queries>`. If neither works, stop and report to the Product Owner: do not add a Gradle manifest transform, and do not unlink `expo-file-system` here (that is T3-19 item 3).

### Backup

Decision D1: **backup is off**, the first branch of item 3. The rules file:

```xml
<?xml version="1.0" encoding="utf-8"?>
<data-extraction-rules>
  <cloud-backup>
    <exclude domain="root" path="." />
    <exclude domain="file" path="." />
    <exclude domain="database" path="." />
    <exclude domain="sharedpref" path="." />
    <exclude domain="external" path="." />
    <exclude domain="device_root" path="." />
    <exclude domain="device_file" path="." />
    <exclude domain="device_database" path="." />
    <exclude domain="device_sharedpref" path="." />
  </cloud-backup>
  <device-transfer>
    <!-- the same nine excludes -->
  </device-transfer>
</data-extraction-rules>
```

- `allowBackup="false"` turns backup off on Android 11 and lower and cloud backup on 12 and higher. On 12 and higher some devices still run device-to-device transfer (Facts), and a missing section means "fully enabled", so both sections are present and each excludes every domain. No `include` appears anywhere.
- No `fullBackupContent` file is added: those rules are read only where `allowBackup="false"` already disables backup. `judgeBackup` refuses a `fullBackupContent` attribute other than `false`, so one cannot arrive unnoticed.
- No `cross-platform-transfer` section: it needs the bundle and team id of an iOS app, and Octave has none (Risks).
- The named list of backed-up preferences is empty, so no credential and no LAN confirmation can be in it. The credential record is also under `getNoBackupFilesDir()` (decision 0005), which Android excludes whatever the rules say.

### The check

`scripts/tv-apk-manifest.mjs`, pure functions first:

- A reader for `aapt2 dump xmltree` text giving `{ name, attributes, children }`, nested by indentation, attribute names without namespace and resource id, quoted values without quotes and the `(Raw: …)` copy, other values as printed. It returns null on a line it cannot read. If T3-15 has merged when this task is implemented, import its `parseXmlTree` and `resolveResourceFile` from `scripts/tv-apk-check.mjs` instead of writing them again; the frozen tests import only from `tv-apk-manifest.mjs`, so either works.
- `ALLOWED_PERMISSIONS`, `ALLOWED_DECLARED_PERMISSIONS`, `ALLOWED_QUERIES`: arrays of `{ name, reason }` (a query entry is `{ key, reason }`, the key being the merger's form, for example `action:android.intent.action.VIEW+data:scheme:https`). The lists live in the script, not in the frozen tests, so a later task adds a row without a frozen-test ruling.
- `judgeManifestSurface(text)` returns `ERROR tv apk: …` lines, one per entry, each naming the entry and the list it is missing from:
  - every child of `<manifest>` whose element name starts with `uses-permission` (so `uses-permission-sdk-23` counts) must be in `ALLOWED_PERMISSIONS`;
  - every `<permission>`, `<permission-group>` and `<permission-tree>` must be in `ALLOWED_DECLARED_PERMISSIONS`;
  - every child of every `<queries>` must be in `ALLOWED_QUERIES`; an empty `<queries>` passes;
  - an unreadable tree, or one whose root is not `manifest`, is an error.
- `judgeBackup({ allowBackup, fullBackupContent, rulesAttribute, rulesFile, rulesTree, backupAgent, fullBackupOnly })` returns error lines unless: `allowBackup` is exactly `false`; `fullBackupContent` is absent or `false`; `backupAgent` and `fullBackupOnly` are absent (spec check note 5: neither takes effect with `allowBackup="false"`, but one added later must not pass unnoticed; `undefined` and `null` both mean absent, since the frozen facts omit them); the rules attribute resolves to one file; the tree's root is `data-extraction-rules`; it holds exactly one `cloud-backup` and one `device-transfer`, and nothing else; no element anywhere is an `include`; and each section holds an `exclude` for each of the nine domains whose `path` names the whole domain (`.`, or the form milestone 2 settles on), and no other child.
- `checkManifest(dump)` takes a function `dump(...args)` that returns the text of `aapt2 dump <args>`, makes the calls (`xmltree <apk> --file AndroidManifest.xml`, `resources <apk>`, `xmltree <apk> --file <rules file>`), and returns every error line from both judges.
- `main`: the APK defaults to `RELEASE_APK` from `scripts/tv-apk-check.mjs`; `aapt2` comes from `newestBuildTool(androidSdk(), "aapt2")`; errors go to stderr as `ERROR tv apk: …` and the exit status is 1; on success it prints one line naming the counts (`tv apk: 2 permissions, 0 queries, backup off`). A missing APK or a failed `aapt2` call is an error, never a pass.

`pnpm tv:apk:check` becomes the two scripts in sequence. That keeps this task out of `tv-apk-check.mjs`'s `main`, which T3-15 is changing, and the `tv` job and the task's `verify` line already run `pnpm tv:apk:check`. No frozen test pins the script's text: T3-01's `scripts/tv-apk-check.test.ts` requires only that `tv:apk:check` exists and that the job runs `pnpm tv:apk:check`, and T3-15's `scripts/tv-cleartext.test.ts` reads `scripts/tv-apk-check.mjs`, not `package.json`.
