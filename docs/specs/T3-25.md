## Goal

T3-16 capped an answer's size (1, 4 or 8 MiB by call class). A small answer can still cost the parser more than its size: JSON nested deeply enough overflows the stack, and the error reaches JavaScript as `network`. After this task:

1. An answer whose JSON nests deeper than **64** is refused as `unexpected-response` before it is parsed, by a scan that does not recurse.
2. A `StackOverflowError` or an `OutOfMemoryError` raised inside a transport call resolves `{ error: "unexpected-response" }`, with no message, class name or other key.
3. The three response-cap cases T3-16's review found untested have tests.
4. `docs/security.md` and decision 0005 state the bound, the two error mappings and their limits.

No native method, event, argument key, error code or dependency is added.

## Approach

### The bound

- **Depth** is the largest number of arrays and objects open at one point of the text. A scalar is 0, `[]` is 1, `{"a":[1]}` is 2.
- **The bound is 64.** Depth 64 crosses; depth 65 is refused.
- Why 64: it is nine times the deepest recorded answer (7); it is far below 200, where the library's reader changes how it reads objects, so the reader stays on its plain path; and at 64 levels the three recursive walks use a few hundred frames.
- It applies at every status (2xx and error), to session and tokenless calls and the sign-in posts. The logout's body is not read.
- It applies to a body whose first character after whitespace is `[` or `{`. No other body can make the reader recurse (Facts, "The library's lexer"), so an HTML error page from a proxy, which begins with `<`, is not scanned and still crosses as a status with no body. Scanning every body would let the quote tracking drift on text that is not JSON and turn such a page into `unexpected-response`.
- A body that begins with `[` or `{`, is not JSON and has 65 brackets open at once as the scan counts them is `unexpected-response`; today it crosses as a status with no body.
- The request body JavaScript hands to `request` is not bounded: it comes from the core's gateway, and `SessionTransport.kt:83` only parses it and drops the result.

### The scan

`JsonDepth.exceeds(text: String, max: Int = JsonDepth.MAX): Boolean`, one pass over the characters, no recursion, no allocation:

- First it skips every leading character at or below U+0020 and U+FEFF. That set holds the lexer's four whitespace characters and more, so the scan never skips less than the reader does. If the next character is not `[` or `{`, or the text ends, it returns false.

- Outside a string: `"` starts a string; `[` or `{` adds one to the depth, and the scan returns true as soon as the depth is above `max`; `]` or `}` takes one off when the depth is above 0. Any other character is skipped.
- Inside a string: `\` skips the next character; `"` ends the string. Any other character is skipped.
- It does not check that closers match openers or that the text is JSON; the parser does that afterwards.

Why the scan cannot count less than the reader recurses: `[`, `{` and `"` are token characters in the library's lexer (`TC_BEGIN_LIST`, `TC_BEGIN_OBJ`, `TC_STRING` in `AbstractJsonLexerKt`), so the reader never reads one as part of an unquoted word. Up to the point where the reader stops on an error, it has entered a level only at a `[` or `{` the scan also counted, and has left a string only at the quote the scan also saw. That the lexer ends an unquoted word at each of these characters is read from the token table, not run; `JsonDepthTest` and item 1's shapes below test it.

`parse` becomes: empty bytes are null; decode as UTF-8; **if `JsonDepth.exceeds(text)` throw `UnusableAnswer()`**; then the parse and `strictJson` as today. `UnusableAnswer` is thrown inside `response.use` and outside the `try` around `call.execute()`, so the response is closed and a `GET` is not sent again. The scan reads the decoded text, the same text the parser gets.

### The two errors

`TransportCodes.of(error: Throwable)` gains one branch before `else`: `is StackOverflowError, is OutOfMemoryError -> UNEXPECTED_RESPONSE`. Every other `Error` and every other exception keeps its code. `outcome` is not changed: it already catches `Throwable` and returns `mapOf("error" to code)`, so no message, class name or stack crosses.

- **StackOverflowError.** After the bound no answer can raise one by nesting: the reader, `strictJson`, `TokenStrip.strip` and `toString` each go at most 64 levels deep. The mapping is the second line should the scan ever disagree with the reader. It is decided by type alone, so a `StackOverflowError` raised anywhere inside a transport call is `unexpected-response`; the only recursion over data the caller does not control is over the answer.
- **OutOfMemoryError: how it is handled.** It is not prevented. It is caught by `outcome` on the thread that made the call, as it is today, and resolves `{ error: "unexpected-response" }` in place of `network`.
  - When the catch runs, the frames that held the body bytes, the text, the tree, the stripped tree and the output text have unwound, so nothing of the answer is still referenced and the collector can free it. The transport keeps no answer between calls.
  - The call is not sent again: `send` re-sends a `GET` only on an `IOException` from `call.execute()`. `response.use` closes the response.
  - In `signIn` an error raised while the answer is read or parsed happens before `SessionRegistry.open`, so no session is opened.
  - Why map it and not let it end the process: the answer that caused it is refused and gone, the app keeps running, and a server cannot stop the app with one answer. `network` is the wrong code for it: its copy says the server could not be reached (Facts, "The error copy"), and the server answered.
  - What the mapping does not do: it does not see an `OutOfMemoryError` raised on another thread (the player, an image load) while this answer holds the memory, and the process may still end. An 8 MiB answer of small values (`[0,0,…]`, about four million elements) is held as a tree, a stripped tree and an output text at once; whether that fits a TV's heap is unverified. A bound on the number of values goes to the backlog (Out of scope).
  - `OctaveSessionModule.run`'s last guard keeps `network`. Nothing reaches it, and it cannot be tested on the JVM.

## Risks and out of scope
