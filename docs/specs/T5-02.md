## Goal

Give the core one entry point that fetches what Home shows and turns it into three things: the Continue watching row, the Recently added row, and the hero pick. T5-03 draws them; T5-04 draws the failures.

Most of Continue watching already exists and is tested (`gateway.resumeItems`, `gateway.nextUp`, `gateway.recentlyPlayed`, `continueWatchingRow` and `pickUpNext` in `packages/core/src/domain/up-next.ts`). What is missing:

1. **Recently added across libraries.** Today the gateway has only `latestInLibrary(parentId)` with a limit of 16 (`gateway.ts:512`). Home needs one list with no library id, capped at 15, of movies and shows.
2. **A Home entry point.** Nothing fetches the four lists together, says which one failed, composes the two rows and the hero, or removes the hero from the row beneath it.
3. **Contract fixtures.** No fixture holds a cross-library Latest answer for any server, the Jellyscale Next Up stub's body, or Jellyscale's answer to the recently-played query.

## Decisions

Technical and placement choices made here. The Product Owner may overrule any of them.

- **D1. The window is an explicit argument with no default.** `composeHome` takes `window: ContinueWindow` and applies none itself. T5-03 passes `"all"` until T5-01 decides. `DEFAULT_CONTINUE_WINDOW` is not read by the new code and not changed (T5-01 and T9-03 own it). Why: reading `"14"` would settle T5-01 by accident.
- **D2. Item 5's two hero rules, not `DESIGN.md` §7.3's four.** `composeHome` calls `pickUpNext` with `sequel` and `similar` undefined. `similarItems`, `itemCollections` and `collectionItems` are not called by Home. The mismatch with §7.3 (rules 2 and 3) goes to the backlog for the Product Owner (see "Backlog lines").
- **D3. Caps count the hero.** Continue watching is at most 16 titles; when the hero is its first title, the row below shows the other 15 at most. Recently added is at most 15 titles; when the hero is its first title (Continue watching empty), the row below shows the other 14 at most. Why: "at most 16 cards" and "capped at 15 titles" then hold for the list and for the row, and no extra request is needed to refill a slot.
- **D4. One request for Recently added, `limit=15`.** Titles the client leaves out (D6) are not refilled, so on today's Jellyscale the row can be shorter than 15 or empty while new episodes are the newest items. Item 4 accepts this until T10-07.
- **D5. The request names the types: `includeItemTypes=Movie,Episode`.** This keeps a music or photo library from filling the 15 slots with albums and photos, and it is Jellyscale's own default. It is kept **only if** the milestone 1 recordings show both Jellyfin versions still group episodes under it (see the stop rule). Otherwise the parameter is dropped and the client filter in D6 does the work alone.
- **D6. What Recently added keeps**, in the server's order (no client sort; the request asks for no date field):
  1. a `Movie`: kept;
  2. a `Series`: kept, once per id;
  3. an `Episode` whose answer carries its `SeriesId` **and** `SeriesName`: shown as its series, once per series, at the place of its newest episode, and left out when that series is already in the list. The card has `id = SeriesId`, `kind = "Series"`, `title = SeriesName`, the series poster when `SeriesPrimaryImageTag` is present, and the parent backdrop, logo and thumb the episode carries. It carries none of the episode's own state or numbers: no `played`, `resumePositionTicks`, `progress`, `remainingTicks`, `lastPlayedAt`, `seasonNumber`, `episodeNumber`, `seriesId` or `addedAt`, and no year, subtitle or unplayed count (item 3 case (c) asserts it with an episode that has a position and `Played: true`);
  4. an `Episode` without `SeriesName`, as Jellyscale's are today: left out;
  5. any other type: left out.

  Rule 3 is the owner's option B ("Owner decisions"). It exists because Jellyfin answers a loose episode for a show with one new episode (the controller lines above), and `DESIGN.md` §7.4 says "A series with new episodes shows once, as the series". Jellyscale's episodes do not name their series, so rule 4 applies to them until T10-07.
- **D7. A failed list does not fail Home.** Each list is fetched by itself. The result names every list that failed, and the rows are composed from the lists that arrived. Continue watching with a failed Next Up shows the in-progress titles; with a failed recently-played list it is built with `plays: undefined` (next episodes sort after the dated titles). An aborted signal rejects the whole load and reports no failed list.
- **D8. The hero's overview and quality facts are not fetched here.** The lists ask for card fields only (item 6). T5-03 reads the hero's extra facts for one item (`itemDetail`), or its spec decides otherwise.
- **D9. `DateCreated` stays on the Next Up request.** It is the one field no card draws, and with the window at `"all"` (D1) nothing reads it yet. It feeds the window rule (`ARCHITECTURE.md` §3 names it in the Next Up row) and an existing test pins it (`home-gateway.test.ts`). Item 6's tests pin each request's `fields` exactly, so nothing else can creep in.
- **D10. New code goes in new files.** `gateway.ts` gains one short method only; it is already far past 400 lines and splitting it is not this task.

## Approach

### Shapes

```ts
// packages/core/src/domain/home.ts
export type HomeListName = "resume" | "nextUp" | "recentlyPlayed" | "recentlyAdded";

// A list that is absent failed or was not asked for.
export interface HomeLists {
  resume?: MediaCard[];
  nextUp?: MediaCard[];
  recentlyPlayed?: RecentPlays;
  recentlyAdded?: MediaCard[];
}

export interface HomeListFailure {
  list: HomeListName;
  // What the gateway raised: already redacted. The app maps it to plain copy and never shows it.
  error: unknown;
}

// The four reads Home needs. JellyfinGateway satisfies it structurally.
export interface HomeSource {
  resumeItems(signal?: AbortSignal): Promise<MediaCard[]>;
  nextUp(signal?: AbortSignal): Promise<MediaCard[]>;
  recentlyPlayed(signal?: AbortSignal): Promise<RecentPlays>;
  latestItems(signal?: AbortSignal): Promise<MediaCard[]>;
}

export const HOME_LISTS: readonly HomeListName[];

export function loadHomeLists(
  source: HomeSource,
  names: readonly HomeListName[],
  signal?: AbortSignal,
): Promise<{ lists: HomeLists; failed: HomeListFailure[] }>;

export interface Home {
  hero: UpNext;                 // { rule: "row" | "newest", card } or { rule: "none" }
  continueWatching: MediaCard[]; // without the hero
  recentlyAdded: MediaCard[];    // without the hero
}

export function composeHome(lists: HomeLists, options: { window: ContinueWindow; now: number }): Home;
```

- `loadHomeLists` starts every named list at once and waits for all of them (`Promise.allSettled`). A rejected list goes to `failed` in the order of `names`; the rest go to `lists`. If `signal` is aborted when the lists settle, it rejects with the abort reason. It makes no write call and no retry.
- **Retry of one list** (T5-04) is `loadHomeLists(source, ["nextUp"])`, merged by the caller over the lists it already holds, then `composeHome` again. That is why the lists and the composition are two functions.
- `composeHome` is pure: `continueWatchingRow({ resume: lists.resume ?? [], nextUp: lists.nextUp ?? [], plays: lists.recentlyPlayed, window, now })`, then `pickUpNext({ row, agedOutIds, sequel: undefined, similar: undefined, latest: [lists.recentlyAdded ?? []] })`, then the hero's id is filtered out of the row it came from (`rule: "row"` from Continue watching, `rule: "newest"` from Recently added). `now` comes from the caller's clock port; the core imports no adapter.
- `gateway.latestItems()` sends, with `CONTROL_REQUEST_TIMEOUT_MS`:

  `GET /Items/Latest?userId=&limit=15&groupItems=true&includeItemTypes=Movie,Episode&enableUserData=true&fields=PrimaryImageAspectRatio&imageTypeLimit=1&enableImageTypes=Primary,Backdrop,Thumb,Logo`

  and returns `toRecentlyAdded(data, RECENTLY_ADDED_LIMIT)`. The answer is a bare array; anything that is not an array maps to an empty list.
- `toRecentlyAdded` applies D6 in one pass with a set of seen ids, and stops at the limit. Movies and series go through the existing `toMediaCard`.

## Risks and out of scope

Risks:

- **Cross-library Latest on Jellyfin is unverified** and differs by version and by which library comes first. The fixture servers show only "Movies first"; a server whose first library is Shows takes another branch on both versions. The client rules in D6 accept any mix of films, series and loose episodes, which covers the shapes the source can produce; a server that leaves films out entirely would not be caught by a fixture. Named in the PR as an untested gate; the dogfood servers are the check (owner).
- **A short Recently added row on Jellyscale** until #234 (D4). Intended by item 4.
- **A large batch of one show's episodes** can shorten the list on Jellyfin (the `limit * 5` and `limit * 2` reads). Upstream.
- **Played titles**: Jellyfin hides played items from Latest when the account's "hide played in latest" setting is on (controller lines 543-549). Octave sends no `isPlayed`, so the account's setting applies. Left as the server decides.
- **Next Up ordering depends on the recently-played list** (100 entries). A series last played before the 100 newest finished plays sorts after the dated titles; existing behaviour of `continueWatchingRow`.
- **The Jellyscale recently-played answer is unrecorded.** If it is a non-2xx, item 7's fixture test shows the row built without it (D7), and the gap gets a Jellyscale issue only after the usual weighing (not filed by this task).
- **Recording changes a user's state on the fixture servers.** The recorder resets what it set; a crash mid-run leaves state that `pnpm fixture:down` clears.

Out of scope:

- Any screen, focus, copy or skeleton (T5-03, T5-04); the "See all" tile and its grid (`DESIGN.md` §7.4; no acceptance item here).
- Remove from Continue watching and the window (T5-01, T5-05, T9-03).
- The sequel and similar hero rules (D2); grouping on Jellyscale (T10-07); Next Up on Jellyscale (#101).
- Caching, refresh on return from the player, and realtime updates.
- Removing `latestInLibrary` or `HOME_ROW_LIMIT`, or splitting `gateway.ts`.
