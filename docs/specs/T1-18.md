# T1-18: Make the review follow-ups step fix small findings in the same pull request

Implementer: `implementer` (TypeScript/JavaScript workflow code and docs only; nothing under `modules/` or `apps/tv/android/`, and not the PlayerEngine port). Not a playback task, so no Jellyscale wire test applies. No dependency is adopted.

## Goal

Bring the task workflow's review follow-ups step (`.claude/workflows/task.js`) in line with the owner's review follow-ups rule of 2026-11-22 (`docs/specs/decisions-process.md`, "Review follow-ups"; `WORKFLOW.md` §2c and §6). Today the step fixes critical, high and medium findings and is told to "Log these low findings as follow-ups in the active plan and commit; do not fix them" (`task.js:710`). Each logged low then became a task of its own (backlog entry 231, `tasks/backlog.jsonl:231`). After this task:

1. The step fixes every critical, high and medium finding and every small low in the task's own pull request, and logs none of those.
2. A finding it leaves becomes one line in `tasks/backlog.jsonl`, with its severity in the `why`, for the phase's hardening task. No plan line and no task of its own.
3. A left finding that opens a path into a self-hoster's home network, or leaks local information, comes back in the task's result as a real-TV gate, with the condition that holds. The Product Owner places it.

## Approach

**Follow-ups prompt.** The shape below keeps the frozen anchor first. `${blocking}` is the critical, high and medium list; `${lows}` is the low list.

1. `Fix these review findings and commit, with a test for each behavior change:\n${blocking}`, or `No critical, high or medium review findings.` when there are none. The literal must still appear first in the source, so keep the conditional as it is today: `${blocking.length ? `Fix these review findings…` : '…'}`.
2. When there are lows: `Also fix in the same pull request each of these low findings that is small, with a test for each behavior change; log none of the findings you fix:\n${lows}`
3. The definition of small: `A low is small when you can fix and test it in the same pull request without a new dependency, a new native module method or event, a change to an acceptance item or a frozen test, or a look, wording or direction call. When it needs one of those, leave it.`
4. The left-finding rule:
   - `For each finding you leave, append one line to tasks/backlog.jsonl (WORKFLOW.md §2a), at the end, without touching another line, and commit it with your fixes`. The fields are:
     - `what`: the fix, in one sentence
     - `why`: `<severity> review finding from ${task}: <the problem>; for the phase's hardening task`, plus `; real-TV gate: <home-network|local-information>` when one holds
     - `source`: `"${task}"`
     - `size`: `S`, `M` or `L`
     - `date`: from `date +%F`
   - `Never append a line whose what is already in the file. Never write a plan line, or a backlog line that asks for a task of its own; one hardening task per phase takes these, and a Product Owner pass places them. Never edit tasks/prd.json.`
5. The real-TV gate rule:
   - `Only a finding that opens a path into a self-hoster's home network, or leaks local information (a LAN address, a serial, a hostname, a credential), gates an install on a real TV.`
   - `Return in leftFindings every finding listed above that is not fixed on the branch, including one an earlier attempt of this step left, each with realTvGate home-network, local-information or none.` (`work()` and `guarded()` keep only the last attempt's output, so the last attempt must list them all.)
   - `Describe a leaked value, never quote it, in the backlog, the result, the evidence and the PR.`
   - Only lows may be left. A critical, high or medium finding you cannot fix is a blocker (done=false), not a left finding.
6. The existing done, evidence, plan-tick and ciSteps text follows, unchanged. It must keep `${taskCli} set ${task}`, `--status done`, `${evidenceRule}` and `commit <sha>`.

**Who classifies.** The follow-ups agent sets `realTvGate`. It is the step that decides what is left, it reads the code it is fixing, and the condition is only needed for left findings. The reviewer and guardian prompts are unchanged. The run does not judge the classification. It checks only that the value is one of three, and it surfaces every gate.

**What the run enforces and what is prompt text only.**
- Enforced by the run and tested: a left finding above low blocks the task; an unknown gate value blocks the task; gates and left findings reach the result on every outcome after the follow-ups; the Ship prompt carries them.
- Enforced by `pnpm check`: the backlog line's format and a repeated `what` (`scripts/check-backlog.mjs`), and that no frozen file changed (`pnpm lint:flow`).
- Prompt text only, tested as text: what "small" means, that a fixed finding is not logged, that no plan line or task of its own is written, that the line carries the severity, and that a leaked value is never quoted.

**A gating finding also gets a backlog line.** Item 2 says every left finding goes to the backlog, and §2c says a gate is for the Product Owner to place. So a gating finding gets both a backlog line, whose `why` names the condition, and an entry in `realTvGates`. This does not contradict "a finding that is left and gates nothing goes to tasks/backlog.jsonl" (`WORKFLOW.md:96`). That sentence says where non-gating findings go and does not forbid a line for a gating one. The line gives the Product Owner pass something to place.

**Ordering in the run.** The order is:

1. The follow-up returns.
2. The `denied` check.
3. `planLeft`: set `left` and `realTvGates` and log each gate; then block on `problems`, then on `unfixed`.
4. The existing `checksPassed`/`done` check.
5. The rest as today: the green gate, then Ship.

`realTvGates` is set before any later `result()` call, so a `blocked` from the follow-up's own check, a `blocked` from the green gate and `ci-red` all carry it. Exceptions: a `denied` follow-up, a `stop` from `guarded()` (a frozen-test or ruling stop) and an empty follow-up end before `planLeft` runs and carry no gates; the step's committed backlog lines still hold any it found.

## Risks and out of scope

**Invariants and hard rules touched.**

- `AGENTS.md` "Tests": never change or delete a frozen test.
  - `task.test.mjs`, `task-resume.test.mjs` and `task-rulings.test.mjs` stay unchanged.
  - The `between('Fix these review findings', …)` slice is the main trap: moving or repeating that literal breaks a frozen test.
- `AGENTS.md` "Tasks":
  - Append deferred work to `tasks/backlog.jsonl`, append only.
  - Leave adding tasks to a Product Owner pass.
  - Never edit `tasks/prd.json` beyond status fields.
  - The prompt keeps the step to append-only lines and no task creation.
- `AGENTS.md` "Tokens and network": never log or display tokens, passwords, authenticated URLs or play-session ids. The owner's point 3 adds LAN addresses, serials and hostnames as local information.
  - The prompt says to describe a leaked value and never quote it.
  - A quoted value in a committed backlog line would itself be a leak, and so would one in `tasks/backlog.jsonl`, the result, the evidence or the PR.
  - `AGENTS.md` "Never commit a server address, a credential, or the owner's name" applies to the backlog line.
- `AGENTS.md` "Models": "log lows in the plan" changes to the owner's rule. This changes a rule line in `AGENTS.md` (and `.claude/skills/change-review/SKILL.md`). It is not an invariant from `ARCHITECTURE.md`, but the PR calls it out as a rule-text change that follows the owner decision of 2026-11-22.
- The owner's security worry (no LAN pivot): this task makes a home-network path a surfaced gate instead of a silently logged low. It loosens nothing: the decision of 2026-11-22 already relaxed the "security lows are fixed promptly" rule, and this task only implements it.

**Risks.**

- The "small" judgement is the agent's, so a lazy step could leave too much. Mitigation: only lows may be left (enforced), and every left one is visible in the backlog and in `left`.
- A misclassified gate (a real leak marked `none`) is not caught by the run. The reviewer and guardian still see the finding, and its backlog line carries the severity. A deterministic classifier is out of scope.
- A rerun of `work()` or `guarded()` may append twice. `scripts/check-backlog.mjs` fails a repeated `what` in `pnpm check`, and the prompt forbids it.
- A finding the follow-ups step cannot fix that is critical, high or medium ends `blocked`. This is today's behaviour through `done=false`, and it is now also checked on `leftFindings`.

**Out of scope.**

- Creating the per-phase hardening task: a Product Owner pass does that.
- Re-judging existing real-TV gates: done in the PO log, `tasks/product-owner-log.md:304-311`.
- Moving existing plan-logged lows to the backlog.
- Changing the reviewer or guardian prompts or schema.
- T1-19 lanes.
