# T3-21: Sign every build for a real TV with a private key

Task: T3-21 (`pnpm task show T3-21`), lane `release`, `human: true`, depends on T3-01 (done, PR #249). Backlog entry 169 (taken). Implementer: `implementer` (TypeScript and JavaScript: a config plugin, Node scripts, CI and docs; no Kotlin file and nothing under `modules/` or `apps/tv/android/` is edited by hand; the Gradle text is written by the config plugin at prebuild). Not a playback task, so there is no Jellyscale wire test.

## Goal

Today every release and e2e APK is signed with the public debug keystore that the Expo template ships. Anyone can build an APK with that key and install it as an update over a sideloaded Octave. The update keeps the app's UID, its data and its Keystore keys, so once T4-05 stores the credential it could decrypt it (backlog 169). After this task:

- a build meant for a real TV is signed with the owner's private key, which the build finds through one environment variable and never holds in the repository;
- a build with no key fails, names what is missing and never falls back to the debug keystore;
- a check reads the certificate of each built APK and fails on the debug certificate;
- every script that installs onto a device refuses a debuggable APK, or one signed with the debug certificate, unless the device is positively an emulator;
- the application ID becomes `cloud.jellyscale.octave` while the Kotlin packages stay under `dev.octave`.

## Facts this spec rests on

- **The template signs release with the debug key.** The generated `apps/tv/android/app/build.gradle` (prebuild output in another worktree, `octave-T3-11`, lines 100 to 115) has `signingConfigs { debug { storeFile file('debug.keystore'); storePassword 'android'; keyAlias 'androiddebugkey'; keyPassword 'android' } }`. Its `buildTypes.release` has `signingConfig signingConfigs.debug` under the comment "Caution! In production, you need to generate your own keystore file."
- **The debug certificate.** `keytool -list -v` on that `debug.keystore` gives owner `CN=Android Debug, OU=Android, O=Unknown, L=Unknown, ST=Unknown, C=US` and SHA-256 `FA:C6:17:45:DC:09:03:78:6F:B9:ED:E6:2A:96:2B:39:9F:73:48:F0:BB:6F:89:9B:83:32:66:75:91:03:3B:9C`. `apksigner verify --print-certs` on an existing e2e APK (`octave-T3-02/apps/tv/dist/e2e/octave-tv-e2e.apk`) prints `V2 Signer: certificate DN: CN=Android Debug, …` and `certificate SHA-256 digest: fac61745dc0903786fb9ede62a962b399f7348f0bb6f899b8332667591033b9c`. Today's shipped builds are signed with the public key.
- **The probe APK is debuggable; the app APKs are not.** `aapt2 dump badging` on `octave-session-probe.apk` prints `package: name='dev.octave.session.test'` and the line `application-debuggable`. On the e2e APK (`dev.octave.tv`) that line is absent. `scripts/tv-cleartext.mjs:132` and `scripts/tv-resolved-address.mjs:96` install the probe with `adb install -r -t`.
- **Where installs happen.** `adb install` runs in `scripts/tv-e2e.mjs:197`, `scripts/tv-first-focus.mjs:101`, `scripts/tv-wire.mjs:264`, `scripts/tv-cleartext.mjs:132` and `scripts/tv-resolved-address.mjs:96`. No other script or living document runs `adb install` on an Octave build. `docs/decisions/0004-tv-shell-go-no-go.md:183` is a spike record for a different package (`dev.fluster.spike.browse`) and is left alone. `docs/commands.md:19` documents `pnpm tv:e2e` on "a real TV". T3-17 item 2 needs `pnpm tv:e2e` to pass on the Shield.
- **How the scripts recognise an emulator.** `scripts/tv-install-id.mjs:30` (`EMULATOR_PROPERTIES = ["ro.boot.qemu", "ro.kernel.qemu"]`, `isEmulator`) treats a device as an emulator only when one property is exactly `1`. `stageRequired(env)` turns a skip into a failure in CI (`GITHUB_ACTIONS`) or under `OCTAVE_INSTALL_ID_STAGE=required`.
- **Expo ties the application ID to the Kotlin package.** `@expo/config-plugins` 58.0.13, `build/android/Package.js:270-276`: `setPackageInBuildGradle` writes `android.package` into both `applicationId` and `namespace` with the regex `(applicationId|namespace)(\s*=\s*|\s+)['"].*['"]`. `withPackageRefactor` (lines 100 to 108, 138 to 160) moves `MainActivity` and `MainApplication` into that package on disk. The Expo config has no separate namespace field.
- **Code that depends on the `dev.octave.` prefix.** The dex check finds Octave's code by that prefix (`scripts/tv-apk-dex-operand.mjs:5`, `scripts/tv-apk-dex-merged.mjs:5`, rule D8 in `scripts/octave-module-packages.mjs`), and so does the R8 keep rule in `apps/tv/app.config.ts:27`. Setting `android.package` to `cloud.jellyscale.octave` would move `MainApplication` out from under that prefix. So the application ID and the Kotlin package have to be set apart (Approach, "The application ID").
- **Where the ID is defined.** `ANDROID_APPLICATION_ID` lives at `packages/core/src/domain/app-identity.ts:6`. It is read by `apps/tv/app.config.ts:12`, by the scripts (`tv-apk-check.mjs`, `tv-apk-manifest.mjs`, `tv-e2e.mjs`, `tv-first-focus.mjs`, `tv-install-id.mjs`, `tv-wire.mjs`) and by `AppIdentityTest.kt`. That test compares it with `android.defaultConfig.applicationId`, which `apps/tv/plugins/with-app-jvm-tests.js:29` passes in.
- **Nothing reads the ID at run time.** No runtime code under `modules/`, `apps/tv/src` or `apps/tv/native` reads the application ID (`git grep "APPLICATION_ID\|packageName"`; the one hit is `versionName` in `OctaveSessionModule.kt:70`).
- **No configuration cache.** The generated `gradle.properties` does not enable the configuration cache, so Gradle does not write the signing values to disk.
- **CI.** The `tv` and `wire` jobs of `.github/workflows/ci.yml` run `pnpm tv:prebuild`, then `pnpm tv:build` (tv) and `pnpm tv:e2e:build` (both). The `tv` job uploads `app-release.apk` as `octave-tv-release-apk`. `actions/setup-java` (temurin 17) provides `keytool`. The SDK build-tools on the runner already provide `aapt2`, and `apksigner` sits in the same directory (local SDK: `build-tools/37.0.0/apksigner`).
- **The key exists.** The owner's request of 2026-11-23, relayed by the coordinator, says the key has been created. The build may read only the key's location, from an environment variable or an ignored local file, and never the key or its password.
- **The ID was the owner's decision.** It is `cloud.jellyscale.octave` (`docs/specs/decisions-owner-inbox-2026-11-22.md` §1). The Product Owner placed "the Kotlin package names under `dev.octave` stay" (`tasks/product-owner-log.md:401`). Its count of files holding the old ID left out "the specs and the task files" (line 400).

## Approach

### The key and where the build finds it

- One environment variable, `OCTAVE_SIGNING_PROPERTIES`, holds the absolute path of a Java properties file outside every checkout. That file holds `storeFile`, `storePassword`, `keyAlias` and `keyPassword`. The variable is set in the shell or in `mise.local.toml` (already gitignored, `.gitignore:22`, and already used for `OCTAVE_DEV_SERVERS`). For agents' worktrees, it can go in the owner's user-level mise config.
- The repository holds only the variable's name. The build reads the location from the variable and the key and passwords from the owner's file. The owner confirmed this shape (open question 1, `docs/specs/decisions-owner-chat-2026-11-23.md` section 1).
- `signingProblems` returns one line per missing piece, for example `ERROR tv build: OCTAVE_SIGNING_PROPERTIES is not set; …`, `…names a file that does not exist`, `…has no keyPassword`, `…storeFile does not exist`, `…is inside the repository`. A line never prints a value or the path, because a home-directory path can hold the owner's name.
- The Gradle guard repeats the essential checks (variable, file, four keys, store file), so a hand-run `./gradlew assembleRelease` also fails. With no key the release `signingConfig` is `null`, never `debug`, so even a bypassed guard yields an unsigned APK, not a debug-signed one.
- The guard acts only when the task graph holds a release packaging task (`packageRelease`, `assembleRelease`, `bundleRelease`). `pnpm tv:native:test` and debug builds therefore need no key. The implementer shows this by running `pnpm tv:native:test` with the variable unset.
- Debug and `debugOptimized` stay on the debug key. They are debuggable, and item 4 keeps them off a real TV.

### CI's key

Each `tv` and `wire` job makes a throwaway key with `keytool` (JDK 17 from `setup-java`). It gets a random password, sits in `$RUNNER_TEMP/octave-signing/`, and is never uploaded or cached and never reused across runs. The emulator builds and the `octave-tv-release-apk` artifact are signed with it.

That artifact is therefore not the debug certificate, and `pnpm tv:apk:check` passes on it. It also cannot update the owner's private-key install on the Shield, because Android refuses an update with a different signer. CI never holds the owner's key. Locally, `node scripts/tv-signing.mjs --throwaway <dir>` makes the same kind of key for emulator-only work, and `docs/commands.md` says such builds never go on a real TV.

### The certificate check

`apksigner verify --print-certs` is run with `newestBuildTool(androidSdk(), "apksigner")`. The judge reads every `Signer` line, which covers both the `V2 Signer:` and the `Signer #1 certificate` forms. It fails closed on output it cannot read.

The pinned SHA-256 is the template's (Facts). Its comment names the source command, `keytool -list -v -keystore apps/tv/android/app/debug.keystore -storepass android`.

### Real-TV installs

Before each `adb install`, `readInstallFacts` reads three things: the two emulator properties (with `getprop <name>`, as `tv-install-id.mjs` does), `aapt2 dump badging` for `application-debuggable`, and the certificate judge. On a device that is not positively an emulator, `installRefusal` returns a refusal line for a debuggable APK or one with the debug certificate. A device that cannot be read counts as not an emulator.

In `pnpm tv:e2e` on such a device, the cleartext and resolved-address stages are skipped with recorded lines in `release-evidence/tv/` (`e2e-cleartext.txt` and `e2e-resolved-address.txt`, saying "skipped, the device is not an emulator"). In CI the skip is a failure. The rest of the run, including the conformance suites T3-17 needs, still runs on the Shield.

`tv:smoke` and `tv:wire` install release-type APKs. Their guard refuses only a debuggable or debug-signed one. Since CI's own APKs are throwaway-signed, the CI emulator runs pass through the guard on the emulator branch either way.

### The application ID

- `app-identity.ts` sets `ANDROID_APPLICATION_ID = "cloud.jellyscale.octave"` and drops the "placeholder until T11-01" note.
- `app.config.ts` passes `android.package: "dev.octave.tv"`. Expo then writes `namespace 'dev.octave.tv'` and keeps the activity and application classes in that package, so the R8 keep rule, D7, D8 and the dex check's prefix are unchanged.
- The signing plugin gets the ID as its `applicationId` option from `app.config.ts` (which imports the core's constant; the plugin holds no ID literal and throws when the option is missing or malformed) and appends `android { defaultConfig { setApplicationId("<id>") } }` after Expo's block. It runs after `defaultConfig`, so it wins. Expo's regex needs a quote right after `applicationId` and whitespace or `=`, so it does not rewrite this form, whatever order the mods run in (unverified; `AppIdentityTest` and the badging check fail if it does not hold).
- The packaged manifest's `package`, the `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` permission and the provider authorities follow the application ID. The aapt2 resource table's `Package name=` is recorded from the real build (unverified whether it follows the namespace or the ID).

### Which occurrences change

An occurrence of `dev.octave.tv` changes only where it is the application ID. That covers a package name, a process name, a component's package half, an ID-derived permission or authority, or an assertion on `ANDROID_APPLICATION_ID`. It stays where it is a Kotlin class or package name, such as `dev.octave.tv.MainActivity`, `MainApplication`, `BackupAgent`, `Probe`, `Taker`, `Mixed` or `Listener` in the dex tests and fixtures.

### Documents

`docs/security.md` §1 gets a new "Release signing" subsection. It says:

- every release and e2e build is signed with a key named through `OCTAVE_SIGNING_PROPERTIES` and never with the template's debug key;
- a build with no key fails;
- the owner's key signs builds for a real TV, and each CI job signs with a throwaway key of its own;
- the certificate check runs in `pnpm tv:apk:check` and before `pnpm tv:e2e` installs;
- every install script refuses a debuggable or debug-signed APK on a device that is not positively an emulator;
- an APK signed with another key cannot update the owner's install;
- not covered: a hand-run `adb install`, and an APK signed with a throwaway key going onto the Shield as a first install.

Two claims-table rows name the tests of items 2 to 4. `docs/commands.md` gets the variable, the throwaway command, the real-TV rule, and that `pnpm tv:e2e` on a real TV skips the two probe stages.

## Risks and out of scope

- **Mod ordering.** If Expo's `setPackageInBuildGradle` ran last and matched `setApplicationId(`, the ID would revert. The regex does not match that form, and `AppIdentityTest` plus the badging check catch it either way.
- **Template drift.** A later Expo template that changes the release `signingConfig` line makes the plugin throw at prebuild, which fails closed.
- **The Gradle daemon** holds the passwords in memory for its lifetime. That is the same process trust as the rest of the build and is accepted.
- **A throwaway-signed artifact as a first install on the Shield** is not refused, since item 4 names debuggable builds only. It cannot replace a private-key install, and the reverse is also true. Pinning the owner's certificate digest for real-TV installs is out of scope and goes to `tasks/backlog.jsonl`.
- **A hand-run `adb install`** cannot be refused. `docs/commands.md` and `docs/security.md` say so.
- **`pnpm tv:e2e` on the Shield** no longer runs the two probe stages. T3-17 item 2 asks only for the conformance suites.
- **Concurrent edits.** This task touches many `scripts/tv-*` tests. The coordinator runs it when no task changing the same scripts is in flight (`tasks/product-owner-log.md:400`).
- **Out of scope:** the Play upload key (T11-04), the store listing (T11-01), and renaming Kotlin packages.

## Decisions

- The key is named through one environment variable pointing at a properties file outside the repository. The password is never in the repository, the environment or argv. The owner chose this (option A) in `docs/specs/decisions-owner-chat-2026-11-23.md` section 1.
- CI signs with a throwaway key made in each job and never holds the owner's key.
- The application ID and the Kotlin package are split by keeping `android.package` as the Kotlin package and setting `applicationId` in the plugin. The alternative, setting `android.package` to the new ID and moving the Kotlin files back, would re-implement Expo's package refactor.
- On a real TV, `pnpm tv:e2e` skips the debuggable probe's stages instead of installing it.
- The certificate check runs outside `E2E_APK_CHECKS`, which is frozen by T3-31, following T3-33.

## Open questions

1. Answered (owner, option A, `docs/specs/decisions-owner-chat-2026-11-23.md` section 1). For the record, the question was: what does the location you give the build point at? (A, recommended) A properties file you keep beside the keystore, outside every checkout, holding the keystore path, the alias and both passwords. The build reads only that file's path from `OCTAVE_SIGNING_PROPERTIES`, and agents and `pnpm tv:build` can sign without asking you. (B) The keystore alone, with the password typed at each build for a real TV. Builds for the TV then need you at the keyboard, and the password passes through the build's environment. (C) The keystore, with the password read from the desktop keyring. This adds a keyring tool to the build. The actual path is never written into the spec or the repository, and it is set only on your machine.
