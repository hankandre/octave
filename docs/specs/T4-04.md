## Goal

A viewer whose server has no Quick Connect, or who prefers to type, signs in with a username and password using the remote alone:

1. The Quick Connect step offers **Use a password** as a secondary action. A server with Quick Connect off still opens straight on the password step, as T4-03 built.
2. The password step, "Who is signing in?", has a Username field, a Password field, a Show password switch, **Sign in** and **Change server**. The fields use the system keyboard, and the keyboard's action key on the password field signs in.
3. A wrong name or password shows the copy table's sentence and keeps the username. Every other failure shows Octave's fixed sentence for it.
4. The password lives in React state only while it is typed. It is cleared when the request returns, whatever the answer. It is never logged, stored or put in a URL.
5. A finished sign-in hands `{ gateway, serverName }` to `AppRoot` through the same `onSignedIn` as Quick Connect, so Home opens.
6. Whether a password route is offered comes from one sign-in methods value. It defaults to offered, so T10-06 can hide it for a server that says it has no password sign-in.

**The core**

- `gateway.login(username, password, signal)` runs `requireTransportConsent()` first. It then derives the DeviceId from the install id, the server id and the username, sends `transport.signIn({ kind: "password", username, password })` and starts the session (`gateway.ts:302-308`, `:362-379`). An unconfirmed private-LAN plain-HTTP server throws `SignInFailure("not-confirmed")` before any request (`:294-300`). A transport failure reaches the caller as a `TransportError` with its `code` and, for `status`, the HTTP status (`gateway.ts:1117-1120`; `packages/core/src/ports/transport.ts`). `logout()` clears local state, then ends the session (`gateway.ts:392-406`).
- The app's transport rejects with `cancelled` as soon as the signal aborts. A native sign-in that succeeds after its abort is ended, so no session is left behind (`apps/tv/src/host/transport.ts:8-10, 47-49, 116-118`).
- `serverChoiceFailure` and `quickConnectFailure` read only `name`, `kind`, `code` and `status`, never `message` (`packages/core/src/domain/server-choice.ts:65-71`; `domain/quick-connect.ts:39-58`). A password failure follows the same rule (D4).

  - the sign-in methods value;

- **T4-06:** several accounts and Add account. The password DeviceId already differs per username (`gateway.ts:305`), so a second account by password does not replace the first's token. Weighing that is T4-06's.
- **T4-07:** the password wire test against Jellyscale and both Jellyfin versions.
- **T10-06:** what a server says about its sign-in methods, and filling `signInMethods` from it. It also owns the dead end when both routes are hidden (backlog 400).

### D2. No native work

The password credential is a `signIn` kind today (header). Checked against decision 0005's surface (`docs/security.md:34`, "`signIn` | origin, DeviceId, and a password credential or a Quick Connect secret") and `SIGN_IN_PASSWORD_KEYS` (`SessionTransport.kt:260`). No method, event, argument or route changes. So this is not an architecture change, and `touchesNative=false`.

### D3. "Use a password" on the Quick Connect step

- **Its own hand-off.** It is drawn only when the flow gives the step `choosePassword`. That is a new optional prop, distinct from `openPassword`.
- **Why two props.** The two hand-offs return to different places. Back from a password step the viewer *chose* goes back to the Quick Connect step. Back from one the server *forced* (Quick Connect off) goes to step 1, as T4-03 fixed (`sign-in-password-route.test.tsx:103-125`). A step that called one function for both could not tell the flow which.
- **The frozen cases.** T4-03's frozen step tests give only `openPassword`, so they draw no "Use a password", and their focus and button cases stay true as written (Facts). This is a consequence of the split, not its reason. No frozen-test ruling is needed.
- **Where it sits.** "Use a password" is `secondary`, `testID` `sign-in-use-password`. It comes after a failure's retry button and before Change server.
- **Focus.** It takes `hasTVPreferredFocus`, the opening focus (`DESIGN.md:358`; T4-03 C4). Change server keeps the preferred focus only when "Use a password" is not drawn. A failure still focuses its retry (`quick-connect-step.tsx:93-96`). The retry press sends focus to "Use a password" when it is drawn, and to Change server otherwise. That keeps the frozen case at `:244-261`, and it keeps a select pressed by habit from leaving for step 1.
- **Hidden in a redirect.** The password post would hit the same redirect, and the gateway refuses every 3xx. "Only another address can help" (`quick-connect-step.tsx:26`).
- **Pressing it.** It calls `choosePassword()`. The flow replaces the step, and the unmount stops the run (`:65`). A sign-in in flight at that moment is logged out by the run (`docs/specs/T4-03.md` D2, step 7).

### D4. Failures

`passwordSignInFailure(error): PasswordSignInFailure | undefined` reads only `name`, `kind`, `code` and `status`:

| Answer | Result | Sentence (D9) |
|---|---|---|
| `TransportError("status", 401)` | `wrong-credentials` | "That username and password didn't work." (`DESIGN.md:465`) |
| `TransportError("status", 403)` | `refused` | "This account can't sign in right now. Try again later. If it still doesn't work, ask the server's owner." (R2) |
| `network`, `timeout` | `unreachable` | "Sign-in, unreachable" with `chosen.address` (`:466`) |
| `SignInFailure("redirect")`, transport `redirect` | `redirect` | "Sign-in, redirect" (`:470`) |
| `cancelled`, `AbortError` | `undefined` (nothing shown) | none |
| anything else: other statuses, `unexpected-response`, `refused`, `SignInFailure("not-confirmed")` | `other` | "Sign-in, anything else" (`:469`) |

- **"not-confirmed" maps to `other`.** The flow confirms a private-LAN plain-HTTP server on step 1 (T4-02 D8a), so the step cannot reach it unless a confirmation was forgotten. The gateway sends nothing in that case (`gateway.ts:303`), and the test proves no `signIn` is sent.
- **Why 403 gets its own code.** On both servers a 403 is not a wrong password. On Jellyfin it is a disabled or locked-out account, a refused device, or the session cap. On Jellyscale it is the "too many failed sign-ins" bound (Facts). "Something went wrong. Try again." would send the viewer to retry into the same lock. Its sentence is R2's.
- **What the step does not know.** The transport hands back the status alone, so the step cannot tell a lock that ends from an account only the server's owner can open, and it does not read Jellyscale's `Retry-After`. The sentence is written to be true of every cause (R2).

### D5. The step: fields, keys, focus

`PasswordStep({ chosen, changeServer, onSignedIn })`, root `testID` `sign-in-password-step`, drawn in `SignInStepFrame` (heading and origin chip). Top to bottom:

1. Heading "Who is signing in?" (`DESIGN.md:360`; C1).
2. **Username**, a `TextField` with `testID` `sign-in-username`:
   - props: `label` "Username", `still`, `autoCapitalize="none"`, `autoCorrect={false}`, `importantForAutofill="no"`, `returnKeyType="next"`;
   - its `onSubmitEditing` sends focus to the Password field's frame through `focusView` (C3).
3. **Password**, a `TextField` with `testID` `sign-in-password`:
   - props: `label` "Password", `still`, `secureTextEntry={!shown}`, `keyboardType={shown ? "visible-password" : "default"}`, `autoCapitalize="none"`, `autoCorrect={false}`, `importantForAutofill="no"`, `returnKeyType="go"`, `onSubmitEditing={submit}`;
   - `visible-password` is Android's input type for a password shown in clear, which asks the keyboard not to learn or suggest it (React Native's `ReactTextInputManager.kt:758-761`; `secureTextEntry` false only removes the hidden-password type, `:697-708`). That the emulator's keyboard still opens and types with it is checked at verify (D10). If it does not, the implementer returns the question; it does not drop the prop quietly.
4. **Show password**: a row with the label `Text` "Show password" (`typeLabel`, `text2`) and a `Switch` (`testID` `sign-in-show-password`, `accessibilityLabel` "Show password"). `shown` is `useState(false)`, so it is off on every mount (item 6; `decisions-product-owner-2026-11-26.md` §3; C8). A Switch is a compact control and lifts (`DESIGN.md:401`).
5. The status line `sign-in-status` "Loading…" while a sign-in is in flight (T4-02 C6; C5), or the failure sentence `sign-in-failure`. Both use `accessibilityLiveRegion="polite"`, so each change is announced once (`DESIGN.md` §11, rule 6).
6. **Sign in** (`primary`, `testID` `sign-in-submit`), the screen's one primary (`DESIGN.md` §7.19).
7. **Change server** (`quiet`, `testID` `sign-in-change-server`), last, as on the Quick Connect step (C1).

**Focus.** The step opens on the Username field (`hasTVPreferredFocus`). The design names a primary action for this step, but focusing Sign in over two empty fields would be a press wasted. "Screens without one focus their first … field" is the closer reading (`DESIGN.md:148`; C2).

After a failure, focus goes to the Password field, which is now empty. A redirect focuses Change server instead.

Both fields are `still`: they fill the column, and a field never scales (`DESIGN.md:342`; T4-02 C10; backlog 387). Nothing is clipped: the frame does not scroll, and the column shares the heading's left edge (T4-02 C10, C11).

**Submit** (`submit()`, from Sign in or the password field's action key):

- With a sign-in in flight, it does nothing.
- With an empty username, it sends nothing and focuses the Username field (C4).
- An empty password is sent: an account may have none (Facts).
- The username is sent as typed, not trimmed. Both servers match names case-insensitively (`users.go:91`, `lower(name) = lower($1)`). Trimming would change what the viewer typed (C4).

The fields stay enabled while a sign-in runs. Disabling a focused control on Android TV drops focus. A second submit is ignored instead.

**Keys.** There is no new remote key. Select on a field opens the system keyboard (TextField). The keyboard's action key fires `onSubmitEditing`. `still` keeps the field from scaling.

### D6. The sign-in methods value (item 5)

### D8. Where the password goes

- **While typing:** `useState` in `PasswordStep`, the controlled `value` of the Password field. This is the only place it is held. Controlled is required: `TextField` takes `value` (`text-field.tsx:14`).
- **On submit:** `usePasswordSignIn` makes a new `AbortController` and calls `gateway.login(username, password, signal)`. The password crosses once into the core, as an argument. It crosses once into Kotlin, as `signIn`'s argument (`transport.ts:103-114`; `docs/security.md:15`). It is never put in a URL: Kotlin sends it in the JSON body of `POST /Users/AuthenticateByName` (`SessionTransport.kt:41-43`), and the core builds no request for it.
- **When the request returns,** whatever the answer:
  - The hook sets the password state to `""` (item 4). On success it does so before calling `onSignedIn`, because `SignInApp` may stay mounted (as in tests).
  - On success it calls `onSignedIn({ gateway: chosen.gateway, serverName: chosen.serverName })` unless the signal was aborted. `AppRoot` then swaps to `SignedInApp` (`app-root.tsx:15-16`).
  - A success after an abort calls `gateway.logout()` once, as the Quick Connect run does (`quick-connect-sign-in.ts:101`). The app's transport already ends a late native sign-in (`transport.ts:116-118`). The step's check covers a transport that does not.
- **Unmount** (Back, Change server, or the swap) aborts the controller. A `cancelled` rejection shows nothing (D4).
- **Never logged.** The step and the hook have no `console` call (`pnpm lint:logs`). A failure is mapped by code alone (D4), and no error object is shown or kept.
- **Never stored.** The step gets no store. It writes no remembered server, no preference and no confirmation. `RememberedServers` is written on step 1 only (`use-server-choice.ts`).
- **Show password** changes only `secureTextEntry` and the field's `keyboardType` (D5). It does not copy the value anywhere.
- **Autofill.** Both fields carry `importantForAutofill="no"`, so Android's autofill framework is not asked to fill them or to save what was typed (R3).
- **What stays outside Octave's reach:**
  - JavaScript strings cannot be zeroed. The cleared string waits for Hermes's collector. That is no worse than the Quick Connect secret, and `docs/security.md` says so in the line milestone 3 adds.
  - The system keyboard sees what is typed, as on every Android TV app. `docs/security.md` §5 ("What is not protected") gets one line for it.

- **C1. Layout.** The step reads top to bottom:
  1. "Who is signing in?" and the origin chip;
  2. Username;
  3. Password;
  4. the Show password row;
  5. the status or failure line;
  6. Sign in (primary);
  7. Change server (quiet, last, as on the Quick Connect step).
- **C2. Opening focus.** The Username field, not Sign in.
- **C3. Keys.** The Username field's action key is "Next" and moves focus to the Password field. The keyboard closes, and select opens it again; that extra press is the owner's to judge on the TV (R1; backlog 403). The Password field's action key is "Go" and signs in.
- **C4. An empty username.** Sign in sends nothing and focuses Username, with no sentence. An empty password is sent. The username is sent as typed.
- **C5. While signing in.** "Loading…" in the status line; a second press does nothing; the fields stay enabled.
- **C6. Failures.**
  - A 403 gets a new sentence: "This account can't sign in right now. Try again later. If it still doesn't work, ask the server's owner." (R2).
  - After any failure the password is cleared, the username kept, and focus goes to the Password field; a redirect focuses Change server.
  - The sentence is `text1` with no icon, as on the Quick Connect step.
- **C7. "Use a password" on the Quick Connect step.** It is secondary, between a failure's retry and Change server, and takes the opening focus. It is hidden in a redirect. After "Get a new code" or "Try again", focus goes to it.
- **C8. Show password.** A row with the label "Show password" and the Switch, showing "On" or "Off", off on every open.
- **C9. Back to Quick Connect.** Back from a password step opened by "Use a password" returns to the Quick Connect step with a new code, focus on "Use a password".
- **C10. Back during a sign-in.** It cancels the sign-in and leaves the step; it does not stay.
- **C11. No "Quick Connect is off" sentence.** The password step does not show it; the §10 row is marked not shown.
- **C12. Autofill and a shown password.** Neither field is offered to Android autofill. While Show password is on, the field tells the keyboard it holds a visible password (R3).
