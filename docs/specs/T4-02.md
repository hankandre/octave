## Goal

A signed-out viewer can pick the server to sign in to, with the remote alone:

1. The first sign-in step, "Where is your server?", lists remembered servers, then the servers found on the home network, with focus on the first; one press chooses one. With none listed, the Server URL field shows and Search again has focus.
2. Choosing or typing a server probes it with no credentials. A public plain-HTTP address and an https address written with a non-ASCII host are refused before any request. A discovered server must report the id it was discovered with. A private-LAN plain-HTTP server asks once per server and origin, with Cancel focused.
3. Every failure shows the copy table's sentence for its code, never server or transport text.
4. A chosen server is handed to the next step, which shows its exact origin; Back never takes a signed-out viewer to Home or the rail.

The task builds the step, the signed-out composition and the hand-off that T4-03 (Quick Connect) and T4-04 (password) plug into. `App.tsx` does not mount it yet (D2, confirmed in R7); T4-03 mounts it with `SignedInApp`.

**The core's connection code**

- `normalizeServerUrl` (`packages/core/src/jellyfin/gateway.ts:102-123`) runs in the `JellyfinGateway` constructor (`:219`), before any request: `new URL` (`:106`, else `invalid-address`), scheme http or https (`:110-112`), no user info (`:113-115`), then `classifyServerAddress` and a refusal of plain HTTP to a public host as `public-http` with `PUBLIC_HTTP_REFUSED_MESSAGE` (`:116-119`). An https address with a non-ASCII host passes: `classifyServerAddress` calls it `public` (`packages/core/src/domain/host-class.ts:37-38`) and https is admitted for every host. That is the gap `tasks/product-owner-log.md:277` names ("today the native client refuses it as `invalid-address` and the core lets it sign in").
- `PUBLIC_HTTP_REFUSED_MESSAGE` (`gateway.ts:95-96`) is word for word the copy table's "Sign-in, refused plain HTTP" row (`DESIGN.md:434`).
- `connect(signal?)` (`gateway.ts:228-253`) is the probe: tokenless `GET /System/Info/Public` with the DeviceId `octave-unauthenticated` (`:69`, `:229-233`). It throws `unexpected-response` for a body with no string `Version` (`:234-236`), `unsupported-version` below 10.11 with the message `Octave needs Jellyfin 10.11 or newer; this server reports ${version}.` (`:237-241`, the server's string in the error: item 10), and `unexpected-response` when a private-LAN plain-HTTP server reports no `Id` (`:242-244`). It returns `ServerConnection { name, id?, version, hostClass, needsUnencryptedConfirmation }` (`:246-252`; `packages/core/src/domain/server-connection.ts:4-13`).
- Transport failures leave `connect` through `failure()` (`gateway.ts:1103-1106`): a `redirect` code becomes `SignInFailure("redirect")` (`:131-137`); anything else is rebuilt by `redactTransportError`, which keeps `code` and `status` and drops the message's context (`packages/core/src/transport-error.ts:36-57`). A 3xx or status 0 answer is `redirect` as well (`gateway.ts:127-129`, `:1133`); a 4xx or 5xx is `TransportError("status")` (`:1136`).
- The transport codes are `network`, `timeout`, `redirect`, `cancelled`, `refused`, `unexpected-response`, `status` (`packages/core/src/ports/transport.ts:73-80`). The pre-sign-in routes are four, the probe first (`:66-71`).

The store's default is a **new** `MemoryLanHttpConfirmations` per gateway (`:215`), so two gateways for one server ask twice unless the caller passes one shared store. ### D3. The step

Top to bottom, inside the title-safe inset (`DESIGN.md` §6), with no rail (`chromeOf` already gives none for sign-in, `routes.ts:113-115`):

1. The heading "Where is your server?" in `typeTitle`, `accessibilityRole="header"` (`DESIGN.md:334`, rule 11.6 at `:486`).
2. **Remembered rows**: one `ServerRow` per remembered server, name in `typeLabel` and address in `typeMono`. No section title (PO call C3).
3. **"On this network"** (`typeHeading`), only when discovery found a row not already remembered; one `ServerRow` per found server: name, address in `typeMono`, "Advertised by {advertisedBy}" in `typeMeta`, and, when `conflicting`, the conflict line in `danger` (PO call C4).
4. **Enter address** (`secondary`), only when at least one row is listed; it reveals the field and moves focus to it. With no row listed it is not drawn, because the field already shows (`DESIGN.md:334`, "Without any found server, the field shows").
5. **The Server URL field** (`TextField`, label "Server URL"), shown with no row listed or after Enter address. `keyboardType="url"`, no autocapitalise or autocorrect, `returnKeyType="go"`; the keyboard's action key submits (`onSubmitEditing`). There is no Connect button (PO call C5).
6. **Search again** (`quiet`). Above the field when nothing is listed, so it takes the opening focus there (item 2); below the rows otherwise.
7. One status line under the field: the failure sentence (`accessibilityLiveRegion="polite"`, announced once per change, rule 11.6) or, while a probe runs, "Loading…" (PO call C6).

Focus (`DESIGN.md:148`, "Opening a screen focuses its primary action. Screens without one focus their first card, field, or section"; item 1, item 2):

- On entry, with rows: the first row (remembered first). With none: Search again.
- While discovery runs and nothing is remembered: `Skeleton` rows (after 150 ms, `DESIGN.md` 7.17), then the rule above. When remembered rows exist they show at once and keep focus; found rows arrive below them and focus does not move (`DESIGN.md` principle 8, `:373`).
- After Search again settles: the first row, or Search again.
- After a failure: on the control that started the probe (the row, or the field's frame for a typed address, keyboard closed). The status line shows the sentence.
- After the dialog closes by Cancel or Back: the control that started the probe (`DESIGN.md:290`, "Focus is trapped and restored on close").
- While a probe runs, the controls stay enabled (disabling the focused view drops focus on Android TV, unverified on this stack) and a second select is ignored.
- Every focusable is at least 64 px tall (rule 11.3, `:483`); tokens only (`AGENTS.md`, Design).

The D-pad alone: Up and Down move through rows, Enter address, the field and Search again in that order; select chooses or opens the keyboard; Back is D11. No platform picker or dialog.

**Item 2's reading (R1, ruled).** Item 2 reads "Enter address reveals the address field" in the no-server case, but DESIGN 7.20 and item 9 say the field shows there. The product is DESIGN's: with nothing listed the field shows, Search again has focus, and Enter address is not drawn; with rows listed, Enter address reveals the field.

**A typed address with no scheme.** `192.168.1.5:8096` or `nas.local:8096` fails `new URL` or reads as another scheme (`gateway.ts:106-112`), and most people type it that way. Ruled (R8, call C7): when the trimmed text has no `://`, the step prepends `http://` if `classifyServerAddress("http://" + text)` is `loopback` or `private-lan`, else `https://`. This adds no acceptance of public plain HTTP (a public host gets https), and a private one still meets the confirmation. The probe and the chip use the completed address, so the viewer sees exactly what was tried. The completion is the step's, in one pure function (`completeAddress` in `server-choice.ts`); the gateway's rules are unchanged and still judge the completed address, the Unicode-host refusal included.

### D5. The probe: `probeServer`

`packages/core/src/jellyfin/server-probe.ts`:

```ts
type ProbeCandidate = { address: string; discoveredId?: string };
type ProbeOutcome =
  | { kind: "chosen"; gateway: JellyfinGateway; connection: ServerConnection }
  | { kind: "confirm"; gateway: JellyfinGateway; connection: ServerConnection }
  | { kind: "failed"; failure: ServerChoiceFailure }
  | { kind: "cancelled" };
function probeServer(open: (address: string) => Promise<JellyfinGateway>, candidate: ProbeCandidate, signal: AbortSignal): Promise<ProbeOutcome>;
```

In order, and the refusal points:

1. `open(address)`: the app passes `(url) => services.gateways(url, { confirmations: services.confirmations })`. The constructor refuses, **before any request**: `invalid-address`, `public-http` (`gateway.ts:116-119`), and the new `unicode-host` (D9). A rejection here (the install id missing, `host/gateway.ts:31-32`) is `other`.
2. `gateway.connect(signal)`, the one request: tokenless `GET /System/Info/Public` (`gateway.ts:229-233`). No `signIn`, no other route.
3. For a found row only: `sameServerId(discoveredId, connection.id)` (`server-discovery.ts:42-46`), else `failed: not-the-discovered-server`. This runs before the confirmation, so a spoofed reply never reaches the dialog (`ARCHITECTURE.md:107`: "refused unless the probe reports the discovered `Id`"). A remembered row is not id-checked: the confirmation is keyed by `(Id, origin)`, so a different server at a remembered origin asks again (decision 0001 §7, `0001-private-lan-http.md:36`).
4. `connection.needsUnencryptedConfirmation` gives `confirm`; otherwise `chosen`.
5. Any throw maps through `serverChoiceFailure` (D7); an abort gives `cancelled` and shows nothing.

`probeServer` never reads `error.message`. The step, on `confirm`, opens the dialog; "Connect without encryption" calls `gateway.confirmUnencryptedConnection()` (`gateway.ts:258-262`) and hands on; Cancel or Back records nothing (the gateway has not called `remember`, so `forgetUnencryptedConnection` is not needed). On hand-off the step calls `remembered.remember({ id, name, address: gateway.serverUrl })` when the probe reported an id; with no id (an https server that omits it) nothing is remembered, since saved servers are keyed by id (`DOMAINS.md` §1 rule).

### D6. Where the confirmation and the remembered servers live

- **The confirmation**: one `MemoryLanHttpConfirmations` per app launch, created in `host-sign-in.ts` and passed to every gateway the step builds (`host/gateway.ts:20-24, 33`). That makes item 4's "asks once per server and origin" hold across Change server, Search again and a re-typed address, which the constructor's per-gateway default does not (`gateway.ts:215`). Keyed by `{ serverId, origin }` (`lan-http-confirmations.ts:7-10`); the origin includes the port (decision 0001 §4).
- **Remembered servers**: `RememberedServers { list(): readonly RememberedServer[]; remember(server: RememberedServer): void }` with `RememberedServer = { id: string; name: string; address: string }`, most recent first, one entry per id (a later choice replaces the earlier one); `MemoryRememberedServers` in `packages/core/src/remembered-servers.ts`, one instance per launch in `host-sign-in.ts`. It holds no token and no user (`ARCHITECTURE.md:256`, I4).
- **Persistence is not in this task** (R5). Both records hold a URL; the preferences record refuses URLs by rule (`preference-store.ts:10-12`) and its native store accepts only that record's shape (`modules/preferences/src/index.ts:5-7`), so persisting needs either a new native method (an architecture change, `AGENTS.md`) or T4-05's encrypted account record. Until T4-05 nothing survives a relaunch anyway: the viewer signs in again each launch. `docs/security.md:164` changes from "Planned (T4-02)" to what this task builds (in memory, one launch) and says that persistence has no owning task yet (the backlog line of R5).

### D7. Failures and their sentences

`ServerChoiceFailure` codes and the sentence each shows (`sign-in-copy.ts`):

| Code | From | Sentence |
|---|---|---|
| `unreachable` | TransportError `network` or `timeout` | "Couldn't reach {address}. Check the address and that the server is running." (`DESIGN.md:433`); `{address}` is the gateway's `serverUrl`, or the text as completed by D3 when no gateway was built |
| `refused-plain-http` | SignInFailure `public-http`; TransportError `refused` when the address's scheme is `http` (item 12) | `DESIGN.md:434` (= `PUBLIC_HTTP_REFUSED_MESSAGE`) |
| `unicode-host` | SignInFailure `unicode-host` | "This address uses characters Octave can't check. Type the server's plain address instead." (`DESIGN.md:435`) |
| `redirect` | SignInFailure `redirect` | "The server answered with a redirect, which Octave does not follow. Enter the server's final address instead." (R2) |
| `unsupported-version` | SignInFailure `unsupported-version` | "This server's version isn't supported. Octave needs Jellyfin 10.11 or newer." (R2) |
| `not-an-address` | SignInFailure `invalid-address` | "That isn't a server address. Type it like 192.168.1.5:8096 or media.example.com." (R2, new wording) |
| `not-the-discovered-server` | the id check of D5 | "The server at this address is not the one that answered on your network. Octave did not connect. Enter the server's address yourself." (R2) |
| `other` | `unexpected-response`, `not-confirmed`, TransportError `status` (any), `unexpected-response`, `refused` on https, a gateway factory rejection, anything else | "Something went wrong. Try again." (`DESIGN.md:436`) |
| (none) | TransportError `cancelled` / `AbortError` | nothing shown |

`serverChoiceFailure` reads only `kind` on a `SignInFailure` and `code` on anything else (as `classifyTransportError` does, `transport-error.ts:11-27`), never `message`. Domain code, so it duck-types the error instead of importing `ports/` (`DOMAINS.md` dependency rule 1).

**Why `refused` on plain HTTP is item 12's sentence.** In a release build, the native refusals a plain-HTTP address the core admitted can meet are `resolved-public` (T3-20) and, if the parsers ever disagreed, `invalid-address`; both mean "Octave will not connect to this plain-HTTP address", which the refused-plain-HTTP sentence says (`decisions-product-owner-2026-11-26.md` §2: "It gets no sentence of its own"). In a development build, `development-build` also arrives as `refused` (`docs/security.md:60`), so a developer probing an unlisted plain-HTTP server reads this sentence; `docs/commands.md:21` already tells developers why, and the sentence does not name the cause wrongly for a viewer of a release build.

- **Which text is "the exact server origin".** The chip shows `gateway.serverUrl`: the normalised address, which begins with `gateway.origin` (scheme, host and non-default port exactly) and keeps a base path such as `/jellyfin`, because two servers can share an origin. The confirmation is keyed by the origin (`gateway.ts:261`), which the chip shows in full.

### D9. Unicode hosts (item 8)

- **Core.** In `normalizeServerUrl`, after trimming and **before** `new URL` (so Expo's partial IDNA on the device cannot change the answer, `docs/security.md:175`): if the text starts with `https:` (any case) and `hasPlainAsciiAuthority(text)` is false, refuse. The kind is `unicode-host` when the authority (the text after `https://` up to the first `/`, `?` or `#`) holds a character above U+007F, and `invalid-address` otherwise (a `%`, a backslash, user info: none of them is "characters Octave can't check" in the viewer's sense). Plain HTTP is unchanged: it is already `public-http` for a non-ASCII host (`gateway-non-ascii-host.test.ts`, frozen, T2-06), and the owner's decision is about https (`tasks/product-owner-log.md:278`). An `xn--` https host passes R1 and is admitted, as T2-06 already intended (`docs/specs/T2-06.md:86`).
- **Native.** No change: `ServerAddress.parse` step 2 refuses every R1 failure, https included (`ServerAddress.kt:33-34`). So the two refuse the same set by construction, and the fixture proves it on concrete vectors.
- **The shared fixture** `packages/core/tests/fixtures/https-hosts.json`: `{ "description": …, "refused": [...], "accepted": [...] }`. Refused, at least: `https://bücher.example`, `https://BÜCHER.example`, `https://ｍedia.example` (fullwidth m), `https://media。example` (U+3002), `https://naſ.example` (long s), `https://Kodi.example` (Kelvin sign), `https://bücher.example:8920/jellyfin`, `https://b%C3%BCcher.example`. Accepted: `https://xn--bcher-kva.example`, `https://XN--BCHER-KVA.example`, `https://media.xn--bcher-kva.example:8920/jellyfin`. Each refused vector also carries `"kind": "unicode-host" | "invalid-address"` for the core test. Escapes for non-printing characters, as `host-class-non-ascii.test.ts:8` does.
- **Tests.** The core test runs every vector through the constructor with a spy transport (0 calls for refused; the probe reaches the transport for accepted). `HttpsHostAgreementTest.kt` runs every vector through `ServerAddress.parse` (`refused` → `OctaveHttpException(INVALID_ADDRESS)`; `accepted` → no throw, host equal to the lower-cased host). If any accepted vector is refused natively (OkHttp's IDNA on a valid `xn--` label is **unverified**), the native engineer stops and returns it to the Product Owner rather than changing `ServerAddress.kt`.
- **The step.** The core refusal gives `unicode-host` and the sentence of `DESIGN.md:435`. The step does not pre-check; the gateway is the one gate.
