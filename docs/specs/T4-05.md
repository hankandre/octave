## Goal

The owner signs in once. On every later launch Octave opens Home with no sign-in screen. The token is kept only by Kotlin: in memory, and as one record per account encrypted under a key in the Android Keystore.

## Facts this spec rests on

- The module defines `signIn`, `request`, `endSession` (`OctaveSessionModule.kt:32-36`). `surface-allowlist.json` lists `restoreSessions` and `sessionEnded` as pending, both `T4-05`.
- `SessionRegistry` is a process-wide object, memory only (`SessionRegistry.kt:45`). `SessionRegistry.open(` appears in `SessionTransport.kt` only, and the frozen `DevelopmentBuildRefusalTest.kt:243-244` pins that.
- `SessionTransport.signIn` asks the development-server rule before it sends (`SessionTransport.kt:57`). `endSession` takes the entry first, then sends the logout (`:113-116`).
- The module's `http` package may import no Android class (`ModuleSurfaceTest.kt`, last test).
- The gateway holds `session`, `userId`, `userName`, `serverId`, `deviceId` (`gateway.ts:218-222`) and has no way to take a session it did not sign in.
- The DeviceId cannot be derived again at restore: a password sign-in derives it from the name as typed (`gateway.ts:305`), Quick Connect from `#quick-connect` (`:357`). Playback needs it (`:1067`, `:1084`). It is not a secret (`docs/security.md:15`).
- The core's `Transport` port has three members (`ports/transport.ts:59-64`). Many test doubles, some frozen, implement it.
- `AppRoot` shows sign-in until `onSignedIn`, then `SignedInApp` (`app-root.tsx`). `SignedIn` is `{ gateway, serverName }`. Nothing in the app calls `gateway.logout()` except the password step's late-answer path (`password-step.tsx:59`); no screen offers sign-out.
- `hostPreferences().useAccount` exists and nothing calls it (`host/preferences.ts:76`; T9-09's evidence).
- Backup is off app-wide and `bmgr backupnow` is refused for the app on the emulator (`docs/security.md` §6, T4-09's install-id stage).
- The session module's own `ModuleSurfaceTest.kt` pins three functions and is in no manifest. `scripts/tv-module-surfaces.test.ts` (frozen, T8-01) passes when a built member leaves `pending`, and accepts any task id for one that stays.
- `pnpm tv:smoke` installs with `adb install -r`, clears nothing, and expects sign-in's first step (`scripts/tv-first-focus.mjs:26-27, 111`). It already reads whether the device is an emulator (`readInstallFacts`).
- `minSdkVersion` is 24 (`docs/specs/T3-22.md:34`). `KeyGenParameterSpec.Builder` is API 23 (Android reference, read 2026-11-26).

## Approach

### D1. The record

- One file per account: `<noBackupFilesDir>/octave-sessions/<name>`. `<name>` is the hex SHA-256 of the server id, a line feed and the user id; the server's base URL stands in when the sign-in gave no server id. A new sign-in to the same account replaces the file.
- Bytes: a version byte `0x01`, the 12-byte IV, then the ciphertext with its 16-byte tag. The associated data is the file's name, so a record copied under another name does not open.
- Plaintext: UTF-8 JSON with exactly `server`, `deviceId`, `token`, `userId`, and optionally `userName`, `serverId`. Kotlin builds the header again at restore from the token, the DeviceId and the current client identity, so an app update changes the header's `Version` and not the record.
- A write goes to a temporary file and is renamed over the record, as `modules/preferences` does.
- **Unreadable** means: over 64 KiB, an unknown version, a failed tag, text that is not that JSON, another key, an empty token, or a `server` that `ServerAddress.parse` refuses. An unreadable record is deleted and not listed. A leftover temporary file is deleted.

### D2. The cipher

- `RecordCipher` has `seal(plain, associated)` and `open(sealed, associated)`; each returns null on any failure and carries no message.
- `KeystoreCipher`: provider `AndroidKeyStore`, alias `octave.session.v1`, AES, 256 bits, GCM, no padding, encrypt and decrypt only. No user authentication (decision 0005). Randomized encryption stays required, so the Keystore makes each IV. StrongBox is not asked for.
- The key is made on the first save. A key that is missing or fails makes every record unreadable (D1) and the next save makes a new key.
- A save that fails leaves the viewer signed in for this launch and not stored. No error code exists for it and none is added.
- The plaintext array is overwritten after use. Kotlin cannot clear the token's `String`.

### D3. Where the code lives

- `SessionStore` and `RecordCipher` sit in `http/`, beside the registry, in plain Kotlin, so they run on the JVM with a software AES-GCM cipher the tests supply.
- `KeystoreCipher` sits in `dev.octave.session.store`. It sees plaintext bytes and never a header or a session id.
- The registry stays the one process-wide index. A `SessionEntry` may carry its account: the base URL, the DeviceId, the user id, the user name, the server id and the record's name. `SessionRegistry.open` gains a defaulted parameter, so every frozen caller compiles unchanged.
- When a new sign-in replaces a record, older live entries that named it stop naming it, so ending an old session never deletes a newer record.
- `OctaveSessionModule` gives the transport a store over `context.noBackupFilesDir`. With no React context the transport has no store: nothing is saved or restored for that call.
- Nothing here logs. `toString` of the new classes is redacted, as the registry's are.

### D4. `restoreSessions`

- JavaScript: `restoreSessions()` takes nothing and resolves `{ sessions: [ { session, server, deviceId, userId, userName?, serverId? } ] }`. It never rejects on purpose and has no error value: a store that cannot be read gives an empty list.
- Kotlin, `SessionTransport.restore()`:
  1. Read each record that no live entry names (D1).
  2. Parse its address and call `servers.check`. A refusal skips the record and **keeps** it: a development build neither opens nor destroys it.
  3. Build the header and call `SessionRegistry.open`, here in `SessionTransport.kt`.
  4. Answer every live entry that carries an account, newest record first (by the file's modified time).
- A second call in the same process answers the same ids (`docs/security.md:55`), because the registry outlives the module instance.
- `server` is the base URL (decision 0005, T2-04 amendment), where the decision's table says `origin`. `deviceId` is new in the result. Both are stated in the amendment this task writes (Q2).
- It sends no request. Validation is the core's (D6).

### D5. Sign-in and sign-out

- `signIn`: after `SessionRegistry.open`, save the record. The result map is unchanged.
- `endSession`: take the entry, delete the record it names, then send the logout with the entry in a local value. The result is unchanged.
- `request` is unchanged. A 401 inside a session does not end it in this task (Q1).

### D6. The core

- `ports/transport.ts` gains `RestoredSession` and a separate port, `SessionRestore { restoreSessions(): Promise<readonly RestoredSession[]> }`. `Transport` keeps its three members, so no test double changes.
- `JellyfinGateway.adopt(restored)`: takes the session, user id, user name, server id and DeviceId. It throws when `restored.server` does not normalize to its own `serverUrl`. It asks no plain-HTTP confirmation: the confirmation was given before the sign-in that made this token, and only sign-in calls require it (`gateway.ts:303-347`).
- `JellyfinGateway.sessionStanding(signal)`: `GET /Users/Me`. A 2xx is `valid`. A 401 is asked once more; a second 401 is `revoked`. Anything else throws as today.
- `restoreSession({ restore, gateways, timeoutMs }, signal)` in `jellyfin/restore-session.ts`, on the newest listed session only:

| What happens | Outcome | The record |
|---|---|---|
| Nothing listed | `none` | n/a |
| The probe answers with another server id, an unsupported version, a redirect or an unusable answer | `none`; the token is never sent | kept |
| The probe cannot reach the server | `signed-in`, not validated (Q4) | kept |
| The probe passes and `sessionStanding` is `valid` | `signed-in` | kept |
| `sessionStanding` is `revoked` | `sign-in-again`, after `gateway.logout()` | deleted |
| `sessionStanding` throws | `signed-in`, not validated (Q4) | kept |

- `signed-in` carries `{ gateway, serverName }`; the name is the probe's, or the address's host when the probe did not answer. `sign-in-again` carries the gateway, the server's name and address, and the user name.
- The probe and the validation each get 5 s here, not the 15 s of `CONTROL_REQUEST_TIMEOUT_MS`, so a dead address delays Home by seconds (Q7). **[judgment]**
- The app's adapter (`host/transport.ts`) implements `SessionRestore`: it keeps only entries whose fields have the right types and whose id is 32 lower-case hex digits, and answers an empty list for a rejection or any other shape.

### D7. The composition root

- `AppRoot` takes an optional `restore` part. Without it, it behaves as today, so the frozen `app-root.test.tsx` holds.
- With it: the root shows the fixed line "Loading…" (`LOADING_LINE`) until the outcome arrives, then Home, sign-in's first step, or sign-in on the chosen server (D8). No sign-in control mounts before the outcome.
- A restore that rejects is `none`.
- `AppRoot` gives `SignedInApp` a `signOut` part: `gateway.logout()`, then `account.deactivate()`, then sign-in's first step. No screen calls it yet; Settings and "Who's watching?" will (T9-05, T4-06).

### D8. Back to sign-in with the server and user chosen

- `SignInApp` and `SignInFlow` take an optional `start: { chosen, username? }`. The flow then opens on the step after the server step, with that server's sign-in methods. Back and "Change server" go to the server step, as from any chosen server.
- `PasswordStepProps` gains an optional `initialUsername`. With it, Username starts filled, focus opens on Password, and the step starts **held**: an empty password is not sent until the viewer edits a field (T4-04 R7; backlog 410). The frozen T4-04 tests pass no name and see no change.
- The Quick Connect step shows the server as it does for any chosen server. No sentence says why the viewer is back (Q6).

### D9. The account's settings

- `App.tsx` wires `account: { activate: (gateway) => hostPreferences().useAccount(accountPreferenceSourceOf(gateway)), deactivate: () => hostPreferences().useAccount(undefined) }`.
- `AppRoot` calls `activate` when a sign-in finishes and when a restore ends `signed-in`, and `deactivate` in `signOut`. A rejection is dropped: `useAccount` keeps the defaults after a failed read.

### D10. The smoke test (backlog 397)

- On any other device it clears nothing. A real TV that holds a session then fails the unchanged oracle. `judgeFirstFocus` and its frozen test do not change.

### The device proof

- **Probe stage `stored-credential`** (the module's test APK, emulator only, as the two existing probes): with the real `KeystoreCipher` it saves a record with a canary token, checks through `KeyInfo` that the key came from the Keystore and needs no user authentication, reads every file of the probe's data directory for the canary, builds a second store over the same directory and gets the account back, deletes the key and sees the record become unreadable and deleted.
- **`transport-canary`** calls `restoreSessions` through the seam recorder after its sign-in (the session is listed) and after its logout (it is not). The recorder scans both results; the existing logcat judge already knows the issued token.
- Not proven on a device: a restore in a new process of the real app (Risks).

## Risks and out of scope

- **A restore in a new process of the real app is not run on a device.** The JVM tests build a new store over the same directory; the probe does the same with the real Keystore. The first true relaunch is the owner's.
- **No device-to-device transfer is run** (backlog 266). The exclusion rests on Android's documentation of the no-backup directory and on the declarations.
- **A not-validated Home** (Q4): when the server cannot be reached at launch, Home opens and its rows show their error states. A revoked token is then found only at the next launch that reaches the server.
- **Several stored sessions** (Q5): only the newest opens; the others stay stored and unseen until T4-06.
- **A wire or e2e run on a real TV** that signs in and does not log out leaves a fixture record in the app's data, because the e2e and release apps share an application id. Every wire test that signs in logs out today; a crashed one may not.
- **Whether a TV's Keystore key is hardware-backed** is not checked; the design does not depend on it (decision 0005).

- **Whether the fake adb of the frozen smoke tests tolerates the extra `pm clear` call** is **[unverified]** (`scripts/tv-first-focus-watch.test.ts`, `tv-dev-server-watch-controls.test.ts`). If one fails, D10 returns to the Product Owner.

## Dependencies

None adopted. The store uses platform APIs: `java.security.KeyStore` with the `AndroidKeyStore` provider, `javax.crypto.Cipher`, `android.security.keystore.KeyGenParameterSpec` (API 23; the app's minimum is 24) and `java.io.File`.

- Why not a library: `androidx.security:security-crypto` deprecated all its APIs in favour of the platform's (decision 0005, read there on 2026-11-20). `expo-secure-store` returns the value to JavaScript, the crossing decision 0005 removes. A JavaScript storage package would be a general store JavaScript can write to.
- Read on 2026-11-26: <https://developer.android.com/privacy-and-security/keystore> ("Key material never enters the application process") and the `KeyGenParameterSpec.Builder` reference (added in API 23; `setRandomizedEncryptionRequired`). Each has a recommendation; none is asked of the owner.

1. **Who builds `sessionEnded`?** The allowlist marks it pending for T4-05, but no T4-05 item needs an event, and T4-08's items 2 and 3 name it. Recommend: T4-08 builds the event, the native confirmed-401 rule and the `store-unreadable` report; this task changes the pending label and the `docs/security.md` line to T4-08. Otherwise this task grows by the event, the cross-module "stop any player" and their tests.
2. **The result of `restoreSessions`.** Recommend `{ sessions: [{ session, server, deviceId, userId, userName?, serverId? }] }`: the base URL in place of `origin` (the T2-04 amendment already carries it everywhere else) and the DeviceId added, since the core cannot derive it again and playback needs it. An amendment to decision 0005 records it.
3. **Who validates, and the logout after a revoke.** Recommend the core validates with `GET /Users/Me` and counts two 401 answers as confirmed, then calls `endSession`. That sends one `POST /Sessions/Logout` with the dead token, where decision 0005 says "without the logout call". The alternative is native validation, which is T4-08's rule built early.
4. **A launch that cannot reach the server.** Recommend Home, not validated: its rows already have error states with Retry, and no new screen or sentence is needed. Alternatives: a new "Couldn't reach {address}" screen with Try again (new look, existing words), or sign-in (which asks a signed-in viewer to sign in again).
5. **Several stored sessions before T4-06.** Recommend: open the newest, keep the rest untouched. The alternative, ending the others at each sign-in, would be undone by T4-06.
6. **Back at sign-in after a 401.** Recommend: Username filled, focus on Password, the empty password held until an edit, and no sentence explaining the return. A sentence would be new on-screen wording.
7. **While restoring.** Recommend the existing line "Loading…" alone on `surface0`, and 5 s for each of the probe and the validation.
8. **The smoke test.** Recommend D10: clear the app's data on an emulator only, and never on a real TV.
9. **A save the Keystore refuses.** Recommend: the sign-in stands for this launch and nothing is stored. Failing the sign-in would lock a viewer out of a TV whose Keystore is broken.
10. **No sign-out control ships here.** The function exists and is tested; the viewer's control is T9-05's and T4-06's. Until then a viewer signs out only by clearing the app's data. Recommend accepting that for this task.
