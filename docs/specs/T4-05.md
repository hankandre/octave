## Goal

The owner signs in once. On every later launch Octave opens Home with no sign-in screen, once the server has answered as the one the sign-in was made on. The token is kept only by Kotlin: in memory, and as one record per account encrypted under a key in the Android Keystore.

## Approach

### D1. The record

- One file per account: `<noBackupFilesDir>/octave-sessions/<name>`. `<name>` is the hex SHA-256 of the server id, a line feed and the user id. A new sign-in to the same account replaces the file.
- A sign-in whose answer holds no server id is **not stored**: the viewer is signed in for that launch only (Q11).
- Bytes: a version byte `0x01`, the 12-byte IV, then the ciphertext with its 16-byte tag. The associated data is the file's name, so a record copied under another name does not open.
- Plaintext: UTF-8 JSON with exactly `server`, `deviceId`, `token`, `userId`, `serverId`, and optionally `userName`. Kotlin builds the header again at restore from the token, the DeviceId and the current client identity.
- A write goes to a temporary file, which is synced, then renamed over the record.
- Reading a record has three answers (issue 4):
  - **Corrupt**: over 64 KiB, empty, an unknown version, a failed tag, text that is not that JSON, another key, an empty token, no server id, a `server` that `ServerAddress.parse` refuses, or the key's alias positively absent from a Keystore that loaded. The record is deleted and not listed.
  - **Unavailable**: any other Keystore, provider or file error. The record is kept, not listed, and no session is opened. A later restore with a working Keystore lists it.
  - **Read**: the session is opened (D4).

### D2. The cipher

- `RecordCipher.open(sealed, associated)` answers the plaintext, corrupt or unavailable. `seal(plain, associated)` answers the sealed bytes or unavailable. Neither carries a message.
- `KeystoreCipher`: provider `AndroidKeyStore`, alias `octave.session.v1`, AES, 256 bits, GCM, no padding, encrypt and decrypt only. No user authentication (decision 0005). Randomized encryption stays required, so the Keystore makes each IV. StrongBox is not asked for.
- A key is generated only when the alias is positively absent from a Keystore that loaded. It is never generated or replaced after a failure.
- A save that is unavailable leaves the viewer signed in for this launch and nothing stored (Q9). No error code is added.
- The plaintext array is overwritten after use. Kotlin cannot clear the token's `String`.

### D3. Where the code lives, and the lock

- `SessionStore` and `RecordCipher` sit in `http/`, in plain Kotlin, so they run on the JVM with a cipher the tests supply.
- `KeystoreCipher` and the factory `SessionStores.of(context)` sit in `dev.octave.session.store`. The cipher sees plaintext bytes and never a header or a session id. `OctaveSessionModule` and the probe both build the store through the factory, over `context.noBackupFilesDir`.
- The registry stays the one process-wide index. A `SessionEntry` may carry its account: the base URL, the DeviceId, the user id, the user name, the server id and the record's `File`. `SessionRegistry.open` gains a defaulted parameter, so every frozen caller compiles unchanged.
- **One process-wide lock** guards save, forget and restore. Under it: the "no live entry names this record" check and the open that follows; the open of a sign-in's entry and the write of its record; every delete, including a leftover temporary file. No request is sent under it.
- When a new sign-in replaces a record, older live entries that named it stop naming it, so ending an old session never deletes a newer record.
- With no React context the transport has no store: nothing is saved or restored for that call. Forgetting needs no store, since the entry holds the file (D5).
- Nothing here logs. `toString` of the new classes is redacted.

### D4. `restoreSessions`

- JavaScript: `restoreSessions()` takes nothing and resolves `{ sessions: [ { session, server, deviceId, userId, serverId, userName? } ] }` (Q2). It never rejects on purpose and has no error value: a store that cannot be read gives an empty list.
- Kotlin, `SessionTransport.restore()`, under the lock:
  1. Read each record that no live entry names (D1).
  2. Parse its address and call `servers.check`. A refusal skips the record and **keeps** it: a development build neither opens nor destroys it.
  3. Build the header and call `SessionRegistry.open`, here in `SessionTransport.kt`.
  4. Answer every live entry that carries an account, newest record first (by the file's modified time).
- A second call in the same process answers the same ids (`docs/security.md:55`), because the registry outlives the module instance.
- It sends no request. Validation is the core's (D6).

### D5. Sign-in and sign-out

- `signIn`: under the lock, open the entry and save the record. The result map is unchanged.
- `endSession`: under the lock, delete the record the entry names, then take the entry. Then, outside the lock, send the logout with the entry in a local value. The result is unchanged.
- A delete that fails is followed by a truncate to no bytes and a second delete. A file left behind holds no token, reads as corrupt and is removed by the next restore.
- `request` is unchanged. A 401 inside a session does not end it in this task (Q1, T4-08).

### D6. The core

- `ports/transport.ts` gains `RestoredSession` and a separate port, `SessionRestore { restoreSessions(): Promise<readonly RestoredSession[]> }`. `Transport` keeps its three members, so no test double changes.
- `JellyfinGateway.adopt(restored)` takes the session, user id, user name and DeviceId. It throws unless `restored.server` normalizes to its own `serverUrl` **and** a `connect()` on this gateway has answered with `restored.serverId`. It writes nothing to the confirmation store.
- `JellyfinGateway.sessionStanding(signal)`: `GET /Users/Me`. A 2xx is `valid`. A 401 is asked once more; a second 401 is `revoked`. Anything else throws as today.
- `restoreSession({ restore, gateways, timeoutMs }, signal)` in `jellyfin/restore-session.ts`, on the newest listed session only (Q5):

| What happens | Outcome | The record | Requests that carry the session |
|---|---|---|---|
| Nothing listed | `none` | n/a | none |
| The probe fails, or answers with another server id, an unsupported version, a redirect or an unusable answer | `unavailable` | kept | none |
| The probe matches and `sessionStanding` is `valid` | `signed-in` | kept | `GET /Users/Me` |
| `sessionStanding` is `revoked` | `sign-in-again`, after `gateway.logout()` | deleted | `GET /Users/Me` twice, one logout (Q3) |
| `sessionStanding` throws | `unavailable` | kept | `GET /Users/Me` |

- There is no not-validated Home (Q4). No request carrying the session leaves before a probe in this launch has answered with the record's server id at the record's origin, for every scheme (issue 2).
- For a private-LAN `http://` server that id match stands in for a new confirmation at launch (Q11, the Product Owner's reading of decision 0001 §7). No confirmation is stored or derived: a later sign-in to that server asks the dialog again.
- `signed-in` carries `{ gateway, serverName }`. `sign-in-again` carries the gateway, its `ServerConnection` and the user name. `unavailable` carries the address and a `ServerChoiceFailure` from `serverChoiceFailure`; another server id is `other`.
- The probe and the validation each get 5 s, and nothing is tried a second time by itself (Q7).
- The wired `gateways` passes the sign-in services' confirmation store, so a confirmation given on the way back (D8) is the one the sign-in steps read.
- The app's adapter (`host/transport.ts`) implements `SessionRestore`: it keeps only entries whose fields have the right types and whose id is 32 lower-case hex digits, and answers an empty list for a rejection or any other shape.

### D7. The composition root

- `AppRoot` takes an optional `restore` part. Without it, it behaves as today, so the frozen `app-root.test.tsx` holds.
- With it, the root shows "Loading…" (`LOADING_LINE`) alone on `surface0` until the outcome arrives. No sign-in control mounts before it. A restore that rejects is `none`.
- `none`: sign-in's first step. `signed-in`: Home. `sign-in-again`: D8.
- `unavailable` (Q12) draws `RestoreUnavailable`: the sentence `signInSentence(failure, address)` in `text1` with no icon and the heading role, then "Try again" (primary, focused), then "Change server" (quiet, last). No new words.

  - "Change server" opens sign-in's first step and keeps the record.
- Back on "Loading…" and on `RestoreUnavailable` leaves the app (Q7, T4-02 C2).
- `AppRoot` gives `SignedInApp` a `signOut` part: `gateway.logout()`, then `account.deactivate()`, then sign-in's first step. No screen calls it yet (Q10; T9-05, T4-06).

### D8. Back to sign-in with the server and user chosen

- `SignInApp` and `SignInFlow` take an optional `start: { gateway, connection, username? }`.
- When `connection.needsUnencryptedConfirmation` is false (HTTPS, loopback), the flow opens on the step after the server step, with that server's sign-in methods. Back and "Change server" go to the server step.
- When it is true (Q13), the flow opens on the server step with the unencrypted-connection dialog already open for that server and "Cancel" focused. `ServerStep` and `useServerChoice` take the opening question as an optional value. "Connect without encryption" records the confirmation and goes to the next step, as the step's own `connect` does. Cancel and Back close the dialog and leave the server step with its usual opening focus.
- The flow keeps `start.username` for that server's address and hands it to the password step as the optional `initialUsername`. With it, Username starts filled, focus opens on Password, and the step starts **held**: an empty password is not sent until the viewer edits a field (Q6; T4-04 R7; backlog 410).
- No sentence says why the viewer is back (Q6).
- Every new prop is optional. If a frozen T4-02 or T4-04 step test still fails, the implementer returns the question and edits none.

### D9. The account's settings

- `App.tsx` wires `account: { activate: (gateway) => hostPreferences().useAccount(accountPreferenceSourceOf(gateway)), deactivate: () => hostPreferences().useAccount(undefined) }`.
- `AppRoot` calls `activate` when a sign-in finishes and when a restore ends `signed-in`, and `deactivate` in `signOut`. A rejection is dropped.

### Issues

1. **High. A stored session whose server cannot be reached locks the viewer out of sign-in (D6, Q4, Q5, Q10 together).** A probe that cannot reach the server gives `signed-in`, on every launch. Nothing on screen then leads to sign-in: there is no sign-out control (Q10), Settings is a placeholder, and only the newest record opens (Q5). A server whose address changed (a new DHCP lease on an IP-literal address, a moved or retired server) leaves Home with error rows for good, where today each launch offers the address field. A fixture record left by a crashed wire run on a real TV does the same and shadows the owner's own record. Clearing the app's data is the only way out. The spec must give the unreachable outcome a way to sign-in's server step (for example its own outcome that shows the existing "Couldn't reach {address}…" sentence with "Try again" and "Change server", or sign-in opened on that server), and a test that proves the viewer can reach the address field from it.
2. **High. The not-validated path sends the token with no server-id match, which breaks decision 0001 for a plain-HTTP server (D6, `adopt`).** `adopt` asks no confirmation, on the ground that the viewer confirmed before the sign-in. That holds only while the server at the origin is the one confirmed: decision 0001 §7 keys the confirmation by (server `Id`, origin) and asks again when another `Id` answers. The validated path keeps this (the probe's id is compared first, "the token is never sent"). The unreachable-probe path and the "`sessionStanding` throws" path do not: Home's Retry and every later call send the token to whatever then answers at that origin, in clear on a private-LAN `http://` address, with no id check and no confirmation in this launch (the TV's confirmations last one launch, `docs/security.md` §3). Before persistence that window was one launch; now it is every launch. Required: no authenticated request leaves for a restored session until a probe in this launch has answered with the record's server id (at least for plain HTTP; simplest for all), with a test that a restored gateway whose probe failed sends nothing carrying the session. State in the 0005 amendment and `docs/security.md` §3 that a restore over plain HTTP rests on the id match in place of a new confirmation; that reading of decision 0001 is the Product Owner's to rule (question 11 below). Also say what a record with no `serverId` does at restore (D1 allows one; nothing can be compared): refuse to restore it, or do not store it.
3. **High. A 401 at launch on a plain-HTTP private-LAN server lands on a step that cannot sign in (D8).** The unencrypted-connection dialog lives only on the server step (`use-server-choice.ts`, kind `confirm`), and the confirmation store is in memory. D8 opens the flow past that step, so `initiateQuickConnect` and `login` throw `not-confirmed` (`gateway.ts`, `requireTransportConsent`) until the viewer finds "Change server" and picks the server again. This is the common home setup, and it is acceptance item 3. The spec must say how the confirmation is asked on this route (for example the server step opened with that server's dialog, or the dialog shown before the next step), keep "Cancel" focused, and add the Jest case for a private-LAN `http://` server.
4. **High. A transient Keystore or I/O failure is treated as a corrupt record, and a failed key can be replaced (D1, D2).** `RecordCipher.open` returns null "on any failure", and null means unreadable, which means deleted. A Keystore that is briefly unavailable (the daemon not ready after boot, a `ProviderException` or `KeyStoreException` that is not about the key or the data) or a file read that fails would silently delete a good credential. "A key that … fails makes every record unreadable and the next save makes a new key" would also overwrite a key that still opens other accounts' records. Required: `open` distinguishes three answers. *Corrupt* (unknown version, over the size bound, a failed tag, not the JSON, a refused address, or the alias positively absent from a Keystore that loaded): delete. *Unavailable* (any other Keystore, provider or I/O error): keep the record, list nothing for it, open no session. A key is generated only when the alias is positively absent, never after a failure. JVM tests with a cipher double for each: an unavailable cipher leaves the record on disk and a later restore with a working cipher lists it; a save with an unavailable cipher replaces no key.
5. **Medium (fix in this spec). No lock is stated for save, forget and restore.** The registry is process-wide and a new module instance builds a new transport, so the lock must be process-wide too. Without it: (a) a `restore` that read a record's bytes before an `endSession` deleted it opens a session for a signed-out account, with a live token if the logout failed; (b) two concurrent `restoreSessions` calls (a reloaded JavaScript runtime) each open a session for one record, against "the same ids back"; (c) `restore` deleting "a leftover temporary file" removes the file of a `signIn` save in flight; (d) a `signIn` whose entry is open and whose record is not yet written, or the reverse, is seen half-done. State one process-wide lock around the three, that the "no live entry names it" check and the open happen under it, and that a temporary file is deleted only under it. Add a JVM test for (a) and (b).
6. **Medium. Sign-out can leave the record.** (a) "With no React context the transport has no store": an `endSession` on such a transport takes the entry and deletes nothing, so the next launch restores a signed-out account. The entry, or a process-wide holder, must carry what is needed to delete, or the store must outlive the module instance. (b) What `endSession` does when the delete itself fails is not said; say it (truncate then delete, and never report `{}` as if the record were gone without a second attempt), and test it. (c) Order: delete the record before taking the entry, so a process death between the two cannot keep a record for a session that was ended.
7. **Medium. No run proves a restore across process death with the real Keystore.** The probe builds its second store in the same process, and the first real relaunch is left to the owner. Two invocations of the probe (save in one `am instrument` run, restore in the next) prove it on the emulator at small cost; add it to the `stored-credential` stage or say why not. A relaunch of the real app stays a backlog line.
8. **Medium. `transport-canary` on a device that holds a real record.** The e2e app shares the application id and the signing key, so on a real TV `restoreSessions` opens and lists the owner's session to the harness: a server address and a user name. State that the test finds its own session by the id its sign-in returned, asserts nothing about the list's length, and that no field of a restore result is written to an `OCTAVE_WIRE` line or an evidence file. Add the shadowing case of issue 1 to Risks.
9. **Low. Item 3's "user already chosen" on the Quick Connect route.** Only the password step shows the name; the Quick Connect step shows the server alone. Say so in the acceptance row (it is the Product Owner's reading, with Q6).
10. **Low. `none` after a redirect or an unusable probe answer** (a captive portal, a proxy error page) shows sign-in to a signed-in viewer with the record kept, while an unreachable server gives Home. Once issue 1 is fixed, route these the same way as unreachable.
11. **Low. No sync before the rename.** A TV that loses power just after sign-in can keep an empty or partial record, which reads as corrupt and is deleted. Sync the temporary file before the rename.
12. **Low. Records that are never opened stay on disk** (an account left behind by the `none` path) with no way to remove them until T4-06 or T9-05. Name it in `docs/security.md` as built.
13. **Low. `updateAAD` on the Keystore's AES-GCM cipher** joins the GCM claim as **[unverified]** until the probe runs. The backlog number for the transfer is 266 in Risks and 267 in the table; 266 is the transfer, 267 the marker.
14. **Low. Item 6 on a device** reads the probe APK's data directory, not the real app's. Say so in `docs/security.md`: the real app's shared preferences and files after a sign-in are covered by the JVM test and the source scans, not read on a device.
15. **Low. `scripts/tv-session-store.test.ts` is three source scans.** Keep the one the acceptance asks for (item 8's, in Kotlin) and prefer the probe's behaviour proof to "the module builds the store with `KeystoreCipher`" where one exists.
