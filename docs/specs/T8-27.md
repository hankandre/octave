## Goal

With only the picture showing, the remote does what every TV video app has taught the thumb (Android TV quality checklist, TV-PC): select pauses, Left and Right step 10 s; and a focused scrubber is unmistakable from three metres.

## Facts

Read 2026-11-26 in this worktree.

- **The key rules** are one pure reducer, `chromeState` (`apps/tv/src/player/chrome-keys.ts:69-96`), returning `{ state, command? }` with one command from `show-scrubber | show-play | seek-back | seek-forward | toggle | pause | resume` (`:46`). From a hidden chrome every arrow returns `show-scrubber` and no seek (`arrow`, `:57-61`); `holderPress` returns `show-play` and no toggle (`:86-87`); `playPause` toggles in every state and a pause shows a hidden chrome (`transport`, `:64-67`).
- **Where focus goes on showing** is derived from the command: `setTarget(result.command === "show-scrubber" ? "scrubber" : "play")` (`use-player-chrome.ts:71`). A hidden Left that also seeks cannot be told apart from a show on Play with this shape.
- **Select from the picture** is read only from the focus holder's `onPress` (`player-screen.tsx:118-125`); the hardware `select` is `activity` (`use-remote-keys.ts:11-26`). Focus moves to the target in an effect after the commit (`player-screen.tsx:96-98`), so the control that takes focus never saw the press begin (T8-04 D4).
- **Before the first frame** the key rules do not run: `active: layer === "picture"` (`player-screen.tsx:89`, `use-player-chrome.ts:80`), the holder is not focusable while loading (`:121`), and `Viewing.seekBy`/`setPaused`/`togglePaused` do nothing unless the phase is `playing` (T8-04 D3).
- **Keys reach JavaScript at key up.** `use-remote-keys.ts:33` drops any event whose `eventKeyAction` is not 1. react-native-tvos 0.88.1-0 names a key held past 300 ms `longLeft`, `longRight`, `longUp`, `longDown` or `longSelect`, on a key down and again on key up, and then never sends the short name for that press (T8-04 Facts, "Keys", and its Implement ruling). `long…` arrows map to `heldArrow`, which shows the chrome and never seeks (`chrome-keys.ts:23-24`, `:73-74`).
- **The scrubber** draws a thumb only while focused, `sizes.scrubThumb` (16) wide in `text1`, with no ring; the track grows from `scrubTrackH` 4 to `scrubTrackHActive` 8; the rail is `scrubThumb` tall and does not clip (`player-scrubber.tsx:80-113`). The row is the focusable `Pressable`; it is a wide control, so it never lifts (`DESIGN.md` §9, "What lifts"). `FocusRing` (`design/focus-frame.tsx`) draws the two-tone ring around any parent that does not clip, its radius following a `radii` key.
- **`scrubThumb`** appears in no test but `scripts/design-tokens.test.ts` (T3-06, frozen), which holds `tokens.ts` to `DESIGN.md` §8 in both directions.
- **Progress posts** come every 10 s (`playstate-reporter.ts:9`) and on each pause, resume and seek (`coordinator.ts:389-393`).
- **Android TV guidance**, read 2026-11-26 at `https://developer.android.com/docs/quality-guidelines/tv-app-quality`. TV-PC is in **Tier 3, TV Ready**, the floor: "While a video or audio is playing, pressing the D-pad center button pauses the media that is playing. When playback is paused, pressing the D-pad center button resumes playback. The D-pad left and right buttons fast-forward and rewind the current track, respectively." TV-PP: the play-pause key toggles. Whether Play's review enforces TV-PC is unverified (decision file, call 4).

## Approach

### D1. The reducer separates where focus goes from what the transport does

```ts
export type ChromeCommand = "seek-back" | "seek-forward" | "toggle" | "pause" | "resume";
export type ChromeResult = { state: ChromeState; command?: ChromeCommand; focus?: "scrubber" | "play" };
```

`focus` is set exactly when the input shows a hidden chrome. Two commands per input (show and seek) would make a list for one case; a separate field keeps one command and states the target directly instead of decoding it from the command.

| Chrome | Input | Result |
|---|---|---|
| hidden | `up`, `down`, `heldArrow` | shown, `focus: "scrubber"`, no command |
| hidden | `left`, `right` | shown, `focus: "scrubber"`, `seek-back` / `seek-forward` |
| hidden | `holderPress` | as `playPause`: `toggle`; a pause shows with `focus: "play"`, a resume leaves it hidden |
| hidden | `playPause`, `pause` | as today, plus `focus: "play"` when it shows |
| shown | anything | as today |

- `holderPress` is the play-pause rule so a hidden, paused picture (an engine-side pause) resumes on select like it does on the play-pause key, instead of a second rule for a rare state.
- Hidden is only reachable while playing (the idle timer stops when paused), so in practice select from the picture pauses.
- The seek's target shows at once: the scrubber draws `seekingTo` (`player-scrubber.tsx:42`), so the chrome appears already reading the new time.
- `heldArrow` from hidden is unchanged: it shows and does not seek (D3).

### D2. The focused thumb

- `sizes.scrubThumb` 16 → 24; no new token. Only the focused scrubber draws a thumb, so "unfocused as today" holds with one value.
- The thumb renders `<FocusRing radius="radiusPill" testID="player-scrubber-thumb-focus-ring" />` as its child. The scrubber is a row, so nothing lifts or scales (§9); reduced motion changes nothing here.
- Room for focus (§9): the ring reaches 7 px (`focusOffset` 3 + `focusRingWidth` 3 + `focusEdgeWidth` 1), so the thumb and ring need 38 px of height, inside the row's `hitMin` 64; at 0% or 100% the ring reaches 19 px past the track's end, inside the `space5` 24 gap before the time. The rail (`scrubThumb` tall) does not clip; the track keeps `overflow: hidden` and the thumb stays its sibling.
- The track still grows to `scrubTrackHActive`. The review's bolder times and brighter track are not taken (call 5).

### D3. Key up, and room for T8-05

- **Every new action fires at key up.** The pause lands when select is released, not pressed: the press's length plus one bridge crossing. Unmeasured on the Shield and the cheap box (backlog line 373, T8-21). Nothing here needs key down.
- **A hold never takes a 10 s step.** A press held past 300 ms arrives only as `long…`, never as `left` or `right`, and `heldArrow` seeks nothing. So T8-05's "a single press still moves exactly 10 s" holds as built, and T8-05 gives `heldArrow` (and, if it needs them, key-down events, read only in `use-remote-keys.ts`) its meaning without undoing a step.
- **Not built here:** anything for a held arrow or a held select; the key-down filter stays as it is. Whether a held select reaches the holder's `onPress` at release is unverified (react-native-tvos `Pressable` with no `onLongPress`); the tests press select short, and T8-05 owns `longSelect` (T8-04's call 3 condition: while a scrub is pending, select commits).
- The holder still names itself in all four directions, so the key down of a waking arrow moves nothing natively and focus moves once, at key up.
